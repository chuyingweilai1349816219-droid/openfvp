# 线程与时间模型（研究笔记）

> 以下内容由 DeepSeek 生成,不一定代表作者个人意愿

FVP 脚本是**多线程/协程**驱动的。本文记录已经确认的事实、失败的尝试，以及 2026-11-24 的最终结论。

> **2026-11-24 更新：协程槽已实现，并实测"行为中立"。** 本文 §7 里「函数体在等时间/输入条件」
> 的推断、§9 里「台词缺失的主因是 ThreadStart 未实现」的结论**都已被推翻**——真正的原因是
> VM 的一个帧返回地址 bug 加上脚本里协程体被编译器常量关掉了。详见 §10。

## 已确认（来自 handler 静态分析）

线程上下文数组：`engine + 0x68dfc0`，**32 个槽**，每槽 **0xB28 字节**。
当前线程号：`engine + 0x6a66d0`。
线程结构内部字段（相对槽起点）：

| 偏移 | 含义 |
|---:|---|
| +0x808 | 等待标志位（bit1 = wait，bit2 = sleep） |
| +0x80c | 等待/睡眠的毫秒数 |
| +0x810 | 「需要切换」标志（ThreadNext 置 1） |

| 命令 | id | 行为 |
|---|---:|---|
| `ThreadExit` | 132 | 参数 0 = 结束全部子线程；非 0 = 结束指定线程 |
| `ThreadNext` | 133 | 把当前线程的 +0x810 置 1，即让出执行权（轮转） |
| `ThreadRaise` | 134 | 对 32 个线程槽逐个调用 **0x4447e0(ctx, ms)**，后者的全部逻辑是 `if ((flags & 4) && ctx->wait_ms == ms) flags &= ~4;` —— **叫醒睡眠时长正好等于 ms 的线程**（只认 ThreadSleep 的 sleep 位 0x4，不认 ThreadWait 的 wait 位 0x2）。arg1 必须是 int，否则整条命令丢弃。**本站已实现**（`fvp_vm_thread_raise()`，见 `docs/vm-commands.md`）；实测 90 万步 0 次调用 |
| `ThreadSleep` | 135 | +0x808 |= 4，+0x80c = 毫秒数，+0x810 = 1 |
| `ThreadStart` | 136 | (线程号 0..31, 入口地址)；号为 0 时先重置所有槽 |
| `ThreadWait` | 137 | +0x808 |= 2，+0x80c = 毫秒数，+0x810 = 1 |
| `TimerSuspend` | 140 | 参数 == 1 时置暂停标志 `engine+0x6a66bc` |

实测用量（90 万步）：`ThreadStart` 5 次、`ThreadNext` 263 次、`ThreadExit` 19 次、`ThreadWait` 1 次、`TimerSet` 259 次、`TimerSleep` 0 次。

## 另一个发现：`initstack a b` 的第二个操作数

之前实现里忽略了 `b`。静态分析与脚本里都能看到形如：

```
0x05aaec  initstack 0 4
0x05aaef  pushint8 0
0x05aaf1  copystack 3      ← 写 4 号槽，但局部变量声明是 0 个
```

说明 `b` 是**参数个数**，参数被放在帧槽位 `0..b-1`；`a` 才是局部变量数。
也就是说帧大小应为 `a + b`，而不是 `a`。

在 Python 原型里改成 `a+b` 并复制参数后，开场文本从 195 行里的前 29 行推进到 34 行（多恢复了 5 句，包括第一句真正的对白「おはよう。大丈夫か？……」）。

**注意**：现有冻结基准（`ref/`）和 C 版 VM 都还是「只用 a」的旧行为，两者一致所以等价性测试通过，但与原版可能不符。改这条要重新做基准。

## 失败的尝试（别再走一遍）

1. **纯轮转调度**（`ThreadNext` 不设阻塞、直接换下一个线程）：90 万步只有 29 行，卡住。
2. **加阻塞恢复**（stall 两轮后解锁）：同样卡住。
3. **帧大小改 a+b**：略有改善（34 行），但仍卡住。

## 第三轮：时间模型 + 抢占式调度（有进展，未完成）

实现内容（`work/fvm_time.py`）：

- **虚拟时钟**：16 ms / 帧，`now_ms` 单调递增
- **16 个定时器**：`TimerSet(id, ms)` 记录起点，`TimerGet(id, default)` 在计时中返回已过毫秒、否则返回 default（语义来自 handler 静态分析）
- **32 线程槽**：`ThreadStart/Next/Exit/Wait/Sleep` 按上面表格实现
- **抢占**：每个线程单帧最多执行 N 条指令，超出就切走（真实引擎里由线程自己 `ThreadNext` 让出，但有循环不让出，必须抢占）

结果（6000 帧 = 96 秒虚拟时间，单线程预算 1500 条）：

| 单线程预算 | 文本行数 | 说明 |
|---:|---:|---|
| 20000 | 64 | 少数线程空转吃光预算，主线程饿死 |
| 1500 | **711** | 大幅推进，但只有 217 行不重复 |

**预算越小推进越远**——说明真实瓶颈是「有空转循环在浪费时间」，抢占让其他线程能跑。

### 还不能算成功

输出的 711 行里大量是 `[0] 0`（正文层打印出整数 0），以及尾巴上「悠馬／不審者」的重复循环。

**关键诊断（已用探针确认）**：单线程跑的时候，`TextPrint` 收到的**全部是正常字符串**：

```
0x03a6d8  2  int 0   str '　……。'
0x03a6d8  2  int 0   str '　空から羽根が降っている。'
0x03aafb  2  int 9   str '空'
```

只有一处例外是**开场第一句**打印 `int 0`（那时文本全局变量还没被赋值，无害）。

所以「打印 0」不是 TextPrint 的句柄解析问题，而是**我的线程实现把文本变量搞坏了**——最可能是 `ThreadStart(id, entry)` 创建的线程没有参数，而入口函数的 `initstack a b` 声明了 `b>0`，我从空参数表里复制出 `b` 个 0，覆盖了本该由协程上下文提供的内容。

也就是说：**单线程是对的（195 行全部正常），线程版是错的**。修线程比修文本句柄更接近问题本质。

## 时间模型的接口约定（给 C 版用）

```
fvp_tick(engine, dt_ms)      // 推进时钟、更新定时器、跑一帧调度
  for each thread: 最多执行 N 条指令
  timer[16].elapsed += dt_ms
```

`N` 需要实测调参；当前 Python 原型里 1500 条/帧效果最好。

## 卡住的直接原因

热点是一条**永远立即返回**的循环体：

```
0x05aaec  initstack    0 4
0x05aaef  pushint8     0
0x05aaf1  copystack    3
0x05aaf3  pushint8     0
0x05aaf5  jmpcond      0x5bd96    ← 常数 0 = 假 → 直接跳到 ret
0x05aafa  <真正的工作：输入、绘制、调度……>
```

`jmpcond` 在条件为假时跳转（已被 948,219 条指令的解析验证过，且 2026-11-24 又用"把方向反过来
跑一遍"反证过：反向后 90 万步只出 **0 行**台词），所以这里每次都被跳到结尾的 `ret`。

> **当时的错误结论**：以为"这个函数在等一个由时间/输入驱动的条件，我们没有 Timer 所以不成立"。
> 实际上条件是**编译期常量 0**，它永远不成立——在**原版引擎里函数体也一次都不执行**。
> 真正让调用方空转的是 §10 里那个 VM bug（栈底帧 ret 指回自己 → ret 死循环），不是缺时间模型。

## 9. C 引擎里的量化诊断（2026-11，90 万步）

加了两个诊断开关后拿到的硬数据：

```

  thread 0: text lines 195          <- 只有主线程打印，其它线程一个都不存在
  unknown cmds: ... 136×5, 132×19, 130×124, 139×259 ...
```

| 事实 | 含义 |
|---|---|
| **195 行全部来自 thread 0** | C 引擎里从未创建过第二个线程 |
| `ThreadStart`(136) 被调用 **5 次** | 脚本确实要起协程，但我们的实现是空的 |
| `ThreadExit`(132) **19 次**、`TextSuspendChr`(130) **124 次** | 线程生命周期与逐字挂起都在被使用，且都是桩 |
| `TimerSet`(139) **259 次** | 计时器同样在脚本里被用到（我们只有虚拟时钟，没有 Timer* 实现） |

### 为什么不能「顺手实现」了事

本文 §3 记录过 Python 原型的 32 线程尝试：加了线程与抢占后文本行数从 195 涨到 **711**，
但其中大量是 `[0] 0`，且只有 217 行不重复 —— 原因是 `ThreadStart` 创建的线程**没有参数**，
而入口的 `initstack a b` 声明了 `b > 0`，于是从空参数表复制出 `b` 个 0，把协程上下文冲掉了。

所以「约 50 句台词缺失」的修复路径是：**先把 `ThreadStart` 的参数语义搞清楚**（协程入口靠什么拿上下文），
再实现 32 槽调度；否则只会把 195 行正常文本换成 711 行垃圾。

## 10. 协程槽已实现，并证明对本作"行为中立"（2026-11-24）

### 10.1 先修掉的 VM bug：栈底帧的返回地址指回了自己

`initstack a b` 有两种情况：

* **跟在 `call` 后面**（帧 marked pending）：填局部变量，正常；
* **没有 `call`**（线程/函数的入口第一条指令）：需要新建一个"栈底帧"。

旧实现把栈底帧的返回地址写成 `ins->pc`，也就是 **`initstack` 自己所在的位置**。于是函数末尾的
`ret` 会跳回 `initstack`，再执行一遍函数体、再 `ret`……**无限自循环**。90 万步里被记为
"58,908 次空转"的正是这条路径，当时误判成"在等时间条件"。

修法只有一行：栈底帧的返回地址 = `script_len`（脚本末尾）。`ret` 之后 `pc` 越界，调度器回收线程。
主线程永远不从栈底帧返回，所以**关闭协程时这条改动完全不影响基线**。

### 10.2 修完之后，协程入口的真面目

5 次 `ThreadStart` 的实测参数（`work/probe_threads3.py` 探针，90 万步）：

| 步数 | 调用点 | 槽号 | 入口 |
|---:|---|---:|---|
| 12,631 | `0x03643e` | 1 | `0x05aaec` |
| 12,634 | `0x036448` | 2 | `0x05c079` |
| 22,445 | `0x03643e` | 1 | `0x05aaec` |
| 22,448 | `0x036448` | 2 | `0x05c079` |
| 52,605 | `0x07bcbb` | 12 | `0x07bcf0` |

三个入口的共同结构（以槽 12 为例）：

```
0x07bcf0  initstack   0 0      ← 函数入口
0x07bcf3  pushint8    0
0x07bcf5  jmpcond     0x07bd36 ← 常数 0 = 假 → 直接跳到函数尾的 ret
0x07bcfa  <协程体：图元/补间/输入轮询>
```

**条件是编译期常量 0。** 所以协程体在**原版引擎里也不会执行**：线程建起来、跑两条指令、
`ret` 到脚本末尾、退出。这不是我们缺功能，而是这份脚本编译时就把协程体关掉了
（多半是引擎里那套"自带 tick 协程"在本作里没用上，或者被 `if (0)` 掉了）。

### 10.3 A/B 实测（C 引擎，`--no-threads` 对照）

| 运行 | 步数 | `ThreadStart` | 台词行数 | 文本 SHA256 |
|---|---:|---:|---:|---|
| 协程关 | 900,000 | 0 | 195 | `7f9837ff…b3ea2` |
| 协程开 | 900,000 | 5（5 个全部退出） | 195 | `7f9837ff…b3ea2` |
| 协程关 | 2,000,000 | 0 | 450 | `32d7d4e2…b3856e` |
| 协程开 | 2,000,000 | 6（6 个全部退出） | 450 | `32d7d4e2…b3856e` |

四组里文本**逐字节相同**，且都与冻结基准一致。所以：

* **"约 50 句台词缺失"这个老问题不存在**（至少不是协程造成的）。脚本的推进进度只受步数预算和
  文本节奏限制：90 万步 195 行、200 万步 450 行，线性增长，没有断流。
* 2026-11 的 Python 原型"开线程后 711 行 / 大量 `[0] 0`"是**原型自己的 bug**（栈底帧自循环导致
  主线程被挤、以及 `initstack` 的 `b` 参数被强行当参数表填充），不是真实行为。

### 10.4 现在的实现（C 版）

| 位置 | 内容 |
|---|---|
| `src/vm.h` | `FVP_THREAD_SLOTS 32`、`FvpVM.thread_slots[32]`、`threads_on`、诊断计数 `thread_starts/exits/resets`、`FvpThread.slot` |
| `src/vm.c` | `fvp_vm_thread_start()` / `fvp_vm_thread_exit()`；死线程回收时清槽并计数；**栈底帧 ret = script_len** |
| `src/syscall.c` | `case 136` / `case 132` 接上上面两个函数（`threads_on == 0` 时保持旧空桩） |
| `src/main.c` | 默认开启，`--no-threads` 关闭；汇总多一行 `coroutines on/off: start/exit/reset` |
| `src/platform/win32/main_win32.c` | 同上（默认开，`--no-threads` 关），启动日志 `threads: coroutine slots on` |
| `tests/verify_threads.py` | 门禁：默认/关闭两种模式都必须与 `ref-900k.txt`、`ref-2m.txt` 逐字节相同，且 `start == exit` |

语义要点（沿用 §1 的静态分析结论）：

* `ThreadStart(0, entry)` 先重置 32 个槽，然后**在 0 号槽**建线程（不是"只重置"）；
* `ThreadStart(n≠0, entry)` 覆盖该槽原有线程；
* `ThreadExit(0)` 收掉除自己以外的所有槽；`ThreadExit(n)` 收掉 n 号槽，若 n 就是自己则线程自杀；
* **主线程不在 32 个槽里**，否则脚本开头的 `ThreadStart(0, …)` 一重置就把自己弄死了；
* `ThreadNext(133)` 仍是"让出两轮"的旧语义（本作里它是唯一的主动让出点，实测不影响文本）。

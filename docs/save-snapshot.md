# 存档槽内的「引擎状态快照」

> 以下内容由 DeepSeek 生成,不一定代表作者个人意愿

本文只讲 `save/sNNN.bin` 里**缩略图之后那一大段**（526 KB ~ 599 KB）：它装的是引擎状态，
也就是「读档之后游戏怎么恢复」。文件头、字符串、缩略图、`save.bin` 的格式见
[`save-format.md`](save-format.md)；写档的 C 实现在 `src/save.c`，路径策略见 save-format §6/§7。

**重要前提**：这一段目前**只有结构被量清、字段语义未解**。所以引擎这边的策略是
「**整段不透明透传**」——读进来什么样，写回去什么样，只改已确证的那几个字段。

### 1.4 变长 DENSE 里的字符串池（2026-11-24 新增，已落地）

`+0x19408` 起是一段**字符串池**：u32 标签 `0x20`、u32 个数（≤8），随后逐条
u16 长度 + NUL 结尾的 **cp932 字符串**，条目之间夹 0 填充（实测有，精确对齐
规则未定）。实测：

| 槽 | 解析结果 |
|---|---|
| s481 / s485 | 1 条 = 当前对话行 |
| s905 | 2 条 = **`BG063_000b`（背景图名）** + 当前对话行 |
| s800 / s901 / s906 | 个数为 0（系统/自动槽），解析器如实返回"没有" |

也就是说 §4 第 1 条问的"变长 DENSE 里是什么"至少一部分答案是：
**当时的图名与文本行就存在这里**，而且是**按结构序列化**的，不是内存原样转储
（槽头的章节名 `プロローグ` 在尾段里找不到）。

- 解析实现（C，只读）：`src/savetail.c` / `src/savetail.h`
  （`fvp_savetail_parse`；接入存档列表行文本，见 `title-menu.md` §4.2）；
- 复现：`python fvp/tools/tailstat.py <save 目录>` 现在会打印
  `== 槽尾字符串池 @+0x19408 ==` 一节（与 C 实现同一规则）；
- 详细记录：`save-format.md` §2.5.1。

### 1.3 常量尾（1,438 B，6 个槽逐字节相同）

```
1,438 B = 216 × 6B 定长表 + 140 B 全零 + 末 2B `01 01`
每条记录内容完全一致：00 00 64 00 00 00   →  {u16 0, u16 100, u16 0}
216 个 0x64(=100) 全部落在记录内偏移 +2，间距恒为 6
```

## 4.1 为"真读档"做的定向搜索（2026-11-25）

三个只读工具，目标是把"读档到底缺什么"缩到具体字段：

### 4.1.1 脚本位置（pc）候选：`tail+0x3BB1`

`scripts/find-save-pc.py` 的思路：存档时脚本通常停在**等玩家输入**的命令上
（`InputGetDown/State/Event...`，命令 id 27..36 的 `syscall`）。把这些 syscall 的
指令地址收集起来（iroseka 共 **692** 个），在槽尾里逐字节搜 u32：

| 槽 | 找到的候选 |
|---|---|
| s481 / s800 / s901 / s905 / s906 | **+0x003BB1 → `0x05AB0E`（`syscall 29` = InputGetCursX）** |
| s485（额外一处） | +0x0031FC → `0x03AB18`（`syscall 34` = InputGetState） |

6 个槽在同一偏移出现同一值，说明它是**结构化字段**而不是巧合；值本身是合法指令地址。
注意到 `0x3BB1` 附近是**成对的 `{u32 value, u32 type}` 记录**（type 常见 0/2/3/4/8），
像一张 Variant 数组（`0x5AB0E` 那一条 type=2 即 int）。

**限定表述**：这是"存档里的脚本位置候选"，还不能证明它就是主线程 pc
（可能是某个协程/动画线程的轮询点）。要确认需要结合"读档后从该地址继续执行"的实测。

### 4.1.2 没有 4 字节步长的 pc 数组

`scripts/find-save-contexts.py` 搜"连续多个 u32 都是合法指令地址"的区域：槽尾里
**没有** ≥8 条的此类游程（找到的都是 `0x200002`/`0x00000f` 这类小整数被误判成指令
地址）。结论：**存档里的上下文表不是"每线程一个 4 字节 pc"的裸数组**，要么指针化了，
要么字段更宽（例如 4.1.1 里那种 `{value,type}` 成对结构）。

### 4.1.3 槽尾**没有** save.bin 那张 1471 条全局变量表

`scripts/find-save-variants.py` 按 `{u32 value, u32 type}`（type ≤ 8）扫游程：

| 观察 | 结果 |
|---|---|
| 最长游程（允许 type=0） | 11,245–11,265 条 —— 与 §2.4.1 的 **86 KB 零区**完全吻合，是填充 |
| 最长游程（跳过 type=0） | 63–65 条 @ `+0x2904`/`+0x2914`，type 直方图 **2:31~32、6:32** |

也就是说：槽尾里最像 Variant 表的东西是**一小段"32 组 (int,float) 成对"的记录**，
**不是** `save.bin` 里那张 1471 条全局变量表。全局变量在槽里要么没存（读档时从
save.bin 走），要么用了另一种编码 —— 这与 §2.4 表 A「每槽全局变量 `8 × countA`，
本作 countA 疑似 0」的推定一致。

**对实现的意义**：`Load` 需要的"脚本位置 + 全局变量"两块，目前一块有候选（4.1.1）、
一块倾向于"不在这份文件里"（4.1.3）。下一步应当先验证 4.1.1 的候选（从这个地址继续
执行看会发生什么），再决定 Load 的可行范围。

### 4.1.4 从候选 pc 直接起跑：不行（实测）

为了验证 4.1.1 的候选，给 `fvm` 加了研究用的 `--pc N`（从指定地址起跑，不经过
`main_start`；`src/vm.c: fvp_vm_start_at()`）。实测 iroseka：

| 起点 | 结果 |
|---|---|
| `0x22F48`（= iroseka 真正的 `main_start`，对照组） | **20,000 步**跑满，线程存活 |
| `0x05AB0E`（候选，`syscall 29`） | **85 步**后线程结束（`ret` 弹空栈） |
| `0x03AB18`（候选，`syscall 34`） | **2,147 步**后线程结束 |
| `0x05AB0E` + `--savebin save.bin`（先灌全局变量） | 仍然 **85 步** |

结论：**光有 pc 不够**——候选地址落在某个函数体里，恢复它需要**保存下来的调用栈/帧**
（以及栈上的局部变量）。所以"读档"必须还原 context（pc + 栈 + 帧），而我们前面
（4.1.2）已经证明槽尾里没有"每线程 4 字节 pc"的裸数组，说明 context 的存储方式
要么指针化、要么字段更宽。

**方法学意义**：`--pc` 这个钩子把"能不能只跳 pc"从猜测变成了可复现的实测（上表），
后续无论从哪条路找到 context，都可以用它验证"恢复后能否继续执行"。

### 4.1.5 在 32×0xB28 协程上下文块里找 pc：过滤器太弱（负结果）

按 §2.4.4 的布局，槽尾**开头**就是 32 个协程上下文（每块 0xB28 = 2,856 B，合计
91,648 B）。`scripts/find-save-contexts2.py` 在每个块里找"值是合法指令地址"的 u32：

| 槽 | 上下文块内的"指令地址"命中数 |
|---|---:|
| s481 / s800 / s901 / s905 / s906 | 156–246 |
| s485 | 444 |

命中太多，而且绝大多数是 `0x000102`、`0x010000`、`0x1d0001` 这种**小整数恰好也是
早期指令地址**（iroseka 的前几个 opcode 编码就是 0x000100/0x000102 这类），属假阳性。
跨槽看"同一 (ctx, offset) 在多槽出现"的候选也只有零星几处（如 ctx4 +0x5CC 两个槽
同为 0x058DFF），**无法据此确认 pc 字段**。

**结论**：靠"值域过滤"在上下文块里认 pc 行不通，必须按结构体字段偏移来读——
也就是把 `0x445540`（读上下文）/`0x43F0C7`（槽反序列化）这两个函数里
"上下文的哪个偏移对应 pc / sp / 栈指针"逐一写出来。这是明确的下一步（需要静态分析
这两个函数，工作量 1–2 轮）。

**同时确认的正面信息**：槽尾前 91,648 B 的稀疏性（只有活动协程非零、其余 31 块
接近全零）与 §2.4.4 的"32 个协程上下文"布局**一致**，说明该布局表是可信的。

## 4.2 静态分析确认：序列化的协程上下文里**没有 pc / 栈**

上一轮的负结果（值域过滤找不到 pc）这轮有了确定性解释：静态分析
`0x445640`（写上下文，供 `0x43DE90` 调用）与 `0x445540`（读回，供槽反序列化调用），
一个协程上下文的序列化布局是**固定的 0xB1D = 2,845 字节**：

| # | 字段 | 引擎侧偏移 | 长度 |
|---|---|---:|---:|
| 1 | 文本缓冲 | `ctx+0x008` | **0x800** |
| 2 | u32 | `ctx+0x814` | 4 |
| 3 | u32 | `ctx+0x818` | 4 |
| 4 | u32 | `ctx+0x808` | 4 |
| 5 | u32 | `ctx+0x80C` | 4 |
| 6 | u8 | `ctx+0x810` | 1 |
| 7 | u32 | `ctx+0x81C` | 4 |
| 8 | u32 | `ctx+0x820` | 4 |
| 9 | u32 | `ctx+0x824` | 4 |
| 10 | 字节块 | `ctx+0x81D` 起 | 0x100 |
| 11 | 字节块 | `ctx+0x91D` 起 | 0x200 |

合计 2048+4+4+4+4+1+4+4+4+256+512 = **2,845 = 0xB1D**，与 docs 里"每窗口 0xB1D"的
推定**完全一致**。**清单里没有任何 pc、sp、调用栈或帧**。

**这意味着什么（重要）**：

1. 存档**不是"执行状态快照"**——没有 pc 就无法"从断点继续执行"。这也解释了为什么
   前两轮找不到 pc / pc 数组：**它本来就不存在**。
2. 所以原版的读档只能是**场景/行号式的重放**：恢复全局变量、文本、flag 等状态 → 让
   脚本从某个**场景入口**重新开始 → 快进跳过已读内容，直到存档记录的那一行。多数
   VN 引擎（包括 BGI）都是这个套路。
3 因此 `Load(40)` 的正确目标不是"恢复 pc"，而是：**(a) 找到存档里的"场景 id / 行号"，
   (b) 实现"快进到该行"的重放**。候选位置：上下文里的 `ctx+0x814/0x818`（成对的
   type/value，像"语句返回槽"）、或 `SaveData` 区（kind=2 的已读标记）、或全局变量里
   的场景计数器。

**下一步（具体）**：在"同一场景、不同行"的两份存档之间做**逐字段差分**，重点看
`ctx+0x814/0x818/0x808/0x80C/0x81C/0x820/0x824` 这 7 个 u32 与 §2.4.4 里
"字符串句柄表 / 动态字符串表"两类区域——行号信息必然随进度变化，而它不会在
上下文之外单独存在。

# 存档槽内的「引擎状态快照」

> 以下内容由 DeepSeek 生成,不一定代表作者个人意愿

本文只讲 `save/sNNN.bin` 里**缩略图之后那一大段**（526 KB ~ 599 KB）：它装的是引擎状态，
也就是「读档之后游戏怎么恢复」。文件头、字符串、缩略图、`save.bin` 的格式见
[`save-format.md`](save-format.md)；写档的 C 实现在 `src/save.c`，路径策略见 save-format §6/§7。

**重要前提**：这一段目前**只有结构被量清、字段语义未解**。所以引擎这边的策略是
「**整段不透明透传**」——读进来什么样，写回去什么样，只改已确证的那几个字段。

## 1. 已经量出来的结构

6 个真实存档（2023-03-19，`プロローグ` 附近）实测。所有数字都可由
`python fvp/tools/tailstat.py <save 目录>` 复现。

```
尾段 = 常量头 64 B
     + 变长中段（500,518 ~ 597,482 B，随存档内容变）
     + 常量尾 1,438 B
```

### 1.4 变长 DENSE 里的字符串池（2026-11-24 新增，已落地）

`+0x19408` 起是一段**字符串池**：u32 标签 `0x20`、u32 个数（≤8），随后逐条
u16 长度 + NUL 结尾的 **cp932 字符串**，条目之间夹 0 填充（实测有，精确对齐
规则未定）。实测：

| 槽 | 解析结果 |
|---|---|
| s481 / s485 | 1 条 = 当前对话行 |
| s905 | 2 条 = **`BG063_000b`（背景图名）** + 当前对话行 |
| s800 / s901 / s906 | 个数为 0（系统/自动槽），解析器如实返回"没有" |

也就是说 §4 第 1 条问的"变长 DENSE 里是什么"至少一部分答案是：
**当时的图名与文本行就存在这里**，而且是**按结构序列化**的，不是内存原样转储
（槽头的章节名 `プロローグ` 在尾段里找不到）。

- 解析实现（C，只读）：`src/savetail.c` / `src/savetail.h`
  （`fvp_savetail_parse`；接入存档列表行文本，见 `title-menu.md` §4.2）；
- 复现：`python fvp/tools/tailstat.py <save 目录>` 现在会打印
  `== 槽尾字符串池 @+0x19408 ==` 一节（与 C 实现同一规则）；
- 详细记录：`save-format.md` §2.5.1。

### 1.3 常量尾（1,438 B，6 个槽逐字节相同）

```
1,438 B = 216 × 6B 定长表 + 140 B 全零 + 末 2B `01 01`
每条记录内容完全一致：00 00 64 00 00 00   →  {u16 0, u16 100, u16 0}
216 个 0x64(=100) 全部落在记录内偏移 +2，间距恒为 6
```

216 条这个数量对不上已知的 32 文本窗口 / 10 音频类型 / 256 SE 槽，**语义未知**。
写回时整段照拷即可。

## 2. 那个 118,784 B 稀疏块

| 槽 | 块内非零字节 | 占比 |
|---|---:|---:|
| s481 / s485 / s800 / s901 / s905 | 103 / 112 / 98 / 31 / 104 | **0.03–0.09%** |
| s906（唯一在演出中途存的） | **454** | 0.38% |

5 个槽几乎全零 ⇒ **不是「32 个文本窗口的内容」**（这条早先的猜想已被数据否掉，
`save-format.md` §2.4.2 有订正）。s906 里它是规则记录流，**周期 17 字节**：

```
+0x51000  16 01 | f4 ff ff ff | 34 03 00 00 | 00 00 | 06 00 00 ff 00
+0x51011  f9 05 | f4 ff ff ff | 34 03 00 00 | 00 00 | 07 00 00 ff 00
+0x51022  f2 05 | f4 ff ff ff | 34 03 00 00 | 00 00 | 08 00 00 ff 00
+0x51033  eb 05 | f4 ff ff ff | 34 03 00 00 | 00 00 | 09 00 00 ff 00
```

`int32 = -12`、`u32 = 820`、递增序号 6/7/8/9。**推测**是动画/演出队列（未验证）。

## 3. 现在的工程策略

| 场景 | 做法 |
|---|---|
| 读存档 | 按 §1 的边界切开；尾段整块保留（`FvpSaveSlot.tail`） |
| 写存档（有模板） | 只替换**时间戳 / 三条字符串 / 缩略图**，尾段原样写回（`tests/test_save.c` 有 59 项断言钉住这一点） |
| 写存档（无模板） | **不支持** —— 缺 §4 的语义，硬造只会写出坏档 |
| 桌面外壳 | `--save-template` + `--save-preview[-every N]`，把运行时缩略图和时间写进真模板 |

这条路径的实测结果是：写出的槽字符串与真实存档 `s481.bin` **逐字节相同**
（`83 76 83 8d 83 8d 81 5b 83 4f` = `プロローグ`）。

## 4. 还没解的（谁想接着做从这开始）

1. **中段各子结构的字段语义**：变长 DENSE 区 229–331 KB —— **字符串池已解**（§1.4：图名 + 文本行），其余子结构（图元？文本窗口布局？）仍未解
2. **常量尾 216×6B 表**的每一项代表什么（为什么全是 100）
3. **118,784 B 块**与动画/事件队列的对应关系（需要静态分析 `engine+0x65ba54` 附近的序列化）
4. 读档时这些段如何**回灌**到运行状态（`Load` 命令 40 / `SaveWrite` 命令 96 仍是兜底桩）

### 继续做的建议路线

1. 拿**同一场景、相邻时间**的两份存档做逐字节差：先把「随时间变化」的字段挑出来
   （注意：中段长度会变 264 B 量级，必须先对齐再比；实测 s481 vs s905 在 `+0x42` 之后即分叉）
2. 静态分析对照：`0x43DE90`（槽序列化）里每段的写入顺序是已知的（save-format §2.4 表 A–Q），
   把其中「长度固定」的几段与本文 §1.2 的固定段一一对上，能进一步缩小未知范围
3. 一旦某个子结构确认，先在 `src/save.c` 里加解析结构体 + 单测，再谈写回

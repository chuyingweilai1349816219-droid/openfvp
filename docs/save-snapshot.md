# 存档槽内的「引擎状态快照」

> 以下内容由 DeepSeek 生成,不一定代表作者个人意愿

本文只讲 `save/sNNN.bin` 里**缩略图之后那一大段**（526 KB ~ 599 KB）：它装的是引擎状态，
也就是「读档之后游戏怎么恢复」。文件头、字符串、缩略图、`save.bin` 的格式见
[`save-format.md`](save-format.md)；写档的 C 实现在 `src/save.c`，路径策略见 save-format §6/§7。

**重要前提**：这一段目前**只有结构被量清、字段语义未解**。所以引擎这边的策略是
「**整段不透明透传**」——读进来什么样，写回去什么样，只改已确证的那几个字段。

## 4.1 为"真读档"做的定向搜索（2026-11-25）

三个只读工具，目标是把"读档到底缺什么"缩到具体字段：

### 4.1.1 脚本位置（pc）候选：`tail+0x3BB1`

`scripts/find-save-pc.py` 的思路：存档时脚本通常停在**等玩家输入**的命令上
（`InputGetDown/State/Event...`，命令 id 27..36 的 `syscall`）。把这些 syscall 的
指令地址收集起来（iroseka 共 **692** 个），在槽尾里逐字节搜 u32：

| 槽 | 找到的候选 |
|---|---|
| s481 / s800 / s901 / s905 / s906 | **+0x003BB1 → `0x05AB0E`（`syscall 29` = InputGetCursX）** |
| s485（额外一处） | +0x0031FC → `0x03AB18`（`syscall 34` = InputGetState） |

6 个槽在同一偏移出现同一值，说明它是**结构化字段**而不是巧合；值本身是合法指令地址。
注意到 `0x3BB1` 附近是**成对的 `{u32 value, u32 type}` 记录**（type 常见 0/2/3/4/8），
像一张 Variant 数组（`0x5AB0E` 那一条 type=2 即 int）。

**限定表述**：这是"存档里的脚本位置候选"，还不能证明它就是主线程 pc
（可能是某个协程/动画线程的轮询点）。要确认需要结合"读档后从该地址继续执行"的实测。

### 4.1.2 没有 4 字节步长的 pc 数组

`scripts/find-save-contexts.py` 搜"连续多个 u32 都是合法指令地址"的区域：槽尾里
**没有** ≥8 条的此类游程（找到的都是 `0x200002`/`0x00000f` 这类小整数被误判成指令
地址）。结论：**存档里的上下文表不是"每线程一个 4 字节 pc"的裸数组**，要么指针化了，
要么字段更宽（例如 4.1.1 里那种 `{value,type}` 成对结构）。

### 4.1.3 槽尾开头那张 1471×8 表（2026-11-26 修正：原先判为"没有"）

`scripts/find-save-variants.py` 按 `{u32 value, u32 type}`（type ≤ 8）扫游程：

| 观察 | 结果 |
|---|---|
| 最长游程（允许 type=0） | 11,245–11,265 条 —— 与 §2.4.1 的 **86 KB 零区**完全吻合，是填充 |
| 最长游程（跳过 type=0） | 63–65 条 @ `+0x2904`/`+0x2914`，type 直方图 **2:31~32、6:32** |

也就是说：槽尾里最像 Variant 表的东西是**一小段"32 组 (int,float) 成对"的记录**，
**原先的结论是"没有这张表"，2026-11-26 被实测推翻**：槽尾开头确实是
**1471 条 × 8 字节**的 Variant 形状记录（`{u8 type, 3B pad, u32 value}`，
type 只出现 0/1/2/4/5/6），正好 0x2DF8 字节；把它算进去之后，字符串池标签就
落在 `0x16610 + 0x2DF8 = 0x19408`（6 份存档全中，`tests/verify_exe_save_serialize.py`
与 `tests/test_savetail.c` 钉住）。**仍不确定**的是：这张表与 `save.bin` 的
全局变量表是不是同一张（值不同、`save.bin` 侧布局尚未按同格式对上），
所以先记"槽尾里的 1471×8 Variant 形状表"，不冒充已解。

**对实现的意义**：`Load` 需要的"脚本位置 + 全局变量"两块，目前一块有候选（4.1.1）、
一块倾向于"不在这份文件里"（4.1.3）。下一步应当先验证 4.1.1 的候选（从这个地址继续
执行看会发生什么），再决定 Load 的可行范围。

### 4.1.4 从候选 pc 直接起跑：不行（实测）

为了验证 4.1.1 的候选，给 `fvm` 加了研究用的 `--pc N`（从指定地址起跑，不经过
`main_start`；`src/vm.c: fvp_vm_start_at()`）。实测 iroseka：

| 起点 | 结果 |
|---|---|
| `0x22F48`（= iroseka 真正的 `main_start`，对照组） | **20,000 步**跑满，线程存活 |
| `0x05AB0E`（候选，`syscall 29`） | **85 步**后线程结束（`ret` 弹空栈） |
| `0x03AB18`（候选，`syscall 34`） | **2,147 步**后线程结束 |
| `0x05AB0E` + `--savebin save.bin`（先灌全局变量） | 仍然 **85 步** |

结论：**光有 pc 不够**——候选地址落在某个函数体里，恢复它需要**保存下来的调用栈/帧**
（以及栈上的局部变量）。所以"读档"必须还原 context（pc + 栈 + 帧），而我们前面
（4.1.2）已经证明槽尾里没有"每线程 4 字节 pc"的裸数组，说明 context 的存储方式
要么指针化、要么字段更宽。

**方法学意义**：`--pc` 这个钩子把"能不能只跳 pc"从猜测变成了可复现的实测（上表），
后续无论从哪条路找到 context，都可以用它验证"恢复后能否继续执行"。

### 4.1.5 在 32×0xB28 协程上下文块里找 pc：过滤器太弱（负结果）

按 §2.4.4 的布局，槽尾**开头**就是 32 个协程上下文（每块 0xB28 = 2,856 B，合计
91,648 B）。`scripts/find-save-contexts2.py` 在每个块里找"值是合法指令地址"的 u32：

| 槽 | 上下文块内的"指令地址"命中数 |
|---|---:|
| s481 / s800 / s901 / s905 / s906 | 156–246 |
| s485 | 444 |

命中太多，而且绝大多数是 `0x000102`、`0x010000`、`0x1d0001` 这种**小整数恰好也是
早期指令地址**（iroseka 的前几个 opcode 编码就是 0x000100/0x000102 这类），属假阳性。
跨槽看"同一 (ctx, offset) 在多槽出现"的候选也只有零星几处（如 ctx4 +0x5CC 两个槽
同为 0x058DFF），**无法据此确认 pc 字段**。

**结论**：靠"值域过滤"在上下文块里认 pc 行不通，必须按结构体字段偏移来读——
也就是把 `0x445540`（读上下文）/`0x43F0C7`（槽反序列化）这两个函数里
"上下文的哪个偏移对应 pc / sp / 栈指针"逐一写出来。这是明确的下一步（需要静态分析
这两个函数，工作量 1–2 轮）。

**同时确认的正面信息**：槽尾前 91,648 B 的稀疏性（只有活动协程非零、其余 31 块
接近全零）与 §2.4.4 的"32 个协程上下文"布局**一致**，说明该布局表是可信的。

## 4.2 静态分析确认：序列化的协程上下文里**没有 pc / 栈**

上一轮的负结果（值域过滤找不到 pc）这轮有了确定性解释：静态分析
`0x445640`（写上下文，供 `0x43DE90` 调用）与 `0x445540`（读回，供槽反序列化调用），
一个协程上下文的序列化布局是**固定的 0xB1D = 2,845 字节**：

| # | 字段 | 引擎侧偏移 | 长度 |
|---|---|---:|---:|
| 1 | 文本缓冲 | `ctx+0x008` | **0x800** |
| 2 | u32 | `ctx+0x814` | 4 |
| 3 | u32 | `ctx+0x818` | 4 |
| 4 | u32 | `ctx+0x808` | 4 |
| 5 | u32 | `ctx+0x80C` | 4 |
| 6 | u8 | `ctx+0x810` | 1 |
| 7 | u32 | `ctx+0x81C` | 4 |
| 8 | u32 | `ctx+0x820` | 4 |
| 9 | u32 | `ctx+0x824` | 4 |
| 10 | 字节块 | **`ctx+0x828`** 起 | 0x100 |
| 11 | 字节块 | **`ctx+0x928`** 起 | 0x200 |

合计 2048+4+4+4+4+1+4+4+4+256+512 = **2,845 = 0xB1D**，与 docs 里"每窗口 0xB1D"的
推定**完全一致**。**清单里没有任何 pc、sp、调用栈或帧**。

**流内偏移 vs 内存偏移（2026-11-25 复核）**：上表的"引擎侧偏移"是**内存**里的来源
（`lea 0x828(%edi)` / `add $0x928,%edi`），而在**序列化流**里这两块分别从 `+0x81D`、
`+0x91D` 开始。写侧 0x445640 的全部写出量是
`0x800 + 8 + 4 + 4 + 1 + 12 + 0x100 + 0x200 = 2,845 = 0xB1D`，
与"每上下文 0xB1D"一致；内存结构则是 0xB28（多出的 11 字节未序列化）。
`0x800` 之后的字段在流里的位置依次是 `+0x800/+0x804/+0x808/+0x80C/+0x810(1B)/+0x811/+0x815/+0x819`。

**记录长度由调用循环定死（2026-11-25 复核）**：槽序列化器 `0x43DE90` 里的循环是

```asm
43e1cb: lea   0x68dfc0(%esi),%edi   ; ctx[0]
43e1d1: mov   $0x20,%ebx            ; 32 个
43e1d6: push  %esi
43e1d7: mov   %edi,%ecx
43e1d9: call  0x445640              ; 写一个上下文（0xB1D 字节）
43e1de: add   $0xb28,%edi           ; 内存里下一个（0xB28）
43e1e4: sub   $0x1,%ebx
43e1e7: jne   0x43e1d6
```

读回侧（`0x43F110`）是同一形状的 32 次循环。所以：**每个上下文在流里就是 0xB1D，
32 个连续 = 91,040 字节，没有额外头**；`0xB28` 只是内存结构大小。步长问题到此确定。

**记录大小用指令计数复核（2026-11-25）**：把 `0x445640` 里所有推进游标的指令加起来
——`add $0x800`、`add $0x8`、5 次 `add %ebx`（ebx=4，共 20 B）、`inc`（1 B）、
`add $0x100`、`add $0x200` —— 合计 **2,845 = 0xB1D**，与字段清单吻合。

**"32 个连续上下文"已用密度证据确认**（上一轮"槽尾开头不是连续上下文"的说法**撤回**）：

| 槽 | 上下文区（0..91,040）非零字节 | 分布 |
|---|---:|---|
| s481 | 1,769 | ctx 0–7 有数据（9–667 B），ctx 8–31 几乎全零 |
| s485 | 2,080 | 同上 |
| s800 | 1,674 | 同上 |
| s901 | 1,068 | 同上 |
| s905 | 2,193 | 同上 |

也就是 32 个上下文里**只有前 8 个是活的**，其余 24 个接近全零——这正是"32 个协程
上下文"应有的样子。之前把 ctx1 `+0x800` 起的周期 8 字节内容当成"不是上下文"，是把
记录内 `+0x81D` 的 **0x100 字节块（32×8B 的小表）** 误读了。

**仍然存疑（下一步）**：把 7 个 u32 按上面算出的偏移读出来，部分值呈"字节平移"的
样子（如 `0x0A000000`），说明**记录内部字段偏移还差最后一次核对**（可能是 u16 对，
或某次 4 字节写入跨了两个字段）。工具 `scripts/save-context-map.py` 会把每个上下文
的字段值打出来，便于对照。

把实际分段对齐出来，再逐段与 `0x43DE90` 的写入顺序匹配；这一步不需要再猜字段。


**这意味着什么（重要）**：

1. 存档**不是"执行状态快照"**——没有 pc 就无法"从断点继续执行"。这也解释了为什么
   前两轮找不到 pc / pc 数组：**它本来就不存在**。
2. 所以原版的读档只能是**场景/行号式的重放**：恢复全局变量、文本、flag 等状态 → 让
   脚本从某个**场景入口**重新开始 → 快进跳过已读内容，直到存档记录的那一行。多数
   VN 引擎（包括 BGI）都是这个套路。
3 因此 `Load(40)` 的正确目标不是"恢复 pc"，而是：**(a) 找到存档里的"场景 id / 行号"，
   (b) 实现"快进到该行"的重放**。候选位置：上下文里的 `ctx+0x814/0x818`（成对的
   type/value，像"语句返回槽"）、或 `SaveData` 区（kind=2 的已读标记）、或全局变量里
   的场景计数器。

**下一步（具体）**：在"同一场景、不同行"的两份存档之间做**逐字段差分**，重点看
`ctx+0x814/0x818/0x808/0x80C/0x81C/0x820/0x824` 这 7 个 u32 与 §2.4.4 里
"字符串句柄表 / 动态字符串表"两类区域——行号信息必然随进度变化，而它不会在
上下文之外单独存在。

## 4.3 用地标把槽尾分段画出来（2026-11-25）

工具：`python scripts/save-tail-map.py <game_dir>`（只读）。它不用猜字段，只用四个
已经被独立证实的地标：

| 地标 | 偏移 | 依据 |
|---|---|---|
| 32 个协程上下文 | `0x00000 .. 0x163A0`（32 × 0xB1D） | 写/读两侧都是 32 次循环（§4.2） |
| 字符串池 | `0x19408` | u32 tag `0x20` + u32 计数 + 长度前缀字符串 |
| 收尾常量块 | 末尾 1,438 B | 6 个槽逐字节相同，末 2 字节 `01 01` |
| 正文区 | 池之后到常量块之前 | 剩下的就是随存档变化的部分 |

实测（iroseka 的 6 个槽）：

| 槽 | 上下文的非零字节 | `0x163A0..0x19408` 非零 | 池里的字符串 | 正文区非零 |
|---|---:|---:|---|---:|
| s481 | 1,769 | **0** | 1 条（台词） | 71,925 |
| s485 | 2,080 | **0** | 1 条 | 93,138 |
| s800 | 1,674 | **0** | 0 条 | 93,032 |
| s901 | 1,068 | **0** | 0 条 | 59,771 |
| s905 | 2,193 | **0** | 2 条（图名 `BG063_000b` + 1 条） | 72,280 |
| s906 | 1,276 | **0** | 0 条 | 61,789 |

三个可以直接用的结论：

1. **`0x163A0..0x19408` 在 6 个槽里全零** —— 这里本该是"字符串句柄表 + 两个字节块
   + 表 + 块"（§2.4.4 的 5–7 段）。本作这个状态下它们是空的，所以**固定 91,040 B 之后
   直接跳到字符串池**，分段顺序不用再猜。
2. **收尾常量块 6 个槽完全一致**（sha256 前缀 `7bab52ab6ea15d15`，末 2 字节 `0101`）——
   写回存档时可以原样拷贝。
3. **字符串池里的条数会变**（0/1/2 条），说明它是"动态字符串表"而不是固定字段：
   `s905` 里有图名 `BG063_000b`，`s481` 只有台词，其余槽是空的。这解释了为什么
   早先"图名 + 台词"的解析在个别槽上看起来不一致。

**对"场景/行号重放"的意义**：正文区（池之后那 400–500 KB）才是随进度变的内容；
把两份"同场景不同行"的存档在这个区间做逐段差分，就能把"行号/场景 id"圈出来——
这是读档路线里现在唯一缺的一块。

## 4.4 正文区朴素差分：**不足以**定位行号（负结果，2026-11-25）

工具：`python scripts/diff-save-body.py <game_dir> <slotA> <slotB>`。
它先跳过**变长**的字符串池（tag `0x20` + 计数 + 长度前缀字符串），再逐字节比较
两份存档池之后的正文区，按"差异游程长度"排序，短游程优先（孤立标量字段通常很短）。

实测 s481（台词 `　……。`）对 s905（台词 `　谁这样说道。`）：

```
body A=421252  body B=421512  (compared 421252, pool skipped)
differing runs: 32,397
```

**结论（负结果）**：从一开始就逐字节分叉，差异游程多达 3.2 万段——这两个槽虽然都在
序章，但**场景/演出状态并不同**（一份在逐字显示、另一份已停住）。朴素字节差分会被
大量非标量差异淹没，**圈不出"行号"**。

**正确方法（下一步）**：做**受控存档对**——用同一个存档读档、只前进一行的最小操作，
再存到另一个槽，把这两份存档差分。这样"只变化的东西"就只剩行号/当前文本指针等少数
标量。原版游戏可以在本机运行（用户已授权），但需要 UI 自动化：读档 → 前进一行 → 存档；
这是下一步要做的实验，脚本化之后可以作为读档路线的决定性证据。

在此之前，`Load(40)` 的"场景/行号重放"仍停在方案阶段；能做的部分（画面 + 台词还原）
已经以"部分恢复"视图落地（见 `docs/title-menu.md` §4.14）。

## 4.5 受控对照：**同一条台词**两份存档的"噪声集"（2026-11-25）

原版引擎自己写出的存档里有一对近乎相同的样本：`s483.bin` / `s484.bin`
（同尺寸 592,516 B、同台词 `　……。`、相隔约 3 分钟）。这就是天然的"受控对照"：

| 比较项 | 结果 |
|---|---|
| 32 个协程上下文 | **完全一致**（`diff-save-contexts.py`：0 个字段不同） |
| 正文区（池后到常量尾） | **55 段差异**，每段 1–2 字节 |

这 55 段的成分（`--classify` 分类，见下）**不是清一色的 ±1**，需要更准确的描述：

| 类别 | 段数 | 特征 |
|---|---:|---|
| 周期性记录数组 | 37 | 落在 17 / 18 / 22 字节等距链里（`+0x3779x`、`+0x58Bxx`、`+0x40BFx`），与早先发现的"动画/事件队列"一致 |
| 小计数器跳动 | 13 | 单/双字节，幅度 ≤ 8（如 `907 → 906`、`831 → 829`） |
| 孤立"其它" | 5 | 6 字节，如 `+0x1631` 的 `3425 → 7e04`、`+0x040BFA` 的 `37 → 45` |

> **更正**：上一版文档写成"55 段全部 ±1/±2/±4"是不准确的——有几段幅度到 +130；正确的
> 说法是"**它们集中在动画/计时器记录里**"，所以判据应当是**偏移是否落在等距链上**，
> 而不是"差值大小"。

**三个结论**：

1. **脚本级状态稳定**：同一台词的两份存档，协程上下文一模一样 → 上下文区装的是脚本
   状态，不是画面/动画状态；
2. **正文区混着计时器噪声**：任何"找行号"的差分都必须先过滤这类 delta ≤ 4、长度 ≤ 2
   的游程，否则会被淹没（`scripts/diff-save-body.py --ignore-small` 就是干这个的）；
3. **行号在哪**：由于上下文不变、正文区只有计时器变化，**行号如果存在，应当是一个
   "跨台词才变"的稳定字段**——下一份受控实验必须是"同一场景、前进一行"的存档对。
   现有 6 个槽里没有这样的样本（两两差异 ≥ 9.5 万字节），所以这条路要么做 UI 自动化
   让原版引擎产出该样本，要么等官方存档。


### 4.5.1 分类工具与"前进一行"实验的现状（2026-11-25）

`python scripts/diff-save-body.py <game> <A> <B> --classify` 会把差异分成三类
（periodic / small-counter / other）并打印明细，**不做自动判定**——判定"是不是同一
条台词"需要已知真值的样本对，否则会变成自欺。

实测两组：

| 样本对 | periodic | small | other |
|---|---:|---:|---:|
| `s483` vs `s484`（同台词） | 37 | 13 | **5（6 字节）** |
| `s481` vs `s905`（不同台词） | 多 | 多 | 多，且含 `a1a1a1ada1ada1a3`（GBK 文本字节） |

**"前进一行"的受控实验暂时没做成**，记录失败过程避免重复踩坑：

1. `iroseka_HD.exe` 能在本机启动（窗口标题 `いろとりどりのセカイ HD Re:GENERATION`），
   但**几秒内自行退出**；用 `Start-Process` 从后台任务里拉起也一样。
2. 窗口是 D3D9 全屏，`PrintWindow` 抓帧失败（返回 0）——`window_control capture`
   拿不到画面；`Graphics.CopyFromScreen` 也只在窗口存在的那几秒内有效。
3. 因此**UI 自动化这条路需要真实桌面会话**（有人看着、手动点到存档菜单），或者用
   窗口消息注入模拟键盘（风险更高）。

结论：读档的"行号"定位仍缺**一个已知"只差一行"的存档对**。它一旦到手，用
`--classify` 过滤 periodic/small 两类，剩下的 `other` 就是候选字段。

## 4.6 `Load(40)` 的边界：哪些能恢复、哪些必须重放（2026-11-25 收尾）

工具：`python scripts/save-recoverable.py <game_dir>`（只读）逐槽打印"今天就能拿到"
的字段，并列出必须重放才能得到的东西。这张表是 `Load(40)` 这一阶段的结论交付。

### 能直接恢复（已在代码里用到）

| 字段 | 来源 | 备注 |
|---|---|---|
| 时间戳 | 头 7 字节 | 年/月/日/星期/时/分，无秒 |
| 章节名 | str0（长度前缀） | 有些槽是空串（存档时没调用 `SaveCreate(0, ..)`） |
| 当前台词 | **字符串池**（`+0x19408`）**或** str2 | **池更可靠**：实测 s485 的 str2 是空串，池里仍有台词 |
| 背景图名 | 字符串池 | 如 `BG063_000b`；只有部分槽有 |
| 缩略图 | 第 3 条字符串之后 | 200×113 BGRA，90,400 B |
| 槽尾长度 / 上下文非零字节 | 文件结构 | 用于诊断，不参与显示 |

### 必须重放（存档里**没有**这些）

| 缺口 | 依据 |
|---|---|
| 脚本位置（pc） | §4.2：序列化的上下文里没有 pc/stack，字段清单里也没有 |
| 全局变量 | §4.1.3：槽尾开头有 1471×8 字节的 Variant 形状表（与 `save.bin` 的全局表是否同源未确认）；精确续玩仍需"脚本用哪个全局量选场景" |
| 其余文本窗口的内容 | 每窗口只存一份快照（0xB1D），没有完整历史 |
| 音频状态、动画/协程栈 | §4.5：同台词两份存档的差异全是动画/计时器记录 |

### 因此的能力边界（明确写死，避免夸大）

* 外壳的 Continue **能**做到：列出存档、显示缩略图、还原"那帧画面 + 那一句台词"；
* **2026-11-26 更新**：`--load-restart` 已经能"读槽 → 场景复位 → 脚本引擎从入口重启
  （保留 globals/flags）"，并把槽尾第 20 段**台词历史环**回灌进引擎
  （`src/savehist.c`，读档路径 `0x43F25A`；详见 `save-format.md` 的 step-2 小节）。
  这已经是"能继续玩"的最小闭环，但**不是**原版那种"从存档那一刻的 pc 继续"：
* 原版语义（存档里没有 pc / 栈 / 全局变量表）决定了：要精确续玩，必须靠
  **重放**（脚本从入口跑到对应全局状态）。要做真正的读档，还差"脚本用哪个全局量
  选场景"这条（§4.1.3 的负结论仍然成立）；
* 没开 `--load-restart` 时，`Load(40)` 的实现仍是"部分恢复"（`docs/title-menu.md`
  §4.14），日志与界面都明确写 `PARTIAL`，不会假装读档成功。

# 文本格式与注音

> 以下内容由 DeepSeek 生成,不一定代表作者个人意愿

`.hcb` 里的字符串是**纯文本 + 一种内联标记**，没有换行符、没有控制字符。

## 统计（日文版 55,461 条字符串）

| 项 | 数量 |
|---|---:|
| 含注音标记 | 715 |
| 含强调点标记 `[・|X]` | 224 |
| 一条里有多处注音 | 186 |
| 最长字符串 | 148 字节 |
| 含下划线 `_` | 3,418（基本是资源名，不是台词） |

控制字符：**0 个**。换行符：**0 个**。尖括号标签：**0 个**。
也就是说排版（折行、居中、缩进）全部由引擎按文本框宽度算，脚本里不管。

## 唯一的标记：`[读音|正文]`

```
[すずかぜ|涼風]に舞い、
```

渲染时是「正文」两个字加上方小字「すずかぜ」。

规则：

- 方括号内以 `|` 分成两段，**前段是上方小字（读音），后段是正文**
- 一条字符串里可以有任意多组（最长的一条有 13 组）
- 组与组之间可以紧邻：`[・|二][・|階][・|堂]…`

## 强调点：`[・|X]`

```
[・|魔][・|法][・|使][・|い]
```

读音部分是半角片假名中点 `・`。这不是注音，而是**傍点**——在每个正文汉字上方打一个点（日语排版里表示强调的「圏点」）。

渲染规则：读音为 `・` 时，不画小字，改在正文字符的上方居中画一个小实心点。

## 与排版相关的其它约定

- 正文首字符常是全角空格 `　`（U+3000），这是**首行缩进**，不是对齐填充
- 人名单独一段（层 8），正文层（层 0）里通常不再重复人名
- 层 9 是章节/地点标题，只有一两个字或短语

## 中文版的情况

汉化补丁把注音**全部去掉**了（中文没有振假名），`[・|X]` 也一并去掉，所以中文脚本里没有这类标记。
如果以后要做「保留注音的中文版」，需要重新决定：中文一般用括号夹注或不用。

## 对渲染层的要求

1. 解析 `[a|b]`：`a` 画在上方小字号，`b` 画在正文位置；`a == "・"` 时改画圈点
2. 注音会**改变行高**（上方要留出小字空间），但**不改变正文步进**——正文按 `b` 的字宽前进
3. 换行按文本框宽度计算，脚本不提供断点
4. 首字全角空格要保留，不要 trim

## 排版参数到底有没有被渲染路径用到（2026-11-25 审计）

命令 118 `TextFormat` / 125 `TextShadowDist` / 128 `TextSpace` 都只是把值写进
文本窗口结构的字段。本站的实现一直"只记录、不渲染"——现在用静态分析把"原版有没有
读回这些字段"查清了。

工具：`python scripts/audit-text-fields.py`（解析 `work/iroseka_HD.asm` 里每次
访问，按 AT&T 语法区分读/写；`work/` 是本地静态分析产物，不入库）。

| 字段 | 含义（命令侧） | **读点** | 写点 |
|---|---|---:|---:|
| `tw+0x5A8` | TextSpace x / TextFormat a | **0** | 3 |
| `tw+0x5AA` | TextSpace y / TextFormat b | **0** | 3 |
| `tw+0x5AC` | TextFormat d | **2** | 2 |
| `tw+0x5AE` | TextFormat c | **0** | 2 |
| `tw+0x5B0` | TextFormat f | **0** | 2 |
| `tw+0x5B4` | TextFormat e | **0** | 2 |
| `tw+0x596` | 阴影前置标志 | **0** | 2 |
| `tw+0x597` | TextShadowDist | **0** | 2 |
| `tw+0x5E8` | TextFormat d 的去向 | **8** | 10 |

结论：

1. **`TextSpace`（128）与 `TextShadowDist`（125）在原版里也只写不读**——渲染路径
   从不读这两个字段。所以本站"只记录、不渲染"**不是偷懒，是忠实**；之前把它们列进
   "待渲染"清单其实是错的预期。
2. `TextFormat`（118）的 a/b/c/e/f 同样只写不读；**只有 d 被读了两处**
   （`0x430e67`、`0x4337a9`），两处都是"把 d 复制到 `tw+0x5E8` 作为初值"，随后
   `tw+0x5E8` 有 8 个读点、10 个写点（含 `add %ax,0x5E8` 这种累加）——它才是有
   真实作用的字段，语义还未解（像"文本窗口的滚动/推进偏移"）。
3. 因此 ③ 这条线的正确目标是 **`tw+0x5E8`** 的语义，而不是给 space/shadow 加渲染。

### `tw+0x5E8` 是什么（2026-11-25，读点分析）

`scripts/audit-text-fields.py --context 6` 可以把每个读点前后各 N 行静态分析打出来。
目前能确认的事实：

| 读点 | 上下文里在做什么 | 推断 |
|---|---|---|
| `0x42456F` | 把 `0x5E8`、`0x5EA` 按**有符号 16 位**读进栈槽，与 `0x6600`、某结构里的字节一起送去画 | 坐标/偏移量（绘图用） |
| `0x433006` / `0x433166` / `0x433467` | `ecx = 0x5E8 + <本次字宽>`，与 `0x5DC - 窗口字段(0x1e)` 比较；超过就 `call 0x432AF0`（换行/推进），否则继续 | **文本行的水平游标（该行已用宽度）**，`0x5DC` 像窗口宽度上限 |
| `0x433029` | `eax = 0x5E8 + (宽 - 栈槽)/2`，再 `mov %ax,0x5E8` | 按字宽**累加**游标（含居中修正） |
| `0x42DCA7` | `mov 0x5E8(%edi),%ax` 后写进 `base + offset` 的缓冲（该写函数按 40 字节记录推进、带容量/回绕逻辑） | `0x5E8` 属于**会被序列化/写出的状态** |

结合"`TextFormat` 的 d（0..64）被复制进 `0x5E8` 作为初值"，最合理的解释是：

- `tw+0x5E8` = **当前行的行内偏移（文本排版游标）**，`TextFormat d` = **初始行内缩进**；
- `tw+0x5EA` = 与之成对的另一维偏移（读点里两者总是一起出现）；
- `tw+0x5DC` ≈ 文本窗口可用宽度（游标的比较上限）。

**为什么还没实现**：把 `d` 当缩进用会改变文本排版 → 会动到冻结基线（参考渲染器
参考渲染器生成的 `out/render/story_*.png` 与 `compare.py` 的 195 行文本）。按项目约束**不允许悄悄
改基线**，所以这条先停在"语义已定、实现待批准 + 需要一起重生成参考帧"。

**顺带的价值**：`0x5E8` 会被写出（读点 4 的证据），意味着它出现在存档槽的状态流里
——这对 ② 的"真读档"是有用的线索（文本游标是读档后必须恢复的状态之一）。


**可信度说明**：这是对 `iroseka_HD.exe` 一份静态分析的静态审计；理论上渲染器也可能
通过结构体拷贝间接使用这些值，但当前证据是"除 d 之外没有读点"。另：星空的记忆的
exe 还没做同样的静态分析，结论先按同一引擎族推断。

## 文本样式命令的真实字段与范围（从 exe handler 抄的，2026-11-25）

上面几节讲的是**字符串内容**的格式；这一节讲**样式命令**改的是哪些字段。
`TextFormat`(118) / `TextFunction`(119) / `TextShadowDist`(125) / `TextSkip`(127) /
`TextSpace`(128) / `TextFont`(113) 在我们的引擎里长期是桩。要让它们"操作上也一样"，
先得知道原版把每个实参写进**哪个字段、合法范围多少、越界时是保持原值还是钳位**——
这些只在 exe 的 handler 里，抓帧拿不到。

`scripts/extract-exe-text-params.py`（基线 `ref/exe-text-params.json`，门禁
`tests/verify_exe_text_params.py`，进 `run_all`）用一个小数据流把 handler 抄成结构化事实。

### 共同形态

六个命令都长这样：

```asm
cmpb $0x2,(%eax)            ; arg0 必须是 int
mov  0x4(%eax),%ecx         ; arg0 = 文本层号
cmp  $0x1f,%ecx / jg        ; 层号 0..31
mov  0x481368,%edx          ; 全局设置对象
mov  0x98(%edx,%ecx,4),%ecx ; ecx = 设置对象->文本层表[层号]（每层 4 字节）
```

也就是说：**文本层号 0..31**，每层有自己的样式对象；下面的字段偏移都相对这个对象。

### 字段表

| 命令 | 实参 → 范围 | 写入 | 宽度 |
|---|---|---|---|
| `TextFormat`(118) | arg1 -32..32 | **+0x5A8** | 2 字节 |
| | arg2 -32..32 | **+0x5AA** | 2 字节 |
| | arg3 0..64 | **+0x5AE** | 2 字节 |
| | arg4 0..64 | **+0x5AC**（同时把 +0x5E8 抬到"见过的最大值"） | 2 字节 |
| | arg5 -16..16 | **+0x5B4** | 2 字节 |
| | arg6 -16..16 | **+0x5B0** | 2 字节 |
| `TextFunction`(119) | arg1 0..1 | **+0x5A5** | 1 字节 |
| | arg2 0..2 | **+0x5A4** | 1 字节 |
| | arg3 0..2 | **+0x5A6** | 1 字节 |
| `TextSkip`(127) | arg1 0..3 | **+0x5D7** | 1 字节 |
| `TextSpace`(128) | arg1 -32..32 | **+0x5A8**（与 TextFormat arg1 同一字段） | 2 字节 |
| | arg2 -32..32 | **+0x5AA**（与 TextFormat arg2 同一字段） | 2 字节 |
| `TextShadowDist`(125) | arg1（先钳到 **0..12**） | 不直接写字段，尾调方法 `0x4248B0` 应用 | — |
| `TextFont`(113) | arg1 / arg2 下限 **-5**，上限 = **字体表长度-1**（`cmp %esi,%eax`，esi 由 `settings+0x94` 的列表长度算出） | 不直接写字段，分别调 `0x4247F0` / `0x424860` | — |
| `TextSize`(126) | arg1 12..64 / arg2 8..32 | 调 `0x424820` / `0x424870` | — |
| `TextOutSize`(120) | arg1 0..12 / arg2 0..8 | 调 `0x424850` / `0x424880` | — |
| `TextSpeed`(129) | arg1 **-1..300000** | — | — |

三条从 asm 里直接读出来的语义：

1. **越界 = 保持原值**（不是钳位）：每个字段都是"先检查范围，越界就跳过那条 `mov`"，
   只有 `TextShadowDist` 是显式钳位（`test/jge` → 0、`mov $0xc` → 12）。
2. **`TextFormat` 与 `TextSpace` 的 arg1/arg2 是同一对字段**（+0x5A8/+0x5AA）——
   前者是"一次设六项"的批量入口，后者是单独设字距。
3. **`TextFont` 的负数下限 -5** 说明 -1..-5 是合法的特例值（不是"非法输入"），
   它的上界是动态的（字体表长度-1），所以基线里记的是"下限 -5 + 上限来自寄存器比较"。

### 这一节能直接用的地方

下一轮实现这些命令时，字段偏移、宽度（1/2 字节）、范围与"越界保持原值"的规则都
不用再猜；`ref/exe-text-params.json` 是机器可读的，门禁保证它和 exe 一致。

### 渲染侧怎么用这些字段：读写点地图（2026-11-25）

上一节只回答了"样式命令写哪里"。这一轮把**所有读点/写点/读改写点**也扫出来
（`scripts/extract-exe-text-fields.py` → `ref/exe-text-fields.json` → 门禁
`tests/verify_exe_text_fields.py`），补上"谁在用"。

| 字段 | 写点 | 读点 | 说明 |
|---|---|---|---|
| +0x5A4 / +0x5A5 / +0x5A6（TextFunction） | 各 2（handler + 拷贝） | 0 | 只写不读 |
| +0x5A8 / +0x5AA（TextSpace / TextFormat 1、2） | 各 3（两个 handler + 拷贝） | **0** | 只写不读 |
| +0x5B0 / +0x5B4（TextFormat 6、5） | 各 2 | **0** | 只写不读 |
| +0x5AC（TextFormat 4） | 2 | **2**（`0x430E67`、`0x4337A9`，dword 读，顺带覆盖 +0x5AE） | 被排版例程读 |
| +0x5D7（TextSkip） | 3（handler + 排版里两处逐字符元数据 `0x432394`、`0x433A70`） | **2**（`0x42DB78`、`0x431084`）+ 4 处覆盖读（0x5D4..0x5D6 那组） | 逐字符复制 |
| +0x597（TextShadowDist 写的字节） | 2（方法 `0x4248B4` + 拷贝） | **0** | **写了没人读** |
| +0x5E8（行宽累计） | 8（含 TextFormat arg4 的"抬下限"） | 6 + 2 处 `add` 读改写（`0x4247C4`/`0x4247DA`） | 累加器 |

三条结论直接可用：

1. **TextShadowDist 的字节在 exe 里没有任何读点** —— 这就是我们"只记录、不画阴影层"
   的**结构分析依据**（不是"没实现"）。原版的阴影如果存在，也不是从这个字段读的，
   所以照它画只会得到一张"看起来像但操作上不同"的图。
2. **+0x5A8/+0x5AA/+0x5B0/+0x5B4 只写不读**：它们会被一处**结构拷贝例程**
   （`0x430E00..0x431100`）搬进排版对象，消费点在那边（字段在排版对象里换了偏移），
   所以"在样式对象上读不到"不等于"没用"——这一点写清楚，避免下一轮误判。
3. **+0x5E8 是累计行宽**：文本方法用 `add %ax,0x5e8(%ecx)` 累加，换行判断
   （`0x433006`）拿它跟 +0x5DC 比；`TextFormat` 的 arg4 在 handler 里只会把它**抬高**
   （`cmp`+`jge` 跳过写入）——我们在 `src/textattr.c` 里就按这个语义实现了
   `fmt_width_floor`（只升不降），并有单测锁住（`tests/test_textattr.c` §8）。

### 文本窗口的默认值：来自 exe 构造函数 0x430EA0（2026-11-25）

上面两节讲的是"命令怎么改样式"。还有一个更基础的问题：**没被命令改过时是什么值**。
这些默认值在 exe 的文本窗口构造函数里（`0x430EA0`，`ret $0x8`，两个参数是窗口宽高）。
`scripts/extract-exe-text-defaults.py` → `ref/exe-text-defaults.json` → 门禁
`tests/verify_exe_text_defaults.py`（进 `run_all`）。

| 字段 | 默认值 | 说明 |
|---|---|---|
| `+0x592` / `+0x594` | **16 / 12** | 默认字号（宽 16、高 12）——**我们之前写成 12×12，已按静态分析改正** |
| `+0x590` / `+0x593` | **0xFFFE / 0xFE ⇒ -2 / -2** | 默认字体号是 **-2**（"未指定"），**不是 0**（0 表示第 0 个字体） |
| `+0x5A8` / `+0x5AA` | 0 | 字距/行距 |
| `+0x5AC` / `+0x5AE` / `+0x5B0` / `+0x5B4` | 0 | TextFormat 的四个排版参数 |
| `+0x5A4` / `+0x5A5` / `+0x5A6` | 0 | TextFunction 三个开关 |
| `+0x597` | 0 | TextShadowDist |
| `+0x5E0` | 0 | TextSpeed（0 = 不等待） |
| `+0x5D4` / `+0x5D9` | 1 / 1 | 构造时的两个布尔 |

另外两条从构造函数/清空例程读出来的硬约束：

1. **尺寸上限 1024**：构造函数用 `cmp $0x400` 检查两个入参（越界走错误分支，错误信息里也打印 1024）。
2. **清空时 `+0x5E8 := +0x5AC`**：行宽累计器从"初始宽度/下限"开始，而不是从 0；同时
   `+0x5EA`、`+0x5D8`、`+0x5D6`、`+0x640` 清 0。

`src/textattr.c` 的 `fvp_textattr_reset()` 已按这张表改正（原来 12×12、字体号 0 是照
文档抄的，与 exe 不一致），门禁第 5 节会把 C 里的默认值和 exe 的常量逐项对比。
`tests/test_textattr.c` 也加了对应断言（默认 16×12、-2/-2、间距/阴影/skip 全 0）。

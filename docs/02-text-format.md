# 文本格式与注音

> 以下内容由 DeepSeek 生成,不一定代表作者个人意愿

`.hcb` 里的字符串是**纯文本 + 一种内联标记**，没有换行符、没有控制字符。

## 统计（日文版 55,461 条字符串）

| 项 | 数量 |
|---|---:|
| 含注音标记 | 715 |
| 含强调点标记 `[・|X]` | 224 |
| 一条里有多处注音 | 186 |
| 最长字符串 | 148 字节 |
| 含下划线 `_` | 3,418（基本是资源名，不是台词） |

控制字符：**0 个**。换行符：**0 个**。尖括号标签：**0 个**。
也就是说排版（折行、居中、缩进）全部由引擎按文本框宽度算，脚本里不管。

## 唯一的标记：`[读音|正文]`

```
[すずかぜ|涼風]に舞い、
```

渲染时是「正文」两个字加上方小字「すずかぜ」。

规则：

- 方括号内以 `|` 分成两段，**前段是上方小字（读音），后段是正文**
- 一条字符串里可以有任意多组（最长的一条有 13 组）
- 组与组之间可以紧邻：`[・|二][・|階][・|堂]…`

## 强调点：`[・|X]`

```
[・|魔][・|法][・|使][・|い]
```

读音部分是半角片假名中点 `・`。这不是注音，而是**傍点**——在每个正文汉字上方打一个点（日语排版里表示强调的「圏点」）。

渲染规则：读音为 `・` 时，不画小字，改在正文字符的上方居中画一个小实心点。

## 与排版相关的其它约定

- 正文首字符常是全角空格 `　`（U+3000），这是**首行缩进**，不是对齐填充
- 人名单独一段（层 8），正文层（层 0）里通常不再重复人名
- 层 9 是章节/地点标题，只有一两个字或短语

## 中文版的情况

汉化补丁把注音**全部去掉**了（中文没有振假名），`[・|X]` 也一并去掉，所以中文脚本里没有这类标记。
如果以后要做「保留注音的中文版」，需要重新决定：中文一般用括号夹注或不用。

## 对渲染层的要求

1. 解析 `[a|b]`：`a` 画在上方小字号，`b` 画在正文位置；`a == "・"` 时改画圈点
2. 注音会**改变行高**（上方要留出小字空间），但**不改变正文步进**——正文按 `b` 的字宽前进
3. 换行按文本框宽度计算，脚本不提供断点
4. 首字全角空格要保留，不要 trim

## 排版参数到底有没有被渲染路径用到（2026-11-25 审计）

命令 118 `TextFormat` / 125 `TextShadowDist` / 128 `TextSpace` 都只是把值写进
文本窗口结构的字段。本站的实现一直"只记录、不渲染"——现在用静态分析把"原版有没有
读回这些字段"查清了。

工具：`python scripts/audit-text-fields.py`（解析 `work/iroseka_HD.asm` 里每次
访问，按 AT&T 语法区分读/写；`work/` 是本地静态分析产物，不入库）。

| 字段 | 含义（命令侧） | **读点** | 写点 |
|---|---|---:|---:|
| `tw+0x5A8` | TextSpace x / TextFormat a | **0** | 3 |
| `tw+0x5AA` | TextSpace y / TextFormat b | **0** | 3 |
| `tw+0x5AC` | TextFormat d | **2** | 2 |
| `tw+0x5AE` | TextFormat c | **0** | 2 |
| `tw+0x5B0` | TextFormat f | **0** | 2 |
| `tw+0x5B4` | TextFormat e | **0** | 2 |
| `tw+0x596` | 阴影前置标志 | **0** | 2 |
| `tw+0x597` | TextShadowDist | **0** | 2 |
| `tw+0x5E8` | TextFormat d 的去向 | **8** | 10 |

结论：

1. **`TextSpace`（128）与 `TextShadowDist`（125）在原版里也只写不读**——渲染路径
   从不读这两个字段。所以本站"只记录、不渲染"**不是偷懒，是忠实**；之前把它们列进
   "待渲染"清单其实是错的预期。
2. `TextFormat`（118）的 a/b/c/e/f 同样只写不读；**只有 d 被读了两处**
   （`0x430e67`、`0x4337a9`），两处都是"把 d 复制到 `tw+0x5E8` 作为初值"，随后
   `tw+0x5E8` 有 8 个读点、10 个写点（含 `add %ax,0x5E8` 这种累加）——它才是有
   真实作用的字段，语义还未解（像"文本窗口的滚动/推进偏移"）。
3. 因此 ③ 这条线的正确目标是 **`tw+0x5E8`** 的语义，而不是给 space/shadow 加渲染。

**可信度说明**：这是对 `iroseka_HD.exe` 一份静态分析的静态审计；理论上渲染器也可能
通过结构体拷贝间接使用这些值，但当前证据是"除 d 之外没有读点"。另：星空的记忆的
exe 还没做同样的静态分析，结论先按同一引擎族推断。

### 外字渲染：已落地（2026-11-24）

`GaijiLoad('ハ', 64, 'graph/gaiji_heart68')` 的意思是：把字符「ハ」在字号 64 下替换成
graph 包里 `gaiji_heart68` 那张图。这解释了之前几个对不上的现象：

* 位图字集是"按实际用到的字"抠的，所以 56px 图集只有 5 个字形；
* 章节标题层 `tw9` 的 `TextFont(9,-2,1)` 选的那套字模，很可能就是外字图；
* 标题里那些"不该是普通字形"的符号，原版是靠外字图画的。

**已经做完的（`commit` 见 CHANGELOG）**：

1. `gfx.h` 新增外字表 API：`gfx_gaiji_add(cp, size, slot)` / `gfx_gaiji_count()`，
   最多 `GFX_MAX_GAIJI = 64` 条，同一码点重复登记即覆盖（重进场景会重新 GaijiLoad）；
2. syscall `case 21`：记录参数后，把图装进**高号图形槽**（`0x0F00` 起，最多 64 个，
   不会和脚本自己的图元/图形槽打架），再登记「码点 → 槽 + 原始字号」；
3. `gfx.c` 的 `draw_text_run` 里命中码点就用槽里的图 **按当前字号等比缩放**
   （最近邻 + alpha 混合，`blit_rgba_scaled`）画上去，并按缩放后的宽度推进笔位，
   所以排版/居中仍然对；槽里没图就退回原来的字形路径；
4. 单测 `tests/test_gaiji_render.c`（**17 项**）用假 host 造一张 8×8 纯红图，
   直接验证：没登记时字符位置**没有**纯红像素 → 登记后同一位置**出现**纯红、
   重复登记不增加条目、码点 0 / 槽号越界 / NULL 全部拒绝、空槽不画东西。

## 第三部作品的交叉验证（《樱花，萌放。（さくら、もゆ。）》，2026-11-24）

用户提供了第三部 FVP 作品，正好用来做 openbgi 那种"一部一部往上加"的兼容性验证。
实测结论（`tests/verify_multigame.py` 已经把它变成门禁）：

| 项 | 结果 |
|---|---|
| HCB 结构 | `Sakura.hcb` 5,002,852 B，`script_len` 5,000,782，`main_start` 0x36a79，966,284 条指令解码成功 |
| 内嵌命令表 | 与 iroseka / hoshimemo **逐项相同**（148 条，名字+argc+顺序全一致）→ 脚本里 syscall 立即数的含义跨作品稳定 |
| 启动流程 | 前 2,179 步正常（音频音量、各类初始化），随后进入 **脚本自带的死循环** |
| 卡死位置 | pc **0x8ef82..0x8ef9b**：`i = 0; while (i >= g[1711]) { garr[1733][i] = 0; i++ }` |
| 根因 | 该循环只有在计数器 `global 1711 >= 1` 时才会立刻退出；我们的运行到这一步时计数器是 0（`0 >= 0` 恒真）。计数器由 `0x8eef3` 初始化、由 `0x8f5d0` 递增、由这个循环自身在退出路径上清零——**说明我们在 0x8eef3 之后的某一步，状态和原版分了叉**（待解） |
| 引擎侧改进 | 新增**卡死侦测**：连续 `--stall-after N` 步没有执行任何 syscall 就判定脚本自旋并停下，`fvm` 汇总打印 `stall pc=0x... after N steps`，`--stall-exit` 让它以退出码 6 结束；外壳同样有 `--stall-after`，汇总里多一行 `stall` |
| 门禁处理 | `sakura` 标为 **KNOWN BLOCKER**：要求两次运行都以退出码 6 结束、卡死 pc 仍落在那个循环窗口内、两次输出逐字节相同。**一旦它哪天跑过去了，这条检查会失败**，提醒我们改记录 |

顺带确证的两条 VM 语义（`docs/vm-commands.md` §1.2 已补）：

* `jmpcond` 的判据是**值的类型字节 == 0**（`cmpb $0x0,(%edx)` + `jne`），不是"数值 == 0"；
  比较类 opcode 把结果写进**类型字节**（0/1），所以这套 VM 里"真假"是类型而不是数值。
* 比较运算走 **7×7 的类型对表**（`0x481450`，索引 = `a.type*7 + b.type`，启动时由
  `0x446580` 循环填），默认项返回 0（"相等"），只有 16/17/23/24/32/33/39/40 这些
  类型对有专用比较函数。这解释了 `ge/lt` 在异类型上的行为，也是上面的死循环判据来源。

### 值模型的第二步：类型即布尔（**第一步已落地，第二步待做**）

**已落地（2026-11-24）**：`FvpType` 增加 `FVP_NULL`（≡ 原版 `Variant.type = 0`），
`pushfalse`(0x09) 压它；`ControlMask` / `CursorShow` / `LipAnim` / `LipSync` 的
null 分支因此第一次可达。为保住 900k 步冻结基准，`FVP_NULL` 在

`tests/test_nullvalue.c` 66 项守着）。**注意：这一步只是把类型引进来了，没有改
比较与跳转的判据**，所以原版那套"真假是类型"的语义还没实现。

**待做的第二步（会动冻结基准，必须先停下来重新审视）**：

* `jmpcond` 的判据是**值的类型字节 == 0**（`cmpb $0x0,(%edx)` + `jne`），不是"数值 == 0"；
* 比较类 opcode 把结果写进**类型字节**（0/1 = 原版 false/true），所以这套 VM 里
  "真假"是类型而不是数值；
* 比较运算走 **7×7 的类型对表**（三张：`0x481388`/`0x481450`/`0x481518`，
  索引 = `a.type*7 + b.type`，启动时由 `0x446580` 循环填）。**2026-11-24 已读全**：
  默认项 `0x444f50` 返回 0（= 比较结果假，不是"相等"），只有 16/17/23/24/32/33/39/40
  这些类型对有专用比较器，表 C 另有 11 项返回 1，详见 `docs/vm-commands.md` §1.2；
* **未赋值的 global 在原版读出来是 null（type 0）**，在本站是 int 0（type 2）。

为什么这三件事必须一起做：脚本里 `pushint8 0; jmpcond` 这种"编译期常量 0"的条件，
在**原版**里 type 2 ≠ 0 → **不跳**（条件为真），在本站是"0 为假" → **跳**。这正是
README 里"协程建起来就退出"那条结论的隐患：它可能不是脚本的行为，而是我们语义的产物。
同理，sakura 的 `0x8ef82` 死循环只在 `g[1711] == 0` 时爆炸，而 `0x8f415`（"压入一条记录"）
在本站一次都没被调用过——上游分支很可能就是被这套"数值真假 vs 类型真假"翻转的。

**第二步的第一次 A/B 已经跑了（2026-11-24，结论是"不能只改布尔表示"）**：

- 加了实验开关 `--bool-type`（默认关）：打开后比较/逻辑/位测试类 opcode 为假压
  `FVP_NULL`、为真压 int 1，`jmpcond` 只在 `type == FVP_NULL` 时跳（逐字照
  handler 0x445a30）。
- 结果：**iroseka 900k 步的文本输出从 195 行掉到 0 行**。第一个分歧点在
  **step 12,645 / pc 0x05aaf5**——正是 `initstack[0,4]; pushint8[0]; copystack[3];
  pushint8[0]; jmpcond` 那一类"常量 0"条件：数值模型跳去 `ret`（函数什么都不做），
  类型模型不跳、继续执行函数体。
- 也就是说：**只把布尔表示换成类型是不够的**。函数体执行起来之后流程立刻走偏
  （`unknown cmds` 从 `80×7975` 变成 `73×286` 这种完全不同的分布），说明还有别的
  语义没对上——最可能是下面那三件里剩下的两件（7×7 比较表、未赋值 global = null）。
- 因此 `--bool-type` 保留为**实验开关，默认关闭**，冻结基线不受影响（`compare.py`
  仍逐字节一致）。下一步应该是先按 7×7 表实现异类型比较、把未赋值 global 变成
  `FVP_NULL`，再打开 `--bool-type` 复测；单独改布尔表示这条路已经被实测否决。

静态统计（`work/jmpcond_pred.py`，用 ref/fvm_ref.py 的官方解码器）给出这三部作品里
`jmpcond` 的条件来自哪里，可以据此判断影响面：

| 作品 | jmpcond | 比较类前驱 | logand/logor | `test` | `pushint8` |
|---|---:|---:|---:|---:|---:|
| iroseka | 8,141 | 84.9% | 13.2% | 1.2% | 0.7%（17 个 0 / 44 个 1） |
| hoshimemo | 9,357 | 81.2% | 16.8% | 1.0% | 1.0%（51 个 0 / 38 个 1） |
| sakura | 9,106 | 83.0% | 14.8% | 1.0% | 1.2%（65 个 0 / 44 个 1） |

`pushint8 1; jmpcond` 在两种语义下都不跳（一致）；真正分叉的是
`pushint8 0; jmpcond` 这一类（iroseka 17 处、hoshimemo 51 处、sakura 65 处）。

**三次 A/B 的经过与结论（2026-11-24）**：

1. **第一次**（只把布尔表示换成类型）：iroseka 900k 步 195 行 -> **0 行**，第一个分歧点
   step 12,645 / pc `0x05aaf5`（`initstack; pushint8 0; jmpcond <ret>` 这类函数守卫：
   数值模型跳去 ret，类型模型继续执行函数体）。
2. **第二次**（再把 7x7 表与“未赋值 global = null”加进开关）：仍是 **0 行**，
   `unknown cmds` 变成 `79x7725, 76x7572`。
3. **第三次**（按分发表把 0x25/0x27 的真实语义也实现进开关）：仍是 **0 行**，但表现变了
   ——这次是 **thread 0 一直跑**，`PrimGroupIn(73)` 被调用 **31,154 次**（默认模型只有
   2,399 次）。也就是说忠实模型不是“跑飞”，而是**卡在粒子 / 动画组循环里**。

**统一结论**：值模型（布尔类型 / 比较表 / 未赋值 global / 0x25-0x27 真实映射）做得再忠实，
只要脚本流程依赖我们**还没建模的东西**（这个循环、或 TitleMenu 之类引擎侧状态），文本就出不来；
反过来说，现在的 195 行是“在我们这套（部分错误的）语义下恰好连贯”的结果。

下一步（按性价比）：
1. 查 `PrimGroupIn(73)` 那个循环在等什么（31,154 次调用对应的动画收尾判断），它很可能是
   下一个真正的缺口；
2. 确认 `pushint8 0; jmpcond` 这类“常量 0”条件在原版里到底是什么构造；
3. **裁决语义矛盾只能靠原版实机判据**（`docs/original-verification.md`，按用户指示暂停中，
   但它是这条线的真正 unblocker）。

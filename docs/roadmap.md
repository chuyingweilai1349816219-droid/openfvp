## 第三部作品的交叉验证（《樱花，萌放。（さくら、もゆ。）》，2026-11-24）

用户提供了第三部 FVP 作品，正好用来做 openbgi 那种"一部一部往上加"的兼容性验证。
实测结论（`tests/verify_multigame.py` 已经把它变成门禁）：

| 项 | 结果 |
|---|---|
| HCB 结构 | `Sakura.hcb` 5,002,852 B，`script_len` 5,000,782，`main_start` 0x36a79，966,284 条指令解码成功 |
| 内嵌命令表 | 与 iroseka / hoshimemo **逐项相同**（148 条，名字+argc+顺序全一致）→ 脚本里 syscall 立即数的含义跨作品稳定 |
| 启动流程 | 前 2,179 步正常（音频音量、各类初始化），随后进入 **脚本自带的死循环** |
| 卡死位置 | pc **0x8ef82..0x8ef9b**：`i = 0; while (i >= g[1711]) { garr[1733][i] = 0; i++ }` |
| 根因 | 该循环只有在计数器 `global 1711 >= 1` 时才会立刻退出；我们的运行到这一步时计数器是 0（`0 >= 0` 恒真）。计数器由 `0x8eef3` 初始化、由 `0x8f5d0` 递增、由这个循环自身在退出路径上清零——**说明我们在 0x8eef3 之后的某一步，状态和原版分了叉**（待解） |
| 引擎侧改进 | 新增**卡死侦测**：连续 `--stall-after N` 步没有执行任何 syscall 就判定脚本自旋并停下，`fvm` 汇总打印 `stall pc=0x... after N steps`，`--stall-exit` 让它以退出码 6 结束；外壳同样有 `--stall-after`，汇总里多一行 `stall` |
| 门禁处理 | `sakura` 标为 **KNOWN BLOCKER**：要求两次运行都以退出码 6 结束、卡死 pc 仍落在那个循环窗口内、两次输出逐字节相同。**一旦它哪天跑过去了，这条检查会失败**，提醒我们改记录 |

顺带确证的两条 VM 语义（`docs/vm-commands.md` §1.2 已补）：

* `jmpcond` 的判据是**值的类型字节 == 0**（`cmpb $0x0,(%edx)` + `jne`），不是"数值 == 0"；
  比较类 opcode 把结果写进**类型字节**（0/1），所以这套 VM 里"真假"是类型而不是数值。
* 比较运算走 **7×7 的类型对表**（`0x481450`，索引 = `a.type*7 + b.type`，启动时由
  `0x446580` 循环填），默认项返回 0（"相等"），只有 16/17/23/24/32/33/39/40 这些
  类型对有专用比较函数。这解释了 `ge/lt` 在异类型上的行为，也是上面的死循环判据来源。

### 下一个要验的假设：值模型把 null 和 int 0 混在一起

`0x8ef82` 那个死循环只在 `g[1711] == 0` 时爆炸，而 g[1711] 由 `0x8f415`（22 个
局部变量、约 100 处调用点的"压入一条记录"函数）递增、由清理函数 `0x8ef6c` 自己
清零。实测我们的运行里 **`0x8f415` 一次都没被调用过**（400k 步 trace 里 pc 没有
出现过），所以第二次调清理函数时计数器是 0。

而 `0x8f415` 没被调用的最可能原因，是上游某个分支条件和原版翻了：
原版的值类型是 **0 = null / 1 = true / 2 = int / 4,5 = 字符串**，未赋值的 global
读出来是 **null**；本站的 `FvpValue` 是 **`FVP_INT = 0`**，未赋值的 global 读出来
是 **int 0**。两者在 `ge/lt/eq` 上会给出不同结果（原版异类型比较走 7×7 表的默认项
"相等"，本站按数值比较），足以让脚本走另一条分支。

验证办法（下一轮）：给 `FvpValue` 引入 `FVP_NIL`、把"未赋值 global"变成 nil、
按 7×7 表重写比较语义，然后看 ① `iroseka` 的 195 行冻结基准是否仍然逐字节一致
（**如果变了，说明基准本身依赖了错误语义，必须停下来重新审视**）② `Sakura` 的
`0x8f415` 是否开始被调用、卡死是否消失。

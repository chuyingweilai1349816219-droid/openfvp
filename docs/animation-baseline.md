# 动画 / 时间模型的验收基线设计（0.4 前置）

> 以下内容由 DeepSeek 生成,不一定代表作者个人意愿

0.4 的主题是**动画（`Motion*`）与时间模型**。这件事会动到现有的验收入口，所以先把
「什么会失效、用什么替代、怎么防止假绿」写清楚，再动代码。

现状：`src/motion.c` 只有**补间数学**（时间轴 + 线性插值 + 回收），**没有接 gfx、没有接 syscall**，
所以现在所有验收数字仍然成立。

---

## 1. 会失效的东西

| 现有验收 | 为什么会被影响 |
|---|---|
| `verify_gfx.ps1` 的 528,000 步参考帧（像素差 0.0141% / PSNR 49.94） | 参考帧是 Python 原型渲染的**静态**一帧；动画一旦生效，立绘会在同一时刻处于不同位置/透明度，像素必然不同 |
| `verify_render_vm.ps1` 的「端到端帧与参考一致」 | 同上 |
| `compare.py` 的逐字节文本（6,496 B / `7F9837FF…`） | 如果时间模型改变了文本推进节奏，文本行数与内容都可能变 |

**注意 `compare.py` 是硬门禁**：它比对的是「跑 N 步后打印出来的文本行」，只有文本流程变了才会失败。
动画本身不改文本，所以只要 `Motion*` 的 `*Test` 语义（等待/完成判定）没接进线程调度，
文本基线就应该保持不动 —— 这一点必须每轮用 `compare.py --run` 验证。

## 2. 新基线（分层，避免一次性重做全部数字）

### 2.1 文本：保留 `compare.py`，并加「动画关闭」开关

- 新增 `--no-motion`（或 VM 侧 `motion_enabled = 0`）：此时 `Motion*` 全部按**立即完成**处理，
  与当前行为完全一致
- `compare.py` 与 `run_all.py` 一律在 `--no-motion` 下跑 → **6,496 B 基线继续有效**，
  且能证明「动画代码没有偷偷影响文本流程」
- CI 里再加一条 `--motion` 的 `run_all` 冒烟（只要求不崩、文本行数在合理范围），不比对逐字节

### 2.2 渲染：从「像素对参考帧」改为「三组自洽断言」

参考帧只有一张、且没有动画，无法用作动画正确性基准。改用：

| 断言 | 判据 |
|---|---|
| **t=0 不动** | 动画表非空但时间轴为 0 时，渲染帧必须与「无动画」帧**逐像素相同** |
| **t=END 到位** | 时间轴推进到 `dur` 之后，图元的位置/透明度/缩放必须**精确等于目标值**（整数，不比对像素） |
| **单调 / 有界** | 线性补间在 0..dur 之间每帧的值单调变化，且始终落在 `[from, to]` 区间内 |

以上三条都能在 C 侧用 `gfx` 的图元字段断言（`prim+0x14/0x16/0x07/0x26/0x28` 的镜像 API），
不需要新参考图，也不依赖原版 exe。

### 2.3 `mode` 缓动曲线：已从静态分析确认（2026-11-24）

补间条目（每槽 28 字节，`engine+0x65BA54` 等 6 个管理器共用同一套代码）里
`+4` 是 mode 字节、`+0x14` 是已过时间、`+0x18` 是时长；推进函数 **0x422C10** 里：

```
422c8d: movsbl 0x4(%eax),%eax        ; mode
422c9b: dec    %eax                  ; mode - 1
422ca6: cmp    $0x4,%eax
422ca9: ja     0x423112              ; 0 或 >5 → 特殊分支（直接给终值）
422caf: jmp    *0x423154(,%eax,4)    ; 跳表：mode-1 → 5 个例程
423154+0  → 0x422CB6   mode 1
423154+4  → 0x422D25   mode 2
423154+8  → 0x422DAF   mode 3
423154+12 → 0x422E37   mode 4
423154+16 → 0x422F8F   mode 5
```

5 个例程都用 64 位整数乘除（`__allmul` **0x447DD0** / `__alldiv` **0x447D20**，
除不尽向零截断），把 `dx = p3 - p1`、`dy = p4 - p2`（i16）按曲线换算后加到起点：

| mode | 曲线 | 依据 |
|---:|---|---|
| 1 | 线性 `dx·t/d` | 0x422CB6 只有「一次 allmul + 一次 alldiv」 |
| 2 | 缓入 `dx·t²/d²` | 0x422D25 是 allmul(t,t) 再除以 d 两次 |
| 3 | 缓出 `dx − dx·(d−t)²/d²` | 0x422DAF 先算 `e = d − t` 的平方，再从 dx 里减 |
| 4 | 缓入-缓出：以 `d/2` 分段，前段 `(dx/2)·(t/(d/2))²`，后段 `dx − (dx/2)·((d−t)/(d/2))²` | 0x422E37 先算 `d/2`、`dx/2`，`cmp` 后分两半 |
| 5 | 先缓出后缓入：前段 `(dx/2)·(1−((d/2−t)/(d/2))²)`，后段对称 | 0x422F8F 同一分段结构、首段用 `d/2 − t` |

本站实现：`fvp_motion_ease(mode, p)`（`src/motion.c`）把线性进度 `p` 映射成系数：
`mode 2 → p²`、`mode 3 → 1−(1−p)²`、`mode 4 → p≤½ ? 2p² : 1−2(1−p)²`、
`mode 5 → p≤½ ? 2p−2p² : ½+2(p−½)²`；`mode 1`/`0`/表外值仍是线性。
`fvp_motion_value()` 用这个系数做插值，所以位置/透明度/缩放三条 Motion* 都吃同一套曲线。

**证据级别（照实写）**：

- mode **1/2/3**：例程结构直接对应上表公式，判定为**已确证**
- mode **4/5**：分段点（`d/2`）、首段公式、端点与中点的取值都能从指令确证；
  **第二半段**因为同一段代码被 x/y 共用、寄存器别名多，只做到"按同一分段结构对称推导"，
  没有逐条指令对到最后一句 —— 已用「单调不减 / 端点精确 / 中点 0.5」三条性质做门禁
  （`tests/test_motion.c` 第 8 组 38 项），但**不声称与原版逐位一致**
- 原版是 i16 + 整数除法（向零截断），本站是 double 插值：中间帧最多差 1 个坐标单位，
  文档不掩饰这一点
- 冻结基线不受影响：`compare.py` / `run_all.py` / `verify_gfx` 都在「动画关闭」下跑
  （`motion: disabled (static prims, pixel baseline kept)`），像素基线仍是 293 px 差

验证：`tests/test_motion.c` 从 47 项扩到 **85 项**（新增 38 项覆盖端点/越界钳制/
中点/5 条曲线单调性/形态特征值/端到端补间取值）；`verify_motion.ps1` 仍是
「关两次一致 / 1,000 步开=关 / 60,000 步开≠关」的三条 A/B。

## 3. 时间模型（第二条线）

`ThreadSleep` / `ThreadWait` / `Timer*` 目前是桩。要进 C 需要：

1. 一个**虚拟时钟**（毫秒），由外壳每帧推进（`fvp_vm_advance_time(ms)`），fvm 里按步数模拟
2. 线程状态机：`flags |= 2/4`（wait/sleep）+ 到期时间 → 到期后清 flag 并恢复
3. `*Test` 命令返回「是否完成」，脚本据此轮询

风险：文本推进节奏会变 → **`compare.py` 可能失效**。届时需要：
- 保留 `--legacy-thread` 作为冻结基线模式（老行为，字节级可复现）
- 新行为单独建立文本基线，并与「原版实机录屏/存档采样」对照（这是唯一真值来源）

**在拿到原版实机对照之前，不把时间模型做成默认开启** —— 否则就是拿没有真值的实现替换已有验收。

## 6. 修正：旋转角单位是 0.05°，不是 0.1°（2026-11-26）

之前 render-model / title-menu / vm-commands 都把 `prim+0x24` 记成"0.1°/单位"。
这次逐指令对完（`scripts/extract-exe-rs-transform.py` → `ref/exe-rs-transform.json`）：

* `PrimSetRS`(82) 的 `idiv 0xE10(3600)` 只是**取模**（存 WORD），
* 渲染 0x42B1E2: `fild 角度` → `fdiv 3600.0` → `fmul π`(0x472E20) →
  `D3DXMatrixRotationZ(弧度)`，
* ⇒ **渲染角 = a·0.05°**，**7200 单位 = 360°**。

所以脚本里的 3600（开场 p1..p3 的 `MotionMoveR 3600→0`）渲染出来是 **180°→0**，
标题背景的 150/250/550/1250 是 **7.5/12.5/27.5/62.5°**。`src/gfx.c` 的四处
角度换算已从 `/10.0` 改成 `/20.0`，`tests/test_gfx_xform.c` 的 90°/180° 断言
改用 1800/3600 单位；`angle_x10` 字段统一改名为 `angle_units`。

## 7. 补充：RS 标志决定两条缩放/旋转变换路径（2026-11-26）

同一段绘制代码里，`test byte [prim+0x6], 0x4`（RS 标志，由 `PrimSetRS/RS2` 设置）
分成两条路：

| | path A（RS 标志置位） | path B（只被 MotionMoveS2 改过 scale） |
|---|---|---|
| 指令 | `0x42B21E` 起（本文件 §RS 段） | `0x42B3A3` 起 |
| 公式 | `final = 画面中心 + S·(R·(图头−OP) + prim + accum)` | `final = prim + 锚点 + S·R·(图头 − 锚点)`，锚点 = OP（未设 OP 时以图头为原点） |
| 旋转 | 有（角度非 0 时） | 有（同一段旋转矩阵先建好） |

脚本事实（`ref/title-bg-motion.json`）：**五彩斑斓只有 258 调过 `PrimSetRS`**（4 次，
且都写 prim 258），259/260/261 没设 ⇒ 258 走 path A（绕画面中心缩放），259..261 走
path B（绕 OP=(1200,675) 缩放）；**星空没有 OP/RS ⇒ path B**，而它的背景图头是
(0,0) ⇒ 等价于**左上锚缩放 2000→1000**，正好是 `src/gfx.c` 的
`gfx_draw_image_zoomed` 已实现的语义（静态分析反过来验证了我们的实现）。

> 诚实记录一次**像素实验**（B 类，仅作参考）：按"动画终态"（25 s 后 A=0.9、
> B/C/D=0.8，角度 0）把 4 层摆出来再和 `out/orig-title/orig-title-005.png` 比，
> 总差是 **21.35**，比现在静态（所有层 s=1、裁剪 240/135）的 **13.11** 更差。
> 说明那张原版帧大概率不是"动画跑完后的稳态"（或它来自窗口缩放的截图，本身带
> 采样偏差），**不能拿它当摆放位置的判据**——这符合"抓帧只做最终像素验证、
> 不能当参数来源"的约定。摆放以脚本 + 静态分析为准，原版帧只用来发现"还差多少"。

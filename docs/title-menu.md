## 2. 已落地：`src/titlemenu.c` 布局 + 命中（与渲染无关）

```c
FvpTitleMenu m;
fvp_title_init(&m);                       /* 几何默认值 = 上表实测值 */
int idx = fvp_title_hit(&m, mx, my, measure, ctx);   /* 0..4 或 -1 */
fvp_title_move(&m, mx, my, measure, ctx);            /* 更新 hover */
int picked = fvp_title_click(&m, mx, my, measure, ctx); /* 命中且 enabled → 0..4 */
```

设计要点：

* **右对齐靠测宽**：模块本身不碰字体，只收一个 `FvpTitleMeasure` 回调
  （`int (*)(void *ctx, const char *utf8, int font_px, int *width)`）。
  有字体就用真宽度，没字体回落到 `字符数 × 字号/2` 的等宽估计——**两种情况下右边界
  都严格是 1769**。
* **墨迹框 ≠ 点击带**：`fvp_title_item_rect()` 返回墨迹框（高 = 字号 3/4 = 42，
  与实测 40..42 吻合）；`fvp_title_hit()` 在此基础上横向各放宽 24 px、纵向补足到
  整行 100 px——原版悬停/点击的行高就是 100。
* `enabled[]` 用来表达"没存档时 Continue 是灰的"这类状态（数据来源是 `save/` 目录，
  由外壳填）。

测试 `tests/test_titlemenu.c`（**90 项**，不需要游戏数据）：用"假测宽"复现上表的实测
宽度，逐项断言右边界 = 1769、左边界 ±1 px、墨迹中心 y ±2 px、墨迹高 ±2 px，以及
命中/悬停/点击/禁用项/无字体回落/NULL 安全。

### 2.1 像素级渲染验证（`tests/test_titlemenu_draw.c`，68 项）

光有布局对是不够的，还得证明"画出来真的落在那个位置"。为此给 gfx 加了两个
引擎侧 UI 用的 API：

```c
int gfx_text_width(Gfx *g, const char *utf8, int px);          /* 量宽 */
int gfx_draw_text_line(Gfx *g, const char *utf8, int x, int y, int px,
                       int r, int gr, int b, int alpha);       /* 画一行 */
```

它们不带文本窗口的排版/换行/对话框，只按字号挑字体逐字画；**字号和字体自带字号
不同时按比例缩放**（内建 8x16 位图放大到 56 px → 一个字 28 px 宽、墨迹高约 42，
正好对上原版实测的 40..42）。注意顺序：`gfx_render()` 会按图元/文本窗口重建画布，
所以引擎侧 UI 的叠加文字必须在 render **之后**画（外壳里也是这个顺序）。

测试在 1920×1080 画布上按布局画 5 项，再扫墨迹包围盒断言：

| 断言 | 结果 |
|---|---|
| 5 项墨迹右边界 | 全部落在 1766..1769（原版 1768/1769） |
| 行距 | 每两项中心差 100 ± 2 px |
| 墨迹高 | 30..60 px（内建字体实测 ≈42，与原版 40..42 一致） |
| 墨迹上沿 | 布局 y 到 y+10 之间（内建位图字形自带约 7 px bearing，属字体度量差异） |
| 命中一致性 | 每项中心点的 `fvp_title_hit()` 都返回该项 |

`make check` 现在跑 23 个单测。

### 3.1 更正：iroseka 的 `title_start*` 是「New Game」的状态变体，不是 5 个菜单项

上一版把 `title_start` / `title_start1..5` 当成 5 个菜单项的贴图，这是错的。
2026-11-24 把 6 张图都看了一遍：

| 素材 | 内容 |
|---|---|
| `title_start`(340×80) | `New Game` 正常态（白边 + 深蓝字） |
| `title_start1`(340×91) | `New Game` **选中态**（青色发光 + 下面带「はじめから」注音） |
| `title_start2..5`(340×80) | `New Game` 的其它变体（不同发光/淡出） |

也就是说 iroseka 只有"New Game"这一项有贴图，`Continue/Album/Option/Exit` 是引擎
**用字体画的**（这也解释了为什么 `font/` 里的字体、以及标题上那套衬线体只出现在
文本项上）。星空的记忆则相反：`title_start`(275×40) 就是文字本身，
`title_start_ray` 是发光层，两项分开贴。

因此 profile 里 **iroseka 的 asset 全部留空 → 走文字模式**，
hoshimemo 的 asset 指向各自贴图 → 走贴图模式。

### 3.2 外壳现在真的会贴图（`gfx_draw_image_at`）

新增 `gfx_draw_image_at(gfx, slot, x, y)`：把图形槽里的图按
`slot_compose() + blit_sprite()` 直接贴到画布（和精灵渲染同一条路径），
在 `gfx_render()` **之后**调用（和文字覆盖层同一时机）。

`--title-menu` 的流程变成：

1. 按 profile 找当前作品 → 把 `asset` 名装进图形槽 `0xF00+i`；
2. 装上了 → 覆盖层逐项 `gfx_draw_image_at()`（星空的记忆：真贴图）；
3. 一张都没装上（五彩斑斓的世界：没有菜单贴图）→ 退回文字模式（内建字体）。

实测：星空的记忆 `title: 5/5 menu textures loaded (slots 0xF00..0xF04)`，
截图出来就是原版那套"白色描边 + 青色发光"的字样、居中、行距 90；
五彩斑斓的世界 `title: no usable texture, falling back to text`，右对齐 1769 不变。

### 4.2 Continue 的存档列表（只读）

点 Continue 会打开存档列表：`src/savelist.c` 把 `<game_dir>\save\sNNN.bin` 逐个
解析成一条记录（时间戳 7 字节、章节名 cp932→UTF-8、当前行、缩略图标记），
按 `x=120, y=150, row_h=64, width=1680` 的带画出来，行文本形如
`No.481   2023/03/19 23:43   プロローグ`。命中判定按行带算（`fvp_savelist_hit`）。

- Windows 下 CJK 路径只能走宽字符 API，所以**目录枚举与读文件在外壳里做**
  （`FindFirstFileW` + `_wfopen`），`savelist.c` 只吃"槽文件字节"
  （`fvp_savelist_add_slot_bytes`），保持可移植；
- 槽尾的 128 槽动态字符串表（`src/savetail.c`，见 `docs/save-format.md` §2.4.5）里能解出
  当时的**背景图名**（例如 s905 的 `BG063_000b`），行文本会显示成
  `No.905   2023/03/19 23:43   [BG063_000b] プロローグ`；解不出来就不显示；
- 选中一行只记日志（`save list: selected No.481 ...`）并**停在列表里**——
  槽尾 500–597 KB 的引擎状态快照还没解，恢复不了，所以不启动脚本（如实标注）；
- 调试/截图入口：`--title-save-list`（等价于启动即打开 Continue 列表）；
- 实测：五彩斑斓的世界 6 个可读槽（第 7 个 `save.bin` 是全局状态不是槽），
  星空的记忆 0 个（没有 `save/` 目录）；这两条都进了多游戏门禁。

### 4.3 键盘导航

`fvp_title_nav(m, +1/-1)` 上下移动 hover（**跳过 `enabled[] == 0` 的项**、到边界环绕、
全禁用时返回 -1），`fvp_title_activate(m)` 确认当前项（没有 hover 时退到第一个可用项）。
外壳把 ↑/↓/Enter/Esc 做成窗口输入里的 `nav` 位掩码（`FVP_NAV_UP/DOWN/LEFT/RIGHT/
ENTER/ESC`），**只有菜单打开时**才让窗口捕获取消 ESC 的"直接退出"语义
（`input.capture_nav`），菜单关掉后 ESC 仍是退出。

单测（`test_titlemenu`，共 227 项）覆盖：从无 hover 开始、连续上下、反向环绕、
禁用项跳过、全禁用、激活回退、NULL。

### 4.4 hover 态（选中状态贴图）

星空的记忆的菜单素材是"文字 + 发光"两张图：`title_start`（文字，275×40）与
`title_start_ray`（整行光带，1920×20），其余四项同理。外壳现在把**发光层也装进
图形槽**（`0xF08+i`），鼠标悬停到第 i 项时先把光带贴上去、再贴文字：

- 光带横向居中、竖向对准该行墨迹中心（`gfx_image_size` 取真实尺寸后算）；
- 五彩斑斓的世界没有发光素材（`asset_glow` 为空）→ 只走文字模式的高亮色；
- `--title-hover N` 是**截图/门禁用的钩子**：把第 N 项锁定为 hover（不随鼠标变化），
  这样"hover 态"可以被像素级验证。

实测（星空的记忆，hover 第 2 项 CONTINUE）：与无 hover 截图相比 **34,128 个像素不同**（逐像素），
且**全部**落在第 2 项那一行（y≈681–686），正是原版选中时那条横贯全屏的青色光带。

### 4.5 标题背景（星空的记忆 `title_bg1`）

`title_bg1`（graph.bin 索引 987，1920×1080）就是星空的记忆的标题背景：晴天海景。
外壳把它装进 `0xFF0` 槽，在贴图模式下**最先**画（铺满整屏），再画发光层、菜单文字。

五彩斑斓的世界没有对应材质（白天那版背景仍未在 graph.bin 里找到），所以它仍是

### 4.6 关键发现：**素材头里自带摆放坐标**

HZC1 图片头除了宽高，还有 `x/y` 两个字段；引擎渲染时 `img.x/img.y` 直接进坐标计算
（`render-model.md` §2.1）。所以标题 logo、版权行、菜单按钮的**摆放位置本来就存在
游戏素材里**，不用从截图反推。实测（星空的记忆）：

| 素材 | 尺寸 | 头里的 x/y | 和之前从截图量的墨迹框对比 |
|---|---|---|---|
| `title_bg1` | 1920×1080 | (0,0) | — |
| `title_logo1` | 1082×418 | (419,72) | — |
| `title_continue` | 230×40 | (845,670) | 墨迹 856..1064 / 671..704 → 正好差 11/1 px（贴图内留白） |
| `title_end` | 110×40 | (905,940) | 墨迹 914..1005 / 941..973 → 同样差 11/1 px |
| `title_copyright` | 445×24 | (737,1043) | 屏幕最底部 |

所以外壳现在**优先用素材头的 x/y** 摆放（`gfx_image_offset()`），只有算不出来时才退回
profile 里按墨迹框反推的位置。五彩斑斓的世界同理：`title_logo1` 1150×283 @ (701,149)，
现在也画在正确位置了。

### 4.8 开场序列（`--opening`，2026-11-25）

原版启动后先是一串 logo 淡入淡出（`docs/original-verification.md` §6 的抓帧时间线），
然后标题画面从白色里淡入。实测素材：`logo_bg` 是**纯白 1920×1080**，
`logo_favo` 是带 alpha 的 FAVORITE logo（868×133 @ (526,407)）。

实现：
- `src/openseq.c/.h`：纯时间轴（不碰 gfx）——白底 300 ms → logo 淡入 1200 →
  停留 2100 → 淡出 1200 → 标题从白色淡入（白色遮罩 255→0）600，合计 **5400 ms**；
- 外壳 `--opening`：按相位画"白底 + logo（按 alpha）"，最后一段先画标题再压白色遮罩；
- `--shot-at N`：跑到 N 毫秒时存一张截图（中间态验证用；结尾不再覆盖同一路径）；
- 单测 `test_openseq`：**388 项**（相位边界、alpha 单调/有界、白底阶段两个 alpha 为 0、
  钳制、NULL 安全）；
- 门禁：`verify_multigame` 新增开场阶段，抓 200 / 1500 / 6200 ms 三帧，断言
  "白场没有 logo 像素 → 1500 ms 有 logo → 序列跑完进标题"。

**如实说明**：时长与缓动是**近似值**（原版整段约 10 s，含第二个 logo 与
`logo_favo_view` 分件动画）；这里先把"白底 + 主 logo + 白场进标题"这条主干做通，
分件与第二个 logo 留给后续轮次。

### 4.9 背景叠加层与菜单配色（2026-11-25）

iroseka 的 `title_bg1_A` 只是"云"，原版标题里的**风车、飘落花瓣、光束**在

叠上后与原版帧的平均差从 48.0 降到 34.6，`title_frame` 再补一点暗角。

- profile 新增 `bg_overlay[4]` + `bg_overlay_count`；外壳在背景之后、logo 之前按序

- `--title-no-bg` 现在会**整组跳过**背景与叠加层（几何测量用）。

**菜单配色**：iroseka 的菜单是深蓝衬线字，实测暗部均值 **RGB(0,19,143)**。profile

### 4.13 New Game 的白场过渡（`--title-fade`，默认 800 ms）

原版点 New Game 后是"白屏过渡再进正文/OP"（`docs/original-verification.md` §6）。
现在外壳这么做：

1. 选中 New Game → 白场 alpha 0→255（前半段，默认 400 ms）；
2. **白场峰值处**才 `fvp_vm_start()`（原版也是遮住画面时才切换）；
3. 后半段 alpha 255→0，露出脚本第一帧。

实现只是一个帧内状态（`title_fade_active` + 已过毫秒），白场用 `gfx_fill_canvas()`；
`--title-fade N` 可改时长（0 = 直接进，用于 A/B）；`--pick N` 是截图/门禁钩子，
把第 N 项当成"已被选中"。

实测（iroseka，`--pick 0 --shot-at 450/1600`）：450 ms 帧均值 **223**（接近全白）、
1600 ms 帧均值 **0.4**（已是脚本画面）；日志给出
`start transition -> vm started at 400 ms` / `start transition done (800 ms)`。
门禁对这两点都有断言（白场峰值亮度 + 脚本确实在过渡中启动）。

### 4.14 存档列表 → "部分恢复"视图（Load 的诚实中间态）

存档列表里按 **Enter**（或左键点同一行）会进入"部分恢复"视图：

1. 把该槽动态字符串表里记的**背景图**整屏铺开（`gfx_draw_image_scaled` 到 1920×1080）；
2. 在下方画出该槽记录的**台词**；
3. 左上角常驻标注 `[PARTIAL RESTORE] visual + text only`；
4. 日志写 `load: partial restore slot=N graph=... (visual+text only, game state NOT restored)`。

**它不是读档**：不恢复全局变量、文本窗口、脚本位置——按 §4.2 的静态分析结论，存档里
本来就没有 pc/栈，真正的读档需要"场景/行号重放"。这个视图的意义是把"存档里确实能
还原的东西（画面+文本）"先做出来，并且**明确标注部分恢复**，不误导。

`--load-slot N` 可直接进入该视图（截图/门禁用）；`ESC` 退回存档列表。

**顺带修的一个真实 bug**：同一存档里章节名是 CP932、汉化台词是 GBK，之前按单一编码
解码会把台词解成半角片假名乱码。现在 `src/savelist.c` 增加了"看着不对就换另一种编码"
的启发式（半角片假名/替换字符占比 > 25% 时重试），并有单测覆盖。

### 4.15 游戏内菜单（引擎侧 UI，覆盖在脚本画面上）

原版没有"画菜单"的脚本命令（命令表里只有 `MenuMessSkip` 与 `TitleMenu` 两条相关项），
游戏内菜单由 exe 自己画。所以这里和标题菜单一样属于**外壳实现**：

- 纯逻辑在 `src/gamemenu.{h,c}`：初始化（标签/行距）、居中布局、命中测试、
  键盘导航（跳过不可用项、循环）、激活/点击、`selected` 记录；
- 单元测试 `tests/test_gamemenu.c`（**50 项**）：坐标边界（左/右/行间/末项之下）、
  跳过不可用项、循环导航、打开时 hover 落在第一项、关闭后不再响应、NULL 与上限安全；
- 外壳（`src/platform/win32/main_win32.c`）：游戏中按 **ESC** 打开/关闭，
  ↑/↓ 或鼠标移动选行，Enter/左键确认；画法是**压暗背景 + 居中列出 5 项 + hover 高亮**，
  文字复用标题菜单字库（`--title-font`，没有就退回位图字体），左上角常驻 `ESC: close`；
- 动作（2026-11-25 起都是**真动作**）：
  * `SAVE`：用模板槽 + 当前画面写一份**真实存档**，但只写到 `--save-preview`
    指定的路径，**绝不写进游戏自己的 `save/`**（日志里明说 game save dir untouched）；
  * `LOAD`：先扫描 `save/sNNN.bin` 再打开存档列表（实测 6 个槽与磁盘一致）；
    真正的"读档"仍是部分恢复，见 `docs/save-snapshot.md` §4.6；
  * `OPTION`：设置面板——**主音量可调**（面板打开时 ↑/↓ 每次 ±10%，通过
    `fvp_snd_bridge_set_master()` 立即作用到正在播放的通道并读回显示；
    文字速度/跳过模式仍只显示当前值）。`--menu-adjust N` 可连调 N 步（门禁用）；
  * `TITLE` 回标题画面、`QUIT` 退出进程；
- `--menu-at N` 是截图/门禁钩子：脚本开始跑 N 毫秒后自动打开菜单。

门禁 `tests/verify_gamemenu.py`（`run_all` 第 6.5 步）：断言日志
`menu: auto-opened at <t> ms (5 item(s))` 且 t 落在请求时间附近（实测 407 ms vs 400 ms）、
截图 1920×1080×32、菜单区域有文字墨迹（实测 446 个采样点）。

**注意**：ESC 现在**不会再直接退出窗口**（`capture_nav` 常开），游戏中 ESC 变成"开关菜单"，

## 6. 一条被证否的猜测：`TitleMenu` 命令**不**负责传递菜单布局（2026-11-25）

前面（§3、§4.11）一直悬着一个问题：标题菜单的**按钮位置**到底是引擎里写死的常量，
还是脚本传进来的参数？按"先结构分析文件"的方法论查了三个独立证据源，结论是
**都不是 `TitleMenu` 命令的参数**：

| 证据 | 结果 |
|---|---|
| exe 的 MSVC RTTI 类名 | 61 个类里**没有** `TitleMenu`（有 `FontList`/`FontRasterizer`/`TextFont`/`HGraphPrim`/`HTextStyler`/`TextureRenderer`/各种 `HPrimMove*`）→ 不是 C++ 类画的 |
| HCB 内嵌命令表 | 有 `TitleMenu` 这一项，`argc = 1`（与 `ref/cmd_table.json` 一致） |
| 脚本里的 6 个调用点（五彩斑斓） | 每个 `syscall 141` 的**紧邻前一条指令都是 `pushtrue`**，即只传 1 个布尔 → 不是 6 个布局参数 |
| 星空のメモリア | 同样：`argc = 1`，7 个调用点全部紧邻 `pushtrue` |
| 命令 handler | `TitleMenu`(141) 的 handler 与 `MenuMessSkip`(41)、`SysAtSkipName`(108) 是**同一个函数** `0x437950`（纯空操作）→ 这个命令在本作里不做任何事 |

**所以那条"从 6 处 `03 8D 00` 调用点实参里能拿到按钮命中矩形"的猜测是错的**，
`0x06` 那个字节也不是 argc（见下一节的对账）。下一步要查的是**标题画面到底由谁画**：
候选是「引擎启动代码用图元摆贴图」或「另一段脚本场景」，两者都能静态查——不再是"量截图"。


## 7. 命令表 argc 的实测对账（`scripts/audit-script-argc.py`）

为了确认上面的 `argc = 1` 不是我们自己读错，换了一个**独立证据源**：看脚本自己在每个
`syscall` 之前实际压了几个值（基本块回溯；遇到 call/表达式/上一条 syscall 的返回值
就记为"不可判定"）。结果（门禁 `tests/verify_script_argc.py`）：

| 作品 | 指令数 | 可判定调用点 | 被证实 argc 的命令 | 异常 |
|---|---:|---:|---:|---|
| 五彩斑斓的世界 HD | 948,219 | 825 | **82 / 148** | 3 条（id 24 / 114 / 116） |
| 星空のメモリア HD | 1,135,159 | 865 | **83 / 148** | **同样这 3 条** |

那 3 条异常在**两部作品里完全相同**、每条只有 1–2 个调用点，成因是表达式临时值
（`pushtemp` / 前一条 `syscall` 的返回值）留在栈上被算进了实参个数，不是表错；
门禁把它们冻结成已知项，任何**新增**异常都会失败。

顺带否掉另一个读法：HCB 命令名表里每个名字后面那个字节**不是 argc**——`TitleMenu`
后面是 `0x06`，但脚本只用 1 个实参调用它；把整个名字表按 `[len][name][NUL][argc]`
解析只能对上 135 条、且与真实调用点冲突。**真正的 argc 以 `ref/cmd_table.json`
（另有 4,700 余个调用点作证）为准。**

## 8. 结论：标题画面是**脚本画的**，菜单项就是图元（2026-11-25）

第 121 轮证否了 `TitleMenu`(141) 传布局参数之后，第 122 轮把"谁画标题画面"用文件证据
定下来了——**是脚本**，不是引擎 UI。证据全部静态可复核
（`scripts/extract-title-scene.py`，基线 `ref/title-scene.json`，门禁
`tests/verify_title_scene.py`）：

## 11. 状态变体的真相：它们是**整幅不同的帧**，不是"轻微高亮"（2026-11-25）

上一节把"五彩斑斓 hover 暂不改变画面"冻结成已知缺口，理由是"哪个变体是 hovered
态"没定。本轮用 `scripts/analyze-title-variants.py` 把变体逐像素比了一遍
（基线 `ref/title-variants.json`，门禁 `tests/verify_title_variants.py`），
结论比"映射未知"更硬：

| 观察 | 数值 |
|---|---|
| 每项变体数 | 五彩斑斓 **5 个**（`title_<item>1..5`）；星空 **1 个**（`title_<item>2`） |
| 变体与基准的差异 | 五彩斑斓 **69.7%–81.0%** 的像素不同，最大通道差 **255** |
| 亮度方向 | 每个变体都是"变暗的像素远多于变亮的像素"（例：`title_start1` darker 17315 / brighter 3438） |
| 变体 1 的尺寸 | 比基准**高 11–12 px**（基准 80/80/80/90/80 → 变体 1 是 91/91/91/92/92） |

两条推论：

1. **"hover = 换一个变体贴图"是错的**。差异 70%+ 的整幅图不可能是"高光/描边"
   级别的状态差；变体 1 还比基准高 11–12 px，说明它多带了一条内容。
2. **变体是脚本状态机选的**。证据在脚本里：`title_*` 的 6 个名字先被读进局部
   变量（`local 4..9` = 第 1 项的基准+5 变体，`10..15` = 第 2 项……），随后
   `GraphLoad` 用的是 **`pushstack 4..15`（变量）** 而不是字符串常量，装进图元
   `1501..1506`（第 1 项）、`1508..1513`（第 2 项）……
   ——即"当前显示哪一张"由脚本按状态用 `PrimSetDraw` 选择。

所以 hover 的正确实现不是"换一张图"，而是**解开这段状态机**：什么时候画哪个
图元、是否还配合 `PrimSetAlpha`/`PrimSetRS`（脚本里同区域确实有
`PrimSetAlpha(265,0)`、`PrimSetRS(265,0,1500)` 这类调用）。
这是下一轮的第一件事；本轮把"变体是整幅帧"这个事实冻结住，避免以后又按
"换张高亮图"的简化去实现。

> 顺带修正 §10.1 的说法：那里写"变体映射未定"，现在知道了——变体不是"状态映射"
> 那么简单，它们是脚本状态机的**素材池**，映射在脚本代码里而不是素材名里。

## 12. 变体映射定出来了，hover 已实现（2026-11-25）

第 125 轮发现"变体是整幅不同的帧"，本轮把映射**定死**并落地。判据是三个可测的量
（`ref/title-variants.json`，门禁 `tests/verify_title_variants.py` §2.5）：

| 变体 | 尺寸 | 均值 alpha | 均值 B−R | 判定 |
|---|---|---:|---:|---|
| `title_<item>`（常态） | 340×80 | 93 | 36 | 基准态 |
| **`title_<item>1`** | 340×**91**（高 11 px） | 95 | **121** | **高亮/选中态**（明显偏蓝、alpha 不降） |
| `title_<item>2` | 340×80 | 81 | 51 | 淡出帧 1 |
| `title_<item>3` | 340×80 | 66 | 63 | 淡出帧 2 |
| `title_<item>4` | 340×80 | 52 | 74 | 淡出帧 3 |
| `title_<item>5` | 340×80 | 35 | 84 | 淡出帧 4（alpha 只剩基准的 38%） |

所以这不是巧合，是设计。星空的记忆没有这套变体（每项只有 1 个变体），它的

## 13. 背景层叠放顺序：脚本给了 Z 值，但它不是剩余误差的主因（2026-11-25）

标题背景是**四层**，脚本把它们分别 `GraphLoad` 进槽位 258–261，然后逐个设 Z：

| 槽位 | 素材 | 尺寸 / 素材头坐标 | 脚本 `PrimSetZ` |
|---|---|---|---:|
| 258 | `title_bg1_A` | 2400×1350 @ (0,0) | **1000** |
| 259 | `title_bg1_B` | 781×1350 @ (518,0) | 900 |
| 260 | `title_bg1_C` | 2400×1350 @ (0,0) | 850 |
| 261 | `title_bg1_D` | 1955×1230 @ (0,111) | 800 |

这些值是脚本里的**字面量**（`PrimSetZ(258,1000)` 这种），已冻结进
`ref/title-scene.json` 的 `layer_z`，门禁 `tests/verify_title_scene.py` §4 断言。

脚本还给每层设了 `PrimSetOP(prim, 2400/2, 1350/2)`（原点=画布中心 → 等效于把
2400×1350 的"设计画布"居中到 1920×1080，裁掉四周 240/135），`PrimSetRS(prim,
…, 1000)`（缩放 1.0）。这与我们 `bg_src_x/y = (240,135)` 的裁剪完全一致——
**裁剪量的来源也补上了**。

### 三种顺序的实测（同一张原版标题帧）

| 绘制顺序 | mean abs diff |
|---|---:|
| **A → C → D → B（保留，实测最优）** | **13.13** |
| A → B → C → D（按 Z 降序） | 13.65 |
| D → C → B → A（按 Z 升序） | 14.38 |

结论（照实写）：

1. **Z 顺序不是剩余误差的主因**——三种排法只差 0.5–1.3，而我们的总差是 13.13；
2. 按 Z 的两种自然排法都**比现有顺序差**，说明要么 FVP 的 z 语义与我们的渲染器相反，
   要么这四层里有一层（很可能 A，2400×1350 那张天空）在引擎里是**垫底并带 alpha**、
   而叠放之外还有别的混合（例如 `PrimSetAlpha`/blend 或整幅提亮）；
3. 所以本轮**没有**凭 Z 值改默认顺序，而是：把 Z 值冻结进基线、把
   `bg_on_top` 作为 profile 字段留出（当前两个 profile 都是 0），并把这个"三种顺序"
   的实测记下来——免得以后再花一轮重新试。

**下一轮的方向**：查这四层的 `PrimSetAlpha`/`PrimSetBlend` 实参（脚本里 258–261 的
Z 之后紧跟着的就是 OP/RS，alpha 可能在别处或用默认 255），以及 logo
（`title_logo1` 1082×418）与版权行的实际叠放位置；这三类更可能是 13.13 的主要来源。

## 15. 背景合成模型：用原版帧验证 18 个候选，结论是"我们的做法已经是最优"（2026-11-25）

§14 的误差分布显示背景（rest）占了差异像素的 88%，所以这一轮专门查"背景四层到底怎么合成"。
做法不是猜：`scripts/analyze-title-bg-blend.py` 把四层素材解成 BGRA，在 numpy 里按下表
18 个候选（顺序 × 混合 × 底色）各合成一遍，**只拿原版帧的纯背景区域**（扣掉 logo /
菜单 / 版权行，实测 1,559,720 px）比平均差。

| 候选 | 平均差 |
|---|---:|
| **measured 顺序（A→C→D→B）+ over（直通 alpha）** | **11.562** ← 最优 |
| z-descending（A→B→C→D）+ over | 12.257 |
| z-ascending（D→C→B→A）+ over | 13.632 |
| measured + add（加色） | 17.816 |
| measured + premul（预乘） | 507.207（素材不是预乘的，模型不适用） |
| 底色黑/白 | 完全相同（第一层 A 是不透明 BGR24，底色被完全覆盖） |

三条结论：

1. **我们渲染器的做法（顺序 A→C→D→B + 直通 alpha over）在 18 个候选里就是最优**——
   这一步有原版帧作证，不再是"试出来的"；**2026-11-25 起这一条有了更强的依据**：
   `ref/exe-d3d-states.json` 从 exe 的 `SetRenderState` 调用点抄出了
   `SRCBLEND=SRCALPHA` / `DESTBLEND=INVSRCALPHA` / `ALPHABLENDENABLE=TRUE` /
   `BLENDOP` 从未设置（默认 ADD），见 `docs/c-gfx.md` 的"D3D9 混合状态"一节。
2. 按 Z 的两种自然顺序都更差（12.26 / 13.63），进一步说明 §13 里"Z 顺序不是主因"的判断；
3. **背景区域仍有 11.56 的平均差**，而合成模型已被排除 → 剩下的差异只可能来自
   **动态量**：脚本在标题初始化里确实调了 `MotionAlpha`(42)、`MotionMoveR`(51)、
   `MotionMoveS2`(54)、`MotionMoveZ`(57) 等动画命令（`0x58217` 起一大串），
   说明这些层/logo 在原版里**是动的**；我们的截图是某个固定时刻，原版帧是另一个时刻，
   相位不同就会留下这种"结构性"残差。

**下一轮**：解 `0x58217` 起那串 Motion* 的实参（哪个图元、什么曲线、多长时长），
把标题画面的**动态**（至少第一帧/静止态）对上去；同时把 §14 说的 hover 上移 48 px

## 17. 用 exe handler 裁决第 130 轮的矛盾：缩放 1.0 是对的（2026-11-25）

§16 里有个没解决的矛盾：脚本写 `MotionMoveS2(258, 1300, 900, …, 7, 3)`，如果它是
"1.3 → 0.9 的缓和动画"，标题稳态就该是 0.9；但拿原版帧扫描却得出 1.0 更贴合。
按方法论，这种矛盾**不能拿截图投票**，得去静态分析 handler。

`scripts/extract-exe-motion-params.py`（基线 `ref/exe-motion-params.json`，门禁
`tests/verify_exe_motion_params.py`）从 handler 里抄出来的事实：

| 命令 | handler | 实参约束（exe 里成对出现 `cmp $MIN` / `cmp $MAX`） |
|---|---|---|
| `MotionMoveS2`(54) | `0x0043af70` | arg0 图元 1..0xFFF；**arg1..arg4 缩放 100..10000**（per-mille）；**arg5 时长 1..300000 ms**；**arg6 缓动 mode 1..5**；arg7 布尔；最后调 `0x0042d670` 注册补间 |
| `MotionMoveS2Stop`(55) | `0x0043b0a0` | 只有 arg0，**跳 `0x00427460`** —— 该例程把补间表里那一条的 active 标志清 0（从 0x200 条里按图元号找），**不改回数值** |
| `MotionAlpha`(42) | `0x0043a8b0` | arg2 目标值**钳到 255**；arg3 时长 1..300000 |
| `PrimSetRS`(82) | `0x0043baf0` | 角度对 3600 取模写 `prim+0x24`（**渲染 1 单位 = 0.05°**，见 `ref/exe-rs-transform.json`）；缩放钳到 ≥100 写 `prim+0x26/+0x28` |
| `PrimSetZ`(91) | `0x0043bff0` | z 钳到 ≥100 写 `prim+0x12` |

于是矛盾解开了：`MotionMoveS2(258, 1300, 900, 1300, 900, 7, 3, null)` 的
**时长是 7 ms**（几乎瞬时），而且这段是"离开标题"时的缩小——不是稳态。
**标题稳态的缩放就是 1.0**，我们的静态绘制是对的；§16 里"用原版帧扫描排除候选"
的结论恰好和 handler 一致，但它现在**不再是依据**，只是验证。

顺带把 ④「缓动 mode 1..5」也坐实了一格：mode 的合法范围 **1..5** 是 exe handler
里的范围检查（`cmp $0x5`），不是我们从脚本里猜的。
## 18. PrimSet* 的实参语义：**非整数 = 保持原值**，坐标是绝对值（2026-11-25）

第 17 轮把 `Motion*` 的实参约束从 handler 里抄出来之后，同一套方法继续往
`PrimSet*` 上补。目标是把"标题/演出怎么摆"里最后几格**缺省语义**也坐实——
这类东西抓帧永远拿不到（帧里只有结果，没有"哪个实参不是整数时就跳过写入"）。

`scripts/extract-exe-motion-params.py` 这一轮新增三类提取：

1. **绝对寻址的字段写**：`mov %dl,0x61dd6b(%eax,%ecx,1)`（基准 `0x61dd64`，
   低字节差就是字段偏移）——`PrimSetAlpha`/`PrimSetBlend` 是这种写法；
2. **prim+6 的脏标记位**：`orb $0x1,0x6(%eax)` 这类，记录每个 handler 置了哪些位；
3. **逐实参的 int 检查 ⇒ 只写那一个字段**（第 6 类事实，见下表"缺省规则"列）。

产物 `ref/exe-motion-params.json` 新增 `abs_field_writes` / `dirty_flag_bits` 两个键，
门禁 `tests/verify_exe_motion_params.py` 加 §6/§7/§8 断言它们；`MotionAlpha` 的
旧断言（把 arg2 写成"钳到 255"）也按 asm 改正为"arg1/arg2 都是 0..255 的 alpha 值"。

| 命令 | handler | 实参约束（asm 里的 `cmp`/`ja`/`jl`） | 写哪里 | prim+6 脏位 |
|---|---|---|---|---|
| `PrimSetAlpha`(77) | `0x00437990` | arg0 prim 1..0xFFF；arg1 必须 int 且 **0..255**（`cmpl $0xff ; ja` 无符号） | 直接写 **prim+7**（alpha 字节） | 无 |
| `PrimSetBlend`(78) | `0x0043ba20` | arg0 prim 0..0xFFF；arg1 必须 int 且 **0..1** | 直接写 **prim+8**（混合模式字节） | 无 |
| `PrimSetOP`(81) | `0x0043ba90` | arg0 prim 1..0xFFF；**只有 type==4 的图元**才继续 | +0x20 / +0x22（各 16 位） | 0x40 |
| `PrimSetWH`(89) | `0x0043bf50` | arg0 prim 1..0xFFF；arg1→+0x18、arg2→+0x1a，**各看各的类型** | +0x18 / +0x1a（各 16 位） | 0x1+0x40 |
| `PrimSetXY`(90) | `0x0043bfa0` | arg0 prim 1..0xFFF；arg1→+0x14、arg2→+0x16，**各看各的类型** | +0x14 / +0x16（各 16 位） | 0x40 |
| `PrimSetZ`(91) | `0x0043bff0` | arg0 prim 1..0xFFF；arg1 int，**<100 钳到 100** | +0x12（16 位） | 0x4+0x40 |
| `MotionAlpha`(42) | `0x0043a8b0` | arg0 prim 1..0xFFF；**arg1/arg2 是两个 0..255 的 alpha 值**（非 int 或越界 → 读 prim+7 的当前值当缺省）；arg3 时长 1..300000 ms；arg4 0..1；arg5 布尔 | 不直接写，调 `0x0042d460` 注册补间 | 无 |

### 这一轮最有用的结论：缺省规则是**逐字段**的

handler 对每个实参先 `cmpb $0x2,(%eax)`（"是不是 int"），**不是 int 就跳过那一条
`mov`，其余字段照写**。所以：

```text
PrimSetXY(prim, true, -48)   ⇒  x 保持不动；y := -48（绝对值赋值，不是 y -= 48）
PrimSetWH(prim, 800, true)   ⇒  w := 800；h 保持不动
PrimSetAlpha(prim, 255)      ⇒  prim+7 := 255
```

这条规则正好解释了我们之前的一个**误读**：§14 把脚本里的
`PrimSetXY(1521/1522, true, -48)` 读成"hover 时上移 48 px"。按 handler 的写入
语义它其实是"**x 不动、y 设成 -48**"，也就是把图元挪到屏幕上方之外（iroseka 的
`title_option` 高 90、行 y 从 495 起，-48 足够整块露出画面外）——这是**隐藏**，
不是位移。调用点（`iroseka.hcb`）：

| pc | 调用 | 上下文 |
|---|---|---|
| `0x58d97` | `PrimSetXY(1522, true, -48)` | 前面是 `pushglobal[3]; pushint8[1]; eq; jmpcond 0x58dab`（某全局状态的条件分支） |
| `0x58da1` | `PrimSetXY(1521, true, -48)` | 同上分支 |

同时脚本对这些图元是**成组**地先显后隐：`PrimSetDraw(1508,1)` + `PrimSetAlpha(1508,0)`
（`0x58c8a..0x58d07`）——高亮变体图元先画出来但 alpha=0，基础图元 `PrimSetDraw(...,0)`
关掉。所以 hover 的实现路线是"**高亮图元常驻 + alpha/显隐切换**"，不是"把基础图元
挪一下"。§14 的 48 px 结论就此作废，下一轮按这个路线实现 hover。

### 为什么值得单独记一笔

字段偏移（+7 alpha、+8 blend、+0x12 z、+0x14/16 xy、+0x18/1a wh、+0x20/22 OP、
+0x24 角度、+0x26/28 缩放）、脏标记位、以及"非 int = 保持原值"的逐字段缺省语义，
这三样都是**"实际操作上一样"的前提**，而它们全都只存在于 exe 的 handler 里：
抓帧看到的永远只是某个时刻的结果，拿不到"传 `true` 时哪个字段不变"。

## 22. 标题背景的缩放/旋转：旋转在脚本里，不在图像包里（2026-11-25）

问题：**背景的旋转能不能靠解包解出数据？** 答案分三层：

1. **图像包（graph.bin / HZC1）里没有旋转**：44 字节头只有 `w/h/x/y/fmt`，
   其余是像素。解包只能得到尺寸与摆放坐标。
2. **旋转/缩放在 HCB 脚本里**：标题背景的 `MotionMoveS2`(54) / `MotionMoveR`(51)
   调用，实参是字面量（角度单位见 `ref/exe-rs-transform.json`：渲染 1 单位 = 0.05°，
即 150/250/550/1250 单位 = 7.5°/12.5°/27.5°/62.5°；缓动 mode 1..5，handler 0x43AE50 / 0x43AF70）。
   新增 `scripts/extract-title-bg-motion.py` 把它们连同 pc 冻结进
   `ref/title-bg-motion.json`，门禁 `tests/verify_title_bg_motion.py`。
3. **"绕哪转、旋转后怎么摆放"是 exe 代码**，不是数据：已解出
   `最终位置 = prim.xy + OP + R·S·(图头 xy − OP)`（`docs/opening.md` §3），
   标题背景的 `PrimSetOP(1200,675)` 正好是 2400×1350 设计画布的中心；
   但"超尺寸图在 OP 缩放下的可见裁剪"还需要再对一遍 exe 的绘制路径（下一轮）。

冻结的事实：

| | 五彩斑斓（0x59143..0x591D3） | 星空（0x6FD87） |

| 背景层 | 258/259/260/261 = title_bg1_A/B/C/D（2400×1350、781×1350、2400×1350、1955×1230） | 只有槽 258，依次装 title_bg3→title_bg2→title_bg1（都是 1920×1080） |

## 23. 星空标题背景缩放已实现（2000→1000 / 40000 ms，2026-11-25）

§22 冻结了背景的缩放/旋转参数。本轮把其中**规则最干净**的一条接到画面上：
星空的背景是单层 1920×1080、`PrimSetOP` 缺省（轴心 (0,0)，左上锚）、不旋转，
脚本只有 `MotionMoveS2(258, 2000, 1000, 2000, 1000, 40000, 3)`（hcb 0x6FD73..0x6FD87，
时长来自 0x6FD67 的 `pushint32 40000`）。

实现：

| 位置 | 内容 |
|---|---|
| `src/titlebg.c/.h` | 时间轴数学：`2000 - 1000·ease3(t/40000)` per-mille，角度恒 0；五彩斑斓返回 `animated=0`（未实现） |
| `src/gfx.c` | `gfx_draw_image_zoomed()`：按缩放只处理"屏幕可见的源区域"，源矩形量化到 16 px 并**缓存**缩放结果 |
| `src/platform/win32/main_win32.c` | `--title-bg-anim`（默认关，`--title-anim` 不会自动打开）；`title_draw_bg()` 在动画可用时走缩放路径 |

实现过程中踩过两次"卡顿"，都记在这里：

1. **三角形滤波太慢**：1920×1080 一次 ~80 ms（外壳只有 **10 fps**）；先加缓存并把
   源矩形量化到 16 px，虽然到 48 fps，但每 ~0.6 s 跳 16 个源像素 → **肉眼可见台阶**。
2. **最终做法**：不量化源矩形，直接按 `源坐标 = (屏幕像素+0.5)/缩放 − 0.5` 的
   **分数映射做双线性**（x/y 表预计算，内层纯整数），每帧重算一次 ~10 ms：
   - 外壳 **~52-59 fps**；
   - 抓 4 s 帧序列（`--shot-every 60 --shot-div 4`）测相邻帧差：
     min **0.386** / median **0.917** / max **1.587**（max/median **1.73**），
     没有"卡住不动"的 0 平台，也没有跳变；
   - 终态 1000‰ 仍走 1:1 直贴，与静态帧逐字节相同。

门禁 `tests/verify_title_bg_anim.py`（一次 42 s 运行）：
* 动画中途 vs 静态：mean_abs **48.09**、差异像素 **74.6%**（背景确实被放大）；
* **40 s 后 == 静态帧逐字节 0 差**（1000‰ 走恒等路径，缓存不污染终态）；
* 日志：星空打印 `bg zoom started (hoshimemo ...)`；五彩斑斓打印
  `iroseka: not implemented, static`（不假装做了）；
* 性能：缩放期间 fps **48**（门禁断言 ≥25）。

**仍未实现**：五彩斑斓 4 层背景的缩放 + 旋转（15/25/55/125°→0、25000 ms、OP=(1200,675)、
超尺寸源图 2400×1350 等）——要先确定 exe 在"OP 轴心 + 超尺寸图"下的可见裁剪规则；
实现后它就是同一套 `titlebg` + `gfx_draw_image_zoomed`（加角度与裁剪参数）的扩展。

## 25. 五彩斑斓的四层背景动画（path A/B；2026-11-26 修两处显示错误 + 全分辨率）

§22/§24 定清了参数与两条变换路径（`docs/animation-baseline.md` §7），本轮把它接到画面：

| 层 | slot（脚本 GraphLoad） | 路径 | 缩放 | 旋转（0.05°/单位） | 图头 |
|---|---|---|---|---|---|
| A `title_bg1_A` | 258 背景槽 | **path A**（唯一设过 `PrimSetRS`）→ 锚点 = 画面中心 | 1300→900 | 150→0（7.5°→0） | (0,0) 2400×1350 |
| B `title_bg1_B` | 259 叠加 0 | path B → 锚点 = OP=(1200,675) | 1600→800 | 250→0（12.5°→0） | (518,0) 781×1350 |
| C `title_bg1_C` | 260 叠加 1 | path B | 2500→800 | 550→0（27.5°→0） | (0,0) 2400×1350 |
| D `title_bg1_D` | 261 叠加 2 | path B | 4000→800 | 1250→0（62.5°→0） | (0,111) 1955×1230 |

全部 25000 ms、缓动 mode 3；屏幕上自下而上按 A → C → D → B 叠
（这个顺序是实测最优，见 §13；脚本的 PrimSetZ 是 A=1000/B=900/C=850/D=800，
按 Z 排的顺序反而更差，说明 Z 的语义与本引擎的"升序贴图"不同）。

### 25.1 两处显示错误（2026-11-26 用户实机反馈）

1. **风车后面多出一道黑色柱状剪影**：`title_draw_overlay()` 在 iroseka 里先画
   静态叠加层（`title_draw_overlays()`），再调 `title_draw_bg()`；而背景动画
   路径**自己也会把三个叠加层按仿射变换画一遍** ⇒ 叠加层被画两遍，静态那份
   （B = 风车）不跟着动，于是看起来"风车后面多了一根柱子"。
   修法：`title_draw_bg()` 改成返回 int（1 = 已把背景+叠加层整组画完），
   调用方拿到 1 就**跳过**静态叠加层；动画关时仍走原静态路径（像素基线不变）。
2. **锚点没换算到画面坐标（风车入场太靠中）**：path B 的锚点 = OP，但 OP 是
   **设计画布**（2400×1350）坐标；屏幕看到的是设计画布裁掉 (240,135) 之后的
   1920×1080。锚点少减这个裁剪原点 ⇒ 整层被恒定平移 (+240,+135)，风车/羽毛
   全都偏右偏下（用户 2026-11-26 反馈"风车剪影的入场位置太靠中"）。
   修法：`锚点 = OP − (bg_src_x, bg_src_y)`。**自检不变式**：缩放 1000‰、角度 0
   时该公式必须退化成静态路径的 `图头 + 源像素 − 裁剪原点`，现在逐字节相等
   （`tests/test_gfx_xform.c` §5 新增 12 项断言）。
3. **图层拿错图**：静态路径按"显示顺序"C→D→B 把叠加层装进 259/260/261，
   动画路径按 `slot_tag` 取图（B=1 → 259）。两套编号不一致，导致动画里
   "风车"实际取到的是 C 的图，而真正的风车图被当成 D 层按 4000‰/62.5° 画——
   于是风车要么消失、要么位置离谱。
   修法：新增 `fvp_titlebg_slot_tag_for_name()`（`src/titlebg.c`），装载与静态
   绘制都按**脚本 GraphLoad 的槽号**（258=A / 259=B / 260=C / 261=D）走；
   静态帧与修前逐字节相同（`out/vs-original/iroseka-title.bmp` 0 差异）。

### 25.2 分辨率：从 1/8 改成全分辨率（用户反馈"羽毛变糊"）

旧实现在 `(1920/8)×(1080/8)` 上合成再双线性放大——风车/羽毛这类高频内容明显发糊
（清晰度只有静态帧的 ~20%）。现在默认 **div=1（全分辨率）**，靠三个优化把
性能拉回可用区间（`src/gfx.c` 的 `gfx_draw_affine_layers()`）：

| 手段 | 说明 |
|---|---|
| 16.16 定点增量映射 | 每行算一次 u/v，行内只做整数加法，去掉每像素 4 次浮点乘加 |
| 8×8 覆盖掩码 | `slot_compo_mask()`：稀疏叠加层（羽毛/风车）命中空掩码格直接跳过 4 次双线性取样 |
| 不透明层快路径 | `slot_compo_opaque()`：alpha 全 255 的背景层跳过 alpha 双线性与混合除法 |
| 像素中心约定 | 逆映射要减 0.5 再取整（与 `zoom_warp_rgba` 一致）；少了它恒等映射落在半像素上，整幅图被双线性糊一层、包围盒少 1 px |
| 末行/末列 | 双线性需要 `ix+1`，越界时基址退到 `cw-2` 并给满权重；否则恒等映射少最后一列 |

实测（本机，`--title-bg-anim --shot-at 2000`，8 s 平均）：

| 设置 | fps | 清晰度（Laplacian 比，静态=1.0） |
|---|---|---|
| 旧：div=8 | 45–52 | ~0.2 |
| div=4 | 43 | — |
| div=2 | 45 | — |
| **默认：div=1（全分辨率）** | **36–41** | **0.78** |

`--title-bg-div N`（1..8）可手动覆盖：老机器用 2 换帧率，追求极致用 1（默认）。
静态标题仍走 1:1 直贴，**像素基线一个字节都不变**（`verify_gfx` 289 px / PSNR 49.95 不变）。

### 25.3 门禁 `tests/verify_title_bg_anim.py`（两作都跑）

## 附录 A：`prim 265` 初始化被跳过的静态证据（2026-11-26）

```
584d8  initstack 1,45
584df  global[1663]==1 && global[1664]==1 && global[1665]==1 && global[1666]==1 ?
       └─ 都成立时再看 global[1662]==1 → local[44]=0/1（local44 = "背景已加载"）
58517  pushstack 254            ; 函数实参
5851b  == 1 ?
5851c  jmpcond 0x58E42          ; 实参 != 1 → 跳去跑批次初始化（258..265 等）
58521  ...                      ; 实参 == 1 → 只加载 title_bg1_A..D（静态标题）
```

| `call 0x584D8` 的调用点 | 实参 | 我们是否执行 |
|---|---|---|
| `0x590CC` | 1（`0x590CA pushint8 1`） | **执行 1 次** → 走静态标题，跳过批次 |
| `0x59E93` | 未执行 | 0 次 |
| `0x59EBB` | 未执行 | 0 次 |
| `0x59EFC` | 未执行 | 0 次 |

统计口径：`pctrace`（`bin/fvp-headless.exe ... --pctrace`）里这些 pc 的出现次数。
`0x58E42` 在 HCB 里只被 `0x5851C` 的 `jmpcond` 引用，所以"没跑到批次"等价于
"`0x584D8` 的另外三个调用点没跑"。

工具：`scripts/scan-prim-refs.py <prim>` 列出某个图元号在 HCB 里的全部引用点
（`pushint16`/`pushint8` 立即数），`--json` 给门禁用；门禁
`tests/verify_prim_refs.py` 冻结了 265 的 38 个引用点与上面四个调用点。

## 附录 B：`MotionAlphaTest(265)` 的两个对照实验（2026-11-26）

| 开关 | 作用 | 结果 |
|---|---|---|
| `FVP_MOTION_TEST_INVERT=1` | 翻转 `*Test` 返回值 | 脚本离开等待循环：`primhit` 0 → **187**（与无 gfx 的 `fvm.exe` 一致），但随即空转清理：`0x235C9..0x235DC`（GraphLoad(prim,true)+PrimGroupOut+PrimSetNull）出现 **190 次** |
| `FVP_MOTION_NO_REAP=1` | 不回收已完成补间 | 无变化（`primhit` 0/0、41395 ThreadNext）——因为 265 的记录从未创建 |

结论：卡死既不是 `*Test` 极性，也不是记录回收；缺的是**脚本自己的菜单交互**
（悬停/选中时给菜单组 265 排动画）。我们的外壳用引擎侧菜单，脚本菜单路径没走，
所以记录永远不出现。默认路径两个开关都关，门禁数字不变。

## 附录 C：`MotionAlphaTest` 的 exe 语义（2026-11-26，逐条反汇编）

```
43a9c0  mov  0x4(%esp),%eax      ; arg0
43a9c4  cmpb $0x2,(%eax)         ; 类型必须 2（int）
43a9c7  jne  0x43aa04            ; 否则不写返回值
43a9c9  mov  0x4(%eax),%eax      ; id
43a9cc  cmp  $0x1,%eax
43a9d1  cmp  $0xfff,%eax
43a9f3  call 0x422990            ; 容器里查这条 id 的记录
43a9f8  test %eax,%eax
43a9fa  setne %al                ; 找到 = 1，没找到 = 0
43a9fd  mov  %al,0x814(%esi)
```

所以 `*Test` 的语义是「容器里有没有这条记录」，**1 = 有**，与 `src/motion.c`
里 `fvp_motion_test()` 的实现一致。`FVP_MOTION_TEST_INVERT` 那个实验里"脚本能离开
等待循环"是假象：把**所有** `*Test` 都反转之后，脚本把"动画已结束"当成初值，
随后空转到标题退场清理（`0x235C9` helper 190 次）。

另：把光标放到 New Game 矩形中心（`FVP_CURSOR=1615,535`，矩形来自
`ref/title-rects.json`）跑 headless，`primhit` 仍是 **0/0** —— 脚本没走到菜单命中轮询，
它还在 `0x592DF` 等 `MotionAlphaTest(265)`。所以"脚本菜单交互没发生"不是卡死的原因，
更准确的是：卡在菜单交互**之前**的 265 等待上。

### 附录 C 补充：`fvm.exe` 不是流程参照

`src/syscall.c` 的 `case 44`（MotionAlphaTest）要求 `vm->gfx_bridge != NULL` 才写返回值；
无 gfx 的 `bin/fvm.exe` 因此走不到写入，脚本读到的 temp 是上一条命令的残留值，
这就是它能"跑出" 194 行台词的原因。冻结文本基线 `ref/ref-900k.txt` 由这条路径产出，
按约束保持不动，但**不能用它判断脚本流程是否正确**；带 gfx 的 headless 只跑到
`0x592DF` 才是语义上诚实的结果。

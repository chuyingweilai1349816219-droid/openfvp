## 1. 结论先行：那 94 KB 是什么

**它不是独立译文表，而是补丁的「超长译文重定位区」。**

中文文件 = 日文文件**原地改字符串**后的副本 + 在文件末尾追加的 94,075 B。
附加数据段（`script_len+4` 之后）拆开是：

```
+0x0000  2,057 B   命令表（与日文版逐字节相同）
+0x0809  94,075 B  重定位区（2,586 条记录，把「放不进原槽位的译文」搬到这里当代码执行）
```

证据：`tail_start = script_len + 4 + 2057 = 0x413c52 = 4,275,282`，恰好等于**日文文件大小**——因为日文文件正好结束在命令表末尾，补丁是在日文文件副本上就地改写再追加。

### 1.1 槽位改写方式一：译文放得下（52,875 条）

槽位长度原样保留，译文后面补 `00` 填充：

```
JP  0e 15 | 90 e1 82 cc 82 e6 82 a4 82 c9 90 5e 82 c1 94 92 82 c5 81 41 | 00
CN  0e 15 | c8 e7 d1 a9 d2 bb b0 e3 b5 c4 b4 bf b0 d7 a3 ac | 00 00 00 00 00
     └同长度┘ └──「如雪一般的纯白，」16 B──┘ └─ NUL + 4 B 填充，凑满 21 B ─┘
```

`0e 15` 的 `0x15=21` 是**日文槽位长度**，不是译文长度；译文实际只有 17 B（含 NUL），其余用 `00` 补齐。

### 1.2 槽位改写方式二：译文超长 → 重定位（2,586 条）

原地槽位的前 5 字节被改写成 `06 <尾巴绝对地址>`（`jmp`），**槽位剩下的旧字节没有清理**；完整译文写进文件尾巴的记录里，记录末尾 `jmp` 回原槽位之后。

```
主脚本 @0x7e8f7（日文槽位 15 B）:
  JP : 0e 0d 92 aa 95 97 82 c9 97 68 82 ea 81 41 00     pushstring(13)「潮風に揺れ、」
  CN : 06 53 3c 41 00 │ 97 82 c9 97 68 82 ea 81 41 00    jmp 0x413c53 + 原槽位第 5 字节后的残渣(10 B)
       └ jmp 0x413c53 ┘

尾巴 @0x413c52（= 日文文件大小）:
  0x413c52: 00                                   填充
  0x413c53: 0e 0f d4 da ba a3 b7 e7 d6 d0 d2 a1 d2 b7 a3 ac 00   pushstring(15)「在海风中摇曳，」
  0x413c64: 06 06 e9 07 00                          jmp 0x7e906（= 原槽位结束处，即下一条指令）
```

### 1.3 尾巴记录格式（hexdump）

每条记录 = `0e <len> <GBK 译文> 00 06 <u32 回跳地址>`，记录之间只有首条前有 1 B `00` 对齐填充。

| 偏移（相对 `0x413c52`） | 字节 | 含义 |
|---|---|---|
| `+0x00` | `00` | 对齐填充（仅首条前） |
| `+0x01` | `0e` | `pushstring` |
| `+0x02` | `0f` | len = 15（含 NUL） |
| `+0x03` | `d4 da ba a3 b7 e7 d6 d0 d2 a1 d2 b7 a3 ac` | GBK「在海风中摇曳，」14 B |
| `+0x11` | `00` | 字符串结尾 NUL |
| `+0x12` | `06` | `jmp` |
| `+0x13` | `06 e9 07 00` | u32 = `0x0007e906`，回跳地址 |
| `+0x17` | `0e` | 下一条记录（即 `jmp` 直接落到这里，跳过中间所有填充） |

`0x12` 字节 / 条（2 + 14 + 1 + 5）是本记录实际占用；平均 36.4 B/条，2,586 条共 94,075 B。

### 1.4 为什么线性静态分析会「错位」，而原版引擎能跑

`06 53 3c 41 00` 后面的 10 B 是**旧槽位残渣**，不是指令。线性扫描器在 `0x7e8f7` 把 `jmp` 读完，接着从 `0x7e8fc`（`0x97`）继续解码就撞上非法 opcode——所以看起来「从第 200,817 条开始整条流崩了」。

实际上**每条指令的边界与日文版逐字节对齐**：`jmp` 是 5 B，槽位 15 B，边界仍在 `0x7e906`。按日文指令边界逐条核对，948,219 条指令里：

- 非字符串指令的 **opcode 差异 = 0**、**操作数差异 = 0**（补丁完全没动代码）；
- 55,461 条字符串 = 52,875 原地 + 2,586 重定位，**一条不缺**。

原版引擎按绝对偏移 `jmp` 跳进尾巴、执行 `pushstring` 再跳回，所以能正常跑——它的 loader 显然把整个文件映射进脚本空间，而不是只映射 `[4, script_len)`。**这个「把字符串搬到文件尾当代码执行」的手法可以当重定位机制看待，但对任何只认 `[4, script_len)` 的工具都是致命的。**

## 2. 重建算法

`fvp/work/cn_rebuild.py`：

1. **骨架 = 日文指令流**（948,219 条，跳转 100% 合法）。逐条重发；非字符串指令原样复制 `opcode + 操作数`。
2. **译文 = 双通道取值**：
   - 若 `CN[off] == 0x0e` → 原地槽位通道：`raw = CN[off+2 : off+2+len]`，取第一个 `00` 之前的内容；
   - 若 `CN[off] == 0x06` → 尾巴通道：读 `jmp` 目标，解析对应记录，取 `0e <len>` 的内容（并校验记录的 `回跳地址 == off + 日文槽位长度`，2,586 条中 2,585 条吻合，最后 1 条回跳被文件尾截断 1 B，不影响取值）。
3. **重发字符串**：`0e <len(译文)+1> <GBK 译文> 00`，长度按实际重算（丢掉补丁的 `00` 填充）。
4. **重算绝对地址**：第一遍记录「旧偏移 → 新偏移」，第二遍回填所有 `call(0x02) / jmp(0x06) / jmpcond(0x07)` 的 u32 目标。因为映射覆盖**每一条指令的起始偏移**，把 `0x0a pushint32` 当跳转落点的情况也自动正确；而 `0x0a` 的操作数本身（如 `call` 后的声音编号）**原样不动**，不存在误改。
5. **文件头**：`script_len = 4 + len(body)`；`main_start = map[0x22f48] = 0x22f02`（它也是绝对偏移，必须跟着变）；命令表从日文版**逐字节复制**（2,057 B，已验证与中文版那段相同）。

### 2.1 编码修正：SJIS 残槽 → GBK 转码（353 条）

补丁有一个副作用：**当译文与日文原文「同字」时，它认为无需写入，直接跳过**，于是槽位里留着原始 Shift-JIS 字节。而引擎按 GBK 读，这些字节很多**恰好是合法的 GBK 双字节**，于是静默变成怪字：

```
JP  0x1367a: 0e 03 8b f3 00        SJIS「空」(8b f3)
CN  0x1367a: 0e 03 8b f3 00        未被补丁碰过
    GBK 读 8b f3 -> 「嬻」           ← 交付前 VM 输出 [9] 嬻 的原因
新  0x13634: 0e 03 bf d5 00        GBK「空」(bf d5)  ← 修正后输出 [9] 空
```

这类条目共 **353 条**（多为地点/房间/章节标签：`空`、`食堂`、`厨房`、`廊下`、`管理人室`、`加奈の部屋`、`学校・廊下`…）。处理方式：

- 对「与日文字节完全相同且含非 ASCII」的槽位，按 `cp932 解码 → gbk 编码` 重新生成字节；
- GBK 无法编码的字符做最小替换（`・`(U+30FB) → `·`(U+00B7)，共 30 处）；
- 转码失败则回退日文原字节并计数（本次 **0 条失败**）。

> 为什么不能「回退日文原文」了事：回退后字节仍是 SJIS，GBK 引擎照样显示怪字。必须转码。
> 另注：普通 `decode('gbk')` + 往返编码校验**抓不到**这类错误——`8b f3` 是合法 GBK、往返也无损，只能靠「与日文原字节相同」这个特征识别。

## 5. 遗留问题

1. **353 条补丁未译条目**（地点/房间/章节标签等）仍显示日文汉字/假名——补丁本身没给译文，不是本次回退。可用 `cn_strings.tsv` 的 `status == reencoded_sjis` 过滤出来批量补译后重跑 `cn_rebuild.py`。
2. 尾巴最后一条记录的回跳 u32 在源文件里被截断 1 B（省 1 B），重建不依赖它，已忽略。
3. `fvp/ref/cmd_argc.json` 与 hcb 命令表有 **6 个 id 的 argc 口径不同**（49/51、52/54、94/95 成对互换），那是 VM 侧按实际压栈数校正的覆盖表，与本次文件结构无关；重建产物仍逐字节复用日文命令表，`cmd_table.json` 完全吻合。
4. 本次重建**不保留**补丁的 `06` 重定位跳转：所有译文都已搬回正常 `pushstring`，因此产物是自包含的、只认 `[4, script_len)` 的工具也能线性静态分析。

## 1. 为什么需要它

`compare.py` 证明的是「我们的 VM 与参考实现逐字节一致」，`verify_gfx` 证明的是「我们的
渲染与参考实现（PNG）一致」——两条都以**我们自己的参考实现**为基准。原版对照是唯一能
证明「参考实现本身没跑偏」的手段：字体、对话框几何、文字落点、颜色、透明度，都得跟
原版画面量出来的数字比。

| 门禁 | 证明什么 | 证明不了什么 |
|---|---|---|
| `tests/compare.py` | VM 语义与参考实现一致（900k 步逐字节） | 参考实现是否等于原版 |
| `tests/verify_gfx.ps1` | 渲染与参考 PNG 一致（293 px 差异） | 参考 PNG 是否等于原版 |
| **本文的方法** | 原版实际画成什么样 | 需要玩家自己持有游戏才能复现 |

## 2. 前置条件（缺一个就直接失败，且**退出码是 0**）

原版引擎启动时会在用户文档目录写「系统存档」：

```
%USERPROFILE%\Documents\FAVORITE\<作品名>\save\s901.bin
```

这个目录**引擎不会自建**。写失败时它弹一个 `#32770` 消息框，内容（cp932）是：

```
'C:\Users\<user>\Documents/FAVORITE/いろとりどりのセカイ HD/save/s901.bin'の作成に失敗しました
```

点「确定」后进程正常退出，**退出码 0**——所以只看退出码会误判成"游戏自己跑完了"。
另外用 `GetWindowText` 取这段文本时，消息正文会显示成 GBK 乱码（`偺嶌惉偵幐攕偟傑偟偨`），
只有路径部分是正常 UTF-16，别被乱码带偏。

两个条件缺一不可：

1. `Documents\FAVORITE\<作品名>\save\` 目录存在；
2. **启动它的进程**对该目录有写权限——沙箱里运行的父进程会把受限令牌继承给游戏，
   于是目录明明存在、游戏照样报错退出。所以抓帧脚本必须在完整权限下跑。

这就是此前"原版启动几秒就退出 / 截图全黑"的真正原因（不是 D3D 抓不到，是根本没到画面）。

## 3. 抓帧方法

```powershell
# 完整权限（游戏要往 Documents 写存档）
powershell -ExecutionPolicy Bypass -File scripts\capture-original.ps1 `
    -GameDir 'D:\games\五彩斑斓的世界HD' -Clicks 1 -CaptureSec 60
```

脚本做五件事：

1. 启动 `<Exe>`（工作目录设为游戏目录），按 pid 枚举顶层窗口，等
   `HS_MAIN_WINDOW_CLASS00` 主窗口出现；期间一旦出现 `#32770` 就把子控件文本全打出来
   （这是定位启动失败的入口）；
2. 用 `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)` 抓整窗位图，存 PNG，并用 24×24
   采样网格算一个内容指纹，标出画面有没有变化；
3. 需要点进正文时，把**游戏空间坐标**（1920×1080）换算成屏幕像素后再 `SetCursorPos` +
   `mouse_event` 点击。窗口会被 DPI 变成 1707×1067 或 1926×1109（两种都出现过），
   硬编码屏幕坐标必然点空，必须用 `GetClientRect` + `ClientToScreen` 现场算；
4. 原版没有"跑 N 秒退出"的开关，抓够时间后由脚本 `Kill`；
5. **把窗口挪走**，免得 1920×1080 的原版窗口挡住桌面（见 §3.1）。

要点：

- `CopyFromScreen` 抓 D3D9 全屏/覆盖层会得到**全黑**位图；`PrintWindow` +
  `PW_RENDERFULLCONTENT` 才能拿到 back buffer。
- 原版渲染恒定 1920×1080，窗口不是 16:9 时**上下加黑边**（letterbox），不是裁切。
- 抓到的 PNG 落在 `out/orig*/`，测试与文档都不引用它们。

### 3.1 窗口缩不小，只能挪走

原版窗口**没法缩小**，实测证据（`out/probe-resize.ps1`，2026-11-24）：

- 窗口样式 `0x14CA0008`：有 `WS_CAPTION`/`WS_SYSMENU`/`WS_MINIMIZEBOX`，
  **没有 `WS_THICKFRAME`**（不可拖拽缩放）；客户区被钉死在 **1920×1080**；
- 对它 `SetWindowPos(..., 964, 570, ...)`：位置变了、尺寸**一分没变**；
- 加 `SWP_FRAMECHANGED`、甚至先换 `WS_OVERLAPPEDWINDOW` 样式再设尺寸：
  外框仍 1926×1109（换样式只让客户区变小 10 px，因为边框被算进去了）——
  引擎在 `WM_WINDOWPOSCHANGING`/`WM_SIZE` 里把自己的尺寸写回去了；
- 注册表 `HKCU\Software` 与 `Documents\FAVORITE\` 下都**没有**分辨率/窗口配置文件，
  所以也改不了"启动分辨率"。

能成功的只有两个动作（`out/probe-park.ps1` 实测）：

| 动作 | 效果 | `PrintWindow` 还能抓到画面吗 |
|---|---|---|
| 移到桌面外（`x = 桌面宽 + 40`） | 桌面上完全看不见 | **能**，非黑像素 99.2%，与在屏上完全一致 |
| 最小化（`SW_MINIMIZE`） | 桌面看不见 | **不能**：窗口被缩成 237×39，抓到的是图标尺寸的空位图 |

所以脚本默认 `-Park offscreen`：一发现主窗口就把它搬到桌面右侧外面，每帧再纠正一次
（引擎启动过程中会自己重定位）；需要点 `New Game` 时才临时挪回屏幕 (0,0)，点完再挪出去。
`-Park minimize` 只适合"只想挂着游戏不抓图"的场景，`-Park none` 保留原行为。

## 4. 原版启动序列（实测）

1. FVP / FAVORITE logo 淡入淡出（约 10 s）；
2. **标题画面**：天空背景 + 作品 logo + 右侧 5 项菜单 + 右下版权行，静止等待输入；
3. 点 `New Game` → 白屏过渡 → 播 OP 影片（`movie/`），画面有 WMV 的模糊/放大特征；
4. 影片段结束后引擎**再次自行退出（退出码 0，无消息框）**——原因未查，见 §6。

### 4.1 结论：标题菜单是**引擎侧 UI**

- 我们的引擎直接从脚本第 0 条指令开始执行，所以 `--run-seconds 14` 的画面已经是序章
  （「空」标题卡 + 对话框「……お願い」），原版同一时刻还停在标题菜单；
- 也就是说 `New Game / Continue / Album / Option / Exit` 这段不是脚本画的，而是引擎
  C++ 代码画的（菜单项、点击命中、存档缩略图读取都在引擎里）；
- 这解释了为什么我们的 900k 步 trace 从序章正文开始——参考实现同样是从脚本入口跑起的，
  它压根没实现标题界面。

→ 这就是目标②「交互闭环」缺的第一块：**TitleMenu 子系统**。

## 5. 量到的原标题画面数字（可用来校对 TitleMenu 实现）

来源：`out/orig-title/orig-title-005.png`，1926×1109 全窗位图，客户区起点偏移 (3, 29)，
客户区 1920×1080（位图多出的 3 px 是边框）。菜单列取客户区右 34%。

| 项目 | 墨迹 y 范围 | 高度 | 墨迹 x 范围 | 宽度 | 中心 | 行间距 |
|---|---|---|---|---|---|---|
| `New Game` | 511..552 | 42 | 1461..1769 | 309 | (1615, 531) | — |
| `Continue` | 611..652 | 42 | 1514..1769 | 256 | (1641, 631) | 100 |
| `Album` | 712..753 | 42 | 1580..1768 | 189 | (1674, 732) | 101 |
| `Option` | 811..852 | 42 | 1575..1768 | 194 | (1671, 831) | 99 |

由此可得：

- **右对齐**：5 项墨迹右边界都在 x = 1768/1769，右边距 = 1920 − 1769 = **151 px**；
- **行距**：100 ± 1 px（中心 y 依次 531 / 631 / 732 / 831 / 931）；
- **字高**：拉丁大写 + 小写墨迹 42 px（`Exit` 40 px，因为 'E' 比 'N' 矮 1 px 且无 'G' 的
  圆弧溢出），按常见比约等于 **56~60 px 字号**；字体是**衬线体**，带浅色描边/阴影；
- **色彩**：菜单文字是深藏青（`R+G+B < 260` 且 `B ≥ R` 的像素才能被上面的检测器命中），
  落在明亮的天空上；
- **版权行**：`Copyright 2011-2022 FAVORITE All Rights Reserved.` 在客户区底部 y ≈ 1026+
  的右半侧（检测到 1958 个暗色采样点）。

这些数字是"实现 TitleMenu 之后应该长什么样"的第一版验收标准；实现时应当用同样的
`work/measure_title.py` 度量我们的输出来比。

### 5.1 字体来源

游戏目录 `font/` 里只有两款 Sarasa Gothic（cjk 字体，22 MB 级），而标题菜单是**衬线拉丁体**，
说明菜单字体来自系统或引擎内建资源，不是 `font/` 里的 sarasa——实现 TitleMenu 时不要
拿 sarasa 去凑。这一点尚未定论，记为待查。

### 5.2 ⚠ 本机原版画面里的日文/中文是乱码，**不能当文字真值**

抓到的正文帧里，日文/中文是一串片假名垃圾（例如 `クュユュヶ`、`レケ・ミッヤ`），
**这不是我们引擎的问题，也不是原版本身的问题，是本机没按补丁要求配置**：

- 游戏自带的 `启动游戏必看说明` 写了三步：① 给 exe 设高 DPI 兼容性；② **以管理员身份安装
  `font/` 目录里的 Sarasa Gothic 字体**；③ 运行 `_StartGameZH.bat` 后在游戏设置里**选中
  Sarasa Gothic**；
- 本机 `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Fonts` 里**没有** Sarasa
  （`font/` 里那两个 ttf 没装）→ 引擎建不出中文字体，回落到日文字体去画汉化后的文本，
  于是变成片假名乱码。

所以这批帧可以用来看 **布局/几何/颜色**（背景、菜单、对话框位置），**不能用来比对字形与
文字内容**。要拿文字真值得先装字体并进 Option 选字体（需管理员权限 + 菜单交互），
属于恢复该任务时的前置步骤。

## 7. 原版帧回归门禁（2026-11-25）

`verify_gfx` 的基准来自我们自己的参考渲染器，只能证明"C 实现 == Python 原型"。
要回答"和原版差多少"，必须拿**原版实拍帧**来比。这就是本节的门禁：

```
python tests/verify_vs_original.py
```

- 语料在 `out/`（不入库）：`out/orig/`（splash）、`out/orig-title/`（标题）、
  `out/orig-ng2/`（New Game 后 60 s）、`out/orig-hoshi2/`（星空的记忆的实拍）；
  缺语料时脚本打印 **SKIP** 并返回 0（与其它依赖环境的门禁一致）。
- 每个用例在 `tests/original-baseline.json` 里描述：原版帧路径、客户区偏移
  （`out/orig-title/*` 是 1926×1109 全窗位图，客户区从 `(3,29)` 开始）、
  我们外壳的重现参数、以及**冻结的实测平均绝对差**与允许余量。
- 判定：`mean_abs <= baseline + tol` 才算通过；超过即回归。

当前记录：

| 用例 | 重现参数 | 实测 mean abs diff | 基线 | 断言 |
|---|---|---:|---:|---|
| iroseka 标题 | `--title-menu --title-font bin/gfx-font-61.bin` | **13.79** | 13.93 + 1.5 | ✅ |
| 星空标题 | 同上 | 36.09 | 36.23 + 2.0 | ⚠️ 只记录（帧归属是推断的） |

**为什么这是"和原版差多少"的权威数字**：它直接拿原版像素做差，不掺我们的参考实现。
目前标题画面 13.79/255 ≈ 5.4% 的平均差，主要来自菜单字体（Palatino Bold 61 是最接近的

刷新基线的方法（语料更新或有意改渲染后）：


## 8. 从 exe 静态提取绘制协议：让"要跑原版才知道"的那一半不用再跑原版（2026-11-25）

### 8.1 先分清两类"原版事实"

这一节是为了纠正一个**过度悲观**的结论。以前把「原版 UI 不能一模一样」当成"只能靠实拍
帧逐步逼近"，但把"原版事实"拆开看，会发现只有一半真的需要跑原版：

| 类别 | 内容 | 能不能静态拿到 | 为什么 |
|---|---|---|---|
| **A 类：绘制协议 / 常量** | 用哪个 GDI API、什么字符集、什么位图格式、什么质量参数、字号换算公式、单位矩阵、坐标常量、混合模式 | **能，而且是原值** | 这些是 exe 里的常量和调用约定，静态分析读到的就是原版用的值；靠截图反推反而只能得到"像不像" |
| **B 类：最终像素** | 光栅化后的每个像素、D3D 混合后的颜色 | 不能（除 B 类可复现部分） | 取决于本机字体文件版本、GDI hinting、GPU 混合顺序，必须实拍帧 |

所以「原版 UI 一模一样」的正确拆法是：**A 类缺口可以静态闭合，B 类才需要实拍**。

### 8.2 做法（`scripts/extract-exe-gdi.py`）

1. 解析 PE 节表，建立 `虚拟地址(VA) → 文件偏移` 映射（脚本用标准库 `struct` 手写，
   不依赖 `pefile`）；
2. 解析 `work/iroseka_HD.asm`（`objdump -d` 文本），把 `call *0x45dXXX` 按
   `work/vm_imports.json` 的 IAT 表解析成导入函数名；
3. 对关注的 GDI 函数，从调用点**往前收 `push`** 还原实参（最后一个 `push` 是第一个
   参数；中间夹的 `sar`/`imul`/`mov` 不影响）；
4. 参数里若是立即数形式的静态数据（如 `GetGlyphOutline` 的 `MAT2`），直接从 exe
   对应偏移读出来。

### 8.3 提取到的事实

| 项 | 原版的值 | 位置 |
|---|---|---|
| `CreateFontA` | **全 exe 只有 1 个调用点** | `0x0042d24d`（函数 `0x0042d1f0`） |
| `nHeight` | 运行时算出：`−( 95 × (2×(2×[+0x1C] − [+0x18]) − [+0x20]) ÷ 100 )`；`0x5f` 是 ×95，`0x51EB851F + sar 5` 是 ÷100，最后 `neg` | `0x0042d208`–`0x0042d24c` |
| `nWidth` / `nEscapement` / `nOrientation` | `0` / `0` / `0` | 同上 |
| `fnWeight` / 斜体 / 下划线 / 删除线 | `0` / `0` / `0` / `0` | 同上 |
| `fdwCharSet` | **`0x80` = `SHIFTJIS_CHARSET`** | 同上 |
| `fdwOutputPrecision` / `ClipPrecision` / `Quality` / `PitchAndFamily` | 全 `0` | 同上 |
| `lpszFace` | **来自寄存器**（对象 `+0x08`）→ 字体族名是**数据驱动**（脚本的 `TextFontName` / 引擎字体表），**没有写死在 exe 里** | 同上 |
| `GetGlyphOutlineA` | 3 个调用点：1 个 `uFormat=0`（`GGO_METRICS`，只取进位）+ 2 个 `uFormat=1`（**`GGO_BITMAP`，1bpp 位图**） | `0x004327cf` / `0x0043280d` / `0x0043288c`（函数 `0x00432770`） |
| `MAT2` | 3 次调用共用同一个指针 `0x0045D8F8`，内容 = **单位矩阵**（16.16 定点 `0x00010000, 0, 0, 0x00010000`） | 静态数据 |
| `GetOutlineTextMetricsA` | 1 个调用点，`cbData = 0xD4`（= `sizeof(OUTLINETEXTMETRIC)`） | `0x004327eb` |
| `EnumFontFamiliesExA` | 1 个调用点，回调 `0x00443B20`（引擎建字体表，供 `TextFontName` 按名查） | `0x00443c0d` |
| `SetTextColor` / `SetBkMode` | 只在另一条路径（`0x00441c80`）出现：白色 `0x00FFFFFF` + `TRANSPARENT(1)` | — |

两条结论值得单独说：

- **原版文字是 1bpp 位图，不是灰度抗锯齿**。`GGO_BITMAP` 每个像素只有 0/1，所以
  原版的字形边缘是"硬"的；任何用 `TextOut` + 抗锯齿画出来的字，与它的边缘必然
  不同——这不是参数没调好，是**协议不同**。
- **字体族名不在 exe 里**。这解释了我们之前"标题菜单字体只能靠相关度猜"的困境：
  exe 只负责用 `SHIFTJIS_CHARSET` 建字体，族名由数据/设置传进来。所以字体这一项
  要查的是游戏数据与设置，不是 exe。

### 8.4 与本仓库实现的差距（这就是"像素级一致"的剩余主因）

| 项 | 原版 | 本仓库外壳（`src/platform/win32/win32_gdi_text.c`） | 后果 |
|---|---|---|---|
| 字符集 | `SHIFTJIS_CHARSET`(0x80) | `DEFAULT_CHARSET` | 同一族名解析到的字形表可能不同 |
| 取字形方式 | `GetGlyphOutlineA` + `GGO_BITMAP` | `TextOutW` + 32bpp DIB，读 B 通道当覆盖率 | 边缘：硬二值 vs 灰度 |
| 质量参数 | `0`（不指定） | `ANTIALIASED_QUALITY` | 灰度差再加一层 |
| 字体族 | 数据驱动（脚本/设置） | 固定 `Microsoft YaHei`（仅缺字回退用） | 回退字与正文用的字不是同一族 |

另外，正文用的位图图集（`bin/gfx-font-*.bin`，由 `scripts/make-font-atlas.py` 从
TrueType 光栅化生成）与 GDI 在同字号下的 hinting **也不完全相同**，这是正文
字形差异的另一半来源。

> 下一轮的实现项：把缺字回退路径改成与原版同一协议（`SHIFTJIS_CHARSET` +
> `GetGlyphOutlineA/GGO_BITMAP` + 单位 `MAT2`），并给它单独的门禁与开关，
> 不动冻结基线（图集路径不变）。

### 8.5 冻结与门禁

```
python tests/verify_exe_gdi_params.py
```

- 第 1 步：调 `scripts/extract-exe-gdi.py --check`，要求重新提取的结果与
  `ref/exe-gdi-params.json` **逐字节一致**（提取逻辑漂移立刻红）；
- 第 2 步：断言关键不变量——`charset == 0x80`、`GetGlyphOutlineA` 调用点 3 个、
  `uFormat ∈ {0,1}`、三次共用同一 `MAT2`、`MAT2` 是单位矩阵、
  `CreateFontA` 的 10 个"应为 0"的实参确实为 0、`lpszFace` 来自寄存器；
- 第 3 步：打印"原版协议 vs 我们"的对照表（只报告不断言，避免把未实现的当成已实现）；
- 已接入 `tests/run_all.py`（44 → 45 步）；缺原版 exe 或静态分析时打印 **SKIP**
  并返回 0，与 `verify_vs_original.py` 同口径；
- **入库的只有参数**（`ref/exe-gdi-params.json`），不含任何游戏数据。

### 8.6 这一节改变了什么

- **修正**：⑥「原版 UI 一模一样」不再整体归为"必须跑原版"。其中 A 类（字符集、
  位图格式、质量参数、字号公式、矩阵、坐标常量）**已经可以静态提取，并已冻结成基线**；
- **仍需实拍**的只剩：最终像素比对（B 类）、影片解码后的画面、以及"这台机器装的
  是哪个版本的字体文件"这种环境事实；
- 这是"用结构分析解决第六点"的正路：**先提取协议，再让实现照协议跑**，而不是拿截图
  反复猜参数。

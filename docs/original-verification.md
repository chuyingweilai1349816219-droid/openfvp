## 1. 为什么需要它

`compare.py` 证明的是「我们的 VM 与参考实现逐字节一致」，`verify_gfx` 证明的是「我们的
渲染与参考实现（PNG）一致」——两条都以**我们自己的参考实现**为基准。原版对照是唯一能
证明「参考实现本身没跑偏」的手段：字体、对话框几何、文字落点、颜色、透明度，都得跟
原版画面量出来的数字比。

| 门禁 | 证明什么 | 证明不了什么 |
|---|---|---|
| `tests/compare.py` | VM 语义与参考实现一致（900k 步逐字节） | 参考实现是否等于原版 |
| `tests/verify_gfx.ps1` | 渲染与参考 PNG 一致（293 px 差异） | 参考 PNG 是否等于原版 |
| **本文的方法** | 原版实际画成什么样 | 需要玩家自己持有游戏才能复现 |

## 2. 前置条件（缺一个就直接失败，且**退出码是 0**）

原版引擎启动时会在用户文档目录写「系统存档」：

```
%USERPROFILE%\Documents\FAVORITE\<作品名>\save\s901.bin
```

这个目录**引擎不会自建**。写失败时它弹一个 `#32770` 消息框，内容（cp932）是：

```
'C:\Users\<user>\Documents/FAVORITE/いろとりどりのセカイ HD/save/s901.bin'の作成に失敗しました
```

点「确定」后进程正常退出，**退出码 0**——所以只看退出码会误判成"游戏自己跑完了"。
另外用 `GetWindowText` 取这段文本时，消息正文会显示成 GBK 乱码（`偺嶌惉偵幐攕偟傑偟偨`），
只有路径部分是正常 UTF-16，别被乱码带偏。

两个条件缺一不可：

1. `Documents\FAVORITE\<作品名>\save\` 目录存在；
2. **启动它的进程**对该目录有写权限——沙箱里运行的父进程会把受限令牌继承给游戏，
   于是目录明明存在、游戏照样报错退出。所以抓帧脚本必须在完整权限下跑。

这就是此前"原版启动几秒就退出 / 截图全黑"的真正原因（不是 D3D 抓不到，是根本没到画面）。

## 3. 抓帧方法

```powershell
# 完整权限（游戏要往 Documents 写存档）
powershell -ExecutionPolicy Bypass -File scripts\capture-original.ps1 `
    -GameDir 'D:\games\五彩斑斓的世界HD' -Clicks 1 -CaptureSec 60
```

脚本做五件事：

1. 启动 `<Exe>`（工作目录设为游戏目录），按 pid 枚举顶层窗口，等
   `HS_MAIN_WINDOW_CLASS00` 主窗口出现；期间一旦出现 `#32770` 就把子控件文本全打出来
   （这是定位启动失败的入口）；
2. 用 `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)` 抓整窗位图，存 PNG，并用 24×24
   采样网格算一个内容指纹，标出画面有没有变化；
3. 需要点进正文时，把**游戏空间坐标**（1920×1080）换算成屏幕像素后再 `SetCursorPos` +
   `mouse_event` 点击。窗口会被 DPI 变成 1707×1067 或 1926×1109（两种都出现过），
   硬编码屏幕坐标必然点空，必须用 `GetClientRect` + `ClientToScreen` 现场算；
4. 原版没有"跑 N 秒退出"的开关，抓够时间后由脚本 `Kill`；
5. **把窗口挪走**，免得 1920×1080 的原版窗口挡住桌面（见 §3.1）。

要点：

- `CopyFromScreen` 抓 D3D9 全屏/覆盖层会得到**全黑**位图；`PrintWindow` +
  `PW_RENDERFULLCONTENT` 才能拿到 back buffer。
- 原版渲染恒定 1920×1080，窗口不是 16:9 时**上下加黑边**（letterbox），不是裁切。
- 抓到的 PNG 落在 `out/orig*/`，测试与文档都不引用它们。

### 3.1 窗口缩不小，只能挪走

原版窗口**没法缩小**，实测证据（`out/probe-resize.ps1`，2026-11-24）：

- 窗口样式 `0x14CA0008`：有 `WS_CAPTION`/`WS_SYSMENU`/`WS_MINIMIZEBOX`，
  **没有 `WS_THICKFRAME`**（不可拖拽缩放）；客户区被钉死在 **1920×1080**；
- 对它 `SetWindowPos(..., 964, 570, ...)`：位置变了、尺寸**一分没变**；
- 加 `SWP_FRAMECHANGED`、甚至先换 `WS_OVERLAPPEDWINDOW` 样式再设尺寸：
  外框仍 1926×1109（换样式只让客户区变小 10 px，因为边框被算进去了）——
  引擎在 `WM_WINDOWPOSCHANGING`/`WM_SIZE` 里把自己的尺寸写回去了；
- 注册表 `HKCU\Software` 与 `Documents\FAVORITE\` 下都**没有**分辨率/窗口配置文件，
  所以也改不了"启动分辨率"。

能成功的只有两个动作（`out/probe-park.ps1` 实测）：

| 动作 | 效果 | `PrintWindow` 还能抓到画面吗 |
|---|---|---|
| 移到桌面外（`x = 桌面宽 + 40`） | 桌面上完全看不见 | **能**，非黑像素 99.2%，与在屏上完全一致 |
| 最小化（`SW_MINIMIZE`） | 桌面看不见 | **不能**：窗口被缩成 237×39，抓到的是图标尺寸的空位图 |

所以脚本默认 `-Park offscreen`：一发现主窗口就把它搬到桌面右侧外面，每帧再纠正一次
（引擎启动过程中会自己重定位）；需要点 `New Game` 时才临时挪回屏幕 (0,0)，点完再挪出去。
`-Park minimize` 只适合"只想挂着游戏不抓图"的场景，`-Park none` 保留原行为。

## 4. 原版启动序列（实测）

1. FVP / FAVORITE logo 淡入淡出（约 10 s）；
2. **标题画面**：天空背景 + 作品 logo + 右侧 5 项菜单 + 右下版权行，静止等待输入；
3. 点 `New Game` → 白屏过渡 → 播 OP 影片（`movie/`），画面有 WMV 的模糊/放大特征；
4. 影片段结束后引擎**再次自行退出（退出码 0，无消息框）**——原因未查，见 §6。

### 4.1 结论：标题菜单是**引擎侧 UI**

- 我们的引擎直接从脚本第 0 条指令开始执行，所以 `--run-seconds 14` 的画面已经是序章
  （「空」标题卡 + 对话框「……お願い」），原版同一时刻还停在标题菜单；
- 也就是说 `New Game / Continue / Album / Option / Exit` 这段不是脚本画的，而是引擎
  C++ 代码画的（菜单项、点击命中、存档缩略图读取都在引擎里）；
- 这解释了为什么我们的 900k 步 trace 从序章正文开始——参考实现同样是从脚本入口跑起的，
  它压根没实现标题界面。

→ 这就是目标②「交互闭环」缺的第一块：**TitleMenu 子系统**。

## 5. 量到的原标题画面数字（可用来校对 TitleMenu 实现）

来源：`out/orig-title/orig-title-005.png`，1926×1109 全窗位图，客户区起点偏移 (3, 29)，
客户区 1920×1080（位图多出的 3 px 是边框）。菜单列取客户区右 34%。

| 项目 | 墨迹 y 范围 | 高度 | 墨迹 x 范围 | 宽度 | 中心 | 行间距 |
|---|---|---|---|---|---|---|
| `New Game` | 511..552 | 42 | 1461..1769 | 309 | (1615, 531) | — |
| `Continue` | 611..652 | 42 | 1514..1769 | 256 | (1641, 631) | 100 |
| `Album` | 712..753 | 42 | 1580..1768 | 189 | (1674, 732) | 101 |
| `Option` | 811..852 | 42 | 1575..1768 | 194 | (1671, 831) | 99 |
| `Exit` | 912..951 | 40 | 1662..1768 | 107 | (1715, 931) | 101 |

由此可得：

- **右对齐**：5 项墨迹右边界都在 x = 1768/1769，右边距 = 1920 − 1769 = **151 px**；
- **行距**：100 ± 1 px（中心 y 依次 531 / 631 / 732 / 831 / 931）；
- **字高**：拉丁大写 + 小写墨迹 42 px（`Exit` 40 px，因为 'E' 比 'N' 矮 1 px 且无 'G' 的
  圆弧溢出），按常见比约等于 **56~60 px 字号**；字体是**衬线体**，带浅色描边/阴影；
- **色彩**：菜单文字是深藏青（`R+G+B < 260` 且 `B ≥ R` 的像素才能被上面的检测器命中），
  落在明亮的天空上；
- **版权行**：`Copyright 2011-2022 FAVORITE All Rights Reserved.` 在客户区底部 y ≈ 1026+
  的右半侧（检测到 1958 个暗色采样点）。

这些数字是"实现 TitleMenu 之后应该长什么样"的第一版验收标准；实现时应当用同样的
`work/measure_title.py` 度量我们的输出来比。

### 5.1 字体来源

游戏目录 `font/` 里只有两款 Sarasa Gothic（cjk 字体，22 MB 级），而标题菜单是**衬线拉丁体**，
说明菜单字体来自系统或引擎内建资源，不是 `font/` 里的 sarasa——实现 TitleMenu 时不要
拿 sarasa 去凑。这一点尚未定论，记为待查。

### 5.2 ⚠ 本机原版画面里的日文/中文是乱码，**不能当文字真值**

抓到的正文帧里，日文/中文是一串片假名垃圾（例如 `クュユュヶ`、`レケ・ミッヤ`），
**这不是我们引擎的问题，也不是原版本身的问题，是本机没按补丁要求配置**：

- 游戏自带的 `启动游戏必看说明` 写了三步：① 给 exe 设高 DPI 兼容性；② **以管理员身份安装
  `font/` 目录里的 Sarasa Gothic 字体**；③ 运行 `_StartGameZH.bat` 后在游戏设置里**选中
  Sarasa Gothic**；
- 本机 `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Fonts` 里**没有** Sarasa
  （`font/` 里那两个 ttf 没装）→ 引擎建不出中文字体，回落到日文字体去画汉化后的文本，
  于是变成片假名乱码。

所以这批帧可以用来看 **布局/几何/颜色**（背景、菜单、对话框位置），**不能用来比对字形与
文字内容**。要拿文字真值得先装字体并进 Option 选字体（需管理员权限 + 菜单交互），
属于恢复该任务时的前置步骤。

## 6. 已抓到的序章时序（2026-11-24，用户授权后自动跑）

`-ClickEvery 3` 让脚本每隔 3 秒点一次客户区中心推进剧情，抓 60 秒得到：

| 阶段 | 时间 | 画面 |
|---|---|---|
| 点 New Game 后 | 0~10 s | 影片段（模糊/放大特征） |
| 第一次白屏 | ≈11.7~17.9 s | 全白 + 一小段乱码文本（≈(500,490)）——对应脚本里的**「空」标题卡** |
| 正文段 | 17.9~49 s | 天空背景 + 每点一次换一段文本（≈15 个不同帧） |
| 第二次白屏 | ≈52.9 s 起 | 又回到全白 + 小段乱码——第二张**「空」标题卡** |

**结构对得上**：我们的 trace（`ref/ref-900k.txt`）里前 30 行的形状是
`[0] …` 几行 → `[9] 空` → 20 行 `[0]` 正文 → `[9] 空`，与"白 → 正文 → 白"一致。
下一步可以拿"两次「空」之间的点击次数"和 trace 里两次 `[9]` 之间的行数（21 行）去对齐，
这是第一个可以量化的原版判据。

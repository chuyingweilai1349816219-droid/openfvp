## 0. 一句话结论

`hzc1` 是「**44 字节定长头 + 标准 zlib 流**」的位图格式：头里带宽高、像素格式、帧数和游戏内屏幕坐标，
zlib 解压后得到**自上而下、通道序 BGR(A)** 的原始像素。像素格式 0/1/2/3/4 分别对应
BGR24 / BGRA32 / **BGRA32 多帧纵向拼接** / 灰度 / 1bit 掩码。多帧文件（104 个）把 N 帧按行
自上而下堆成一张 `w × (h*N)` 的大图，文件里**没有任何逐帧时长字段**。

## 1. 容器：graph.bin

```

数据区
```

## 2. 文件总体布局

```
0x00 ┌──────────────────────────┐
     │ 44 字节 hzc1/NVSG 头      │
0x2C ├──────────────────────────┤
     │ zlib 流（78 DA）          │  → 解压后 = w*h*bpp*帧数 字节
EOF  └──────────────────────────┘
```

没有尾部数据、没有分块表、没有调色板。`usize` 字段 = 解压后的纯像素字节数，不含 44 字节头。

## 5. 行序与通道序（关键，容易错）

### 5.1 行序：自上而下（top-down），不是 BMP 自下而上

把 `0793_mio_end6` 按「原样」和「上下翻转」各导出一张对比：

* 原样：<fvp/extract/preview/cg_0793_mio_end6.png>
* 翻转：人物倒立、脸在下、腿在上 → 错误

更硬的证据是**文字**：`1042_title_logo1` 解出来是
「いろとりどりのセカイ HD Re:GENERATION」正读无误
（<fvp/extract/preview/logo_1042_title_logo1_checker.png>）。若行序反了，文字会上下镜像。

> 与网络资料的分歧：Kungal 的结构分析帖称 HD 版 hzc 像素是「逐行倒序写入的去文件头 BMP 字节」（自下而上）。
> 本作（2022 HD Re:GENERATION）实测为自上而下；本地参考实现 `nvsg_converter`、
> `nvsgconverter.cpp` 也都不做翻转，与实测一致。可能是旧 HD 版与本作存在版本差异。

### 5.2 通道序：文件里是 B,G,R[,A]

`0004_010101W` 的实测像素：

```
raw pixel(400,150): B=212 G=226 R=245 A=255  →  RGB(245,226,212) 肤色
raw pixel(300,250): B=0   G=125 R=201 A=0    →  RGB(201,125,0)   橙色（透明区）
```

统计判决（`0004_010101W`，alpha>200 的不透明像素 93,513 个）：

| 解释方式 | 满足条件 | 占比 |
|---|---|---|
| BGR→RGB（本文实现） | R>G>B（肤色/暖色） | **74.60%** |
| 直接当 RGBA 读 | B>G>R | 0.18% |

即：按 BGRA 解释时绝大多数像素符合暖色调分布；按 RGBA 直读则几乎没有暖色，显然是错的。
fmt=0 同理是 BGR 三通道。fmt=3/4 单通道不涉及。

### 5.3 alpha

`0004_010101W` alpha 分布：`==255` 38.1%，`==0` 60.4%，四角全 0 —— 是干净的人物剪影。
合成到棋盘底后轮廓正确（<fvp/extract/preview/portrait_0004_010101W_checker.png>）。
透明像素仍保留 RGB 值（例如 alpha=0 处仍有 `R=201,G=125`），解码时不要丢弃。

## 6. 多帧格式（fmt=2）

### 6.1 布局：纵向堆叠

```
zlib 解压后的像素块（w × h*N）:
row   0 .. h-1     → frame 0
row   h .. 2h-1    → frame 1
...
row (N-1)h .. Nh-1 → frame N-1
```

每帧大小固定 `w × h`，帧内行序同样是自上而下，帧内像素同样是 BGRA。
文件里除 `0x20` 的帧数外**没有任何逐帧偏移表**——因为偏移是纯算术的：

```
frame i 在像素块中的偏移 = (0, i*h)
frame i 在屏幕上的位置   = 头部 (x, y)，尺寸 w × h
```

证据：104 个 fmt=2 文件的 `usize` 全部精确等于 `w*h*4*count`（1112/1112 全库尺寸校验通过），
且把像素块按 `h` 行切开后每一帧都是完整的人脸表情（
<fvp/extract/preview/multiframe_0005_010101W_F_sheet.png> 34 帧，
<fvp/extract/preview/multiframe_0207_170106W_F_sheet.png> 40 帧）；
按列切则完全不成图。

### 6.2 帧数分布（104 个多帧文件）

| count | 4 | 6 | 7 | 8 | 10 | 11 | 12 | 18 | 20 | 22 | 24 | 26 | 28 | 30 | 32 | 34 | 38 | 40 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 文件数 | 2 | 1 | 1 | 1 | 3 | 1 | 2 | 1 | 3 | 25 | 2 | 8 | 19 | 13 | 8 | 11 | 2 | 1 |

合计 104 个文件；全库总帧数 3654 帧。单帧格式（fmt 0/1/3/4）的 `0x20` 字段恒为 0。

### 6.3 帧时长：不在文件里

* 44 字节头之后**全部**是 zlib 流，`usize` 精确等于像素字节数，没有任何空间放时间表；
* 1112 个文件的 4 个零字段（0x1C/0x24/0x28）全部为 0，没有任何非零的「间隔/时长」候选值。

因此逐帧显示时长由引擎/脚本决定。脚本层确实有动画类命令（证据：
`fvp/work/cmd_registrations.json` 中 `MotionAnim` argc=4、`LipAnim` argc=8、`MotionAlpha` argc=6），
但参数含义未静态分析确认，故**具体帧间隔仍属未解**。

### 6.4 帧间差异（用途推断）

`0005_010101W_F` 34 帧：相邻帧平均绝对差 0.48..13.73（中位 0.93），差异区域集中在面部
（0 帧 vs 30 帧的变化像素只占 21.4%）。`0207_170106W_F` 40 帧同理。
说明这些多帧文件是**表情/口型差分**（配合 `LipAnim`/`MotionAnim`），而不是整屏动画。
文件命名中 `_F` 后缀（如 `0005_010101W_F`）也符合「Frame/差分」语义。

## 7. 屏幕坐标 x/y

`0x18/0x1A` 是这两个少量小端整数，用于把「部件图」贴到屏幕合成位置：

* 784/1112 个文件 x≠0（最大 1845），793/1112 个 y≠0（最大 1243）；
* 全屏 CG/背景 `x=y=0`（如 `0559_endback1` 1920×1080）；
* 1056/1112 个文件满足 `x+w ≤ 1920` 且 `y+h ≤ 1080` —— 坐标基准就是 **1920×1080 画布**；
* 最好的证据是 `0793_mio_end6`（1880×1040, x=20, y=20）：`20+1880+20=1920`、
  `20+1040+20=1080`，即 1:1 CG 在 16:9 画布上**精确居中**；
* 剩下 56 个越界样本全部是 `bu_effect*` 特效（如 `0349_bu_effect15_L_1` y=1243，
  整张图在屏幕下缘之外），这是特效「从画外滑入」的起始坐标，属正常数据而非解析错误。
  `0287_bl_char`（2000×1200, x=y=0）是代码按图集直接切的图标表，不做屏幕贴图。

结论：x/y 是**该图左上角在 1920×1080 屏幕上的位置**，可以为负/出界（特效）。
解码成单张 PNG 时该字段应保留为元数据，不要裁掉。
（标题背景 2400×1350 的 `x=y=0`，由引擎做整体缩放，不参与部件合成。）

## 8. 压缩

标准 zlib（`78 DA`，RFC1950），无自定义字典、无 RLE/DXT。
1112/1112 的 zlib 头都是 `78 DA`（level 9）。
解压耗时：全库 516 MB 约数秒；单张 1880×1040 CG 约 10–20 ms。

## 9. 解码器 `fvp\work\hzc1.py`

零依赖（Pillow + numpy），无 Py2 兼容层。

```powershell
# 单文件 -> 该文件所有帧
python fvp\work\hzc1.py fvp\extract\graph\0793_mio_end6 -o fvp\extract\preview

# 多帧 + 联系表
python fvp\work\hzc1.py fvp\extract\graph\0005_010101W_F -o out --sheet

# 整个目录
python fvp\work\hzc1.py fvp\extract\graph -o fvp\extract\graph_png --json report.json
```

输出命名：`<文件名去扩展>_000.png`、`_001.png` …；`--atlas` 额外输出整块拼接图，
`--sheet` 输出多帧联系表，`--json` 输出逐文件摘要（含 `fmt/frames/width/height`）。

程序会打印：格式编号与名称、帧尺寸、帧数、帧偏移、游戏坐标、`usize` 校验结果；
多帧文件额外提示「帧时长不在文件内」。

Python API：

```python
import hzc1
hz = hzc1.Hzc1Image('path/to/file')
hz.fmt, hz.width, hz.height, hz.frames       # 元数据
for im in hz.frame_images():                 # PIL.Image，逐帧
    ...
hz.raw                                       # 解压后的原始字节（已做 usize 校验）
```

**踩坑记录**：`fvp\work\` 下有其它任务的 `dis.py`、`names.py` 等脚本，会遮蔽标准库同名模块
（`numpy.ma → inspect → dis` 会炸在 `dis.py` 上）。从该目录运行/导入 numpy 前应先把它从
`sys.path` 移除；`hzc1_sample.py` 已按此处理。`hzc1.py` 本身不导入这些模块，可安全直接用。

> 为什么不直接用参考实现：`nvsg_converter` 用的是 Py2 时代的 `Image.fromstring`（Pillow 12 已删除），
> 且只处理单帧、不支持 1bit；`nvsgconverter.cpp` 需要 Qt + 编译。自写版本约 300 行。

## 11. 未确认 / 待办

1. **帧时长**：文件内无字段；HCB 侧 `MotionAnim`(argc=4)/`LipAnim`(argc=8) 的参数含义未静态分析，
   实际播放间隔未知。
2. `0x10` 恒为 `0x0100`（256）的含义未知（无证据支撑任何猜测）。
3. `x/y` 坐标系已确认是 1920×1080 画布（居中 CG + 出界特效两项证据）；但部件与底图的合成顺序、
   以及「同一角色部件组」如何配对，不在图像格式范围内，未研究。
4. fmt=2 的「第 0 帧 = 顶部」顺序、以及它究竟按索引选表情还是按时间播放，仅由帧间差异和命名推断。
5. fmt=4 的「1=墨迹」只在外字图标上视觉验证过，是否存在反相变体未知。
6. 本包内 1112 个文件全是 `hzc1`+`NVSG`；旧版 `hzc` 变体不在本包内，未验证。
7. 2400×1350 与 1920×1080 两套分辨率在游戏内的缩放规则未研究。

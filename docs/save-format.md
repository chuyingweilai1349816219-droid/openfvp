## 0. TL;DR

```
save/sNNN.bin  = 7 字节本地时间戳 + 3 条长度前缀字符串 + 200×113 原始 BGRA 缩略图
                 + 引擎状态快照（文本窗口 32 个、字符串表、图元、动画、调色板…）
save/save.bin  = 1471 条全局变量(8B/条) + 20 字节设置头 + 1MB 已读文本位图
                 + 256B Flag 位图 + u32 + 字体名("メイリオ")
```

* 缩略图**没有 BMP 头**，是裸 BGRA；`s800.bin` 偏移 0xAF86 处的 `BM` 只是两个像素字节（`ff 96 42 4d ff`），**不是内嵌 BMP**。
* 尺寸 **200×113** 不写在槽文件里，槽文件按「引擎当前的 `SaveThumbSize`」解释；实际取值存在 `save.bin` 的 20 字节头里（+12/+16）。
* 时间戳不带秒，所以与文件 mtime 只精确到分钟。
* 槽文件的字符串编码混合：章节名是 CP932（日文原版脚本），当前对话行是 GBK（汉化版脚本）。

## 1. 文件名的来源

| 用途 | 格式串 | VA | 用它的函数 |
|---|---|---|---|
| 存档槽 | `%s/save/s%03d.bin` | `0x45DA64` | 写 `0x43F811`、读 `0x43EEC8` 附近 `wsprintfA` |
| 全局设置 | `/save/save.bin` | `0x45DBBC` | 写 `0x43932F`、读 `0x439B5F` 附近 |

槽号 `%03d` 直接来自 `SaveWrite`/`Load` 的参数（0..999），所以 `s481.bin` 就是槽 481。

相关 handler（`fvp/work/vm_id_handler.json`）：

|---:|---|---:|---|
| 93 | SaveCreate | 2 | `0x43C060` |
| 94 | SaveThumbSize | 2 | `0x43C180` |
| 95 | SaveData | 3 | `0x43D710` |
| 96 | SaveWrite | 1 | `0x43C1E0` |
| 40 | Load | 1 | `0x43A870` |

实现侧关键函数：

| VA | 作用 |
|---|---|
| `0x43DE90` | **存档槽序列化**（写内存缓冲） |
| `0x43F0C7` 起 | 存档槽反序列化（读） |

### 1.1 存档请求的消费路径（`engine` 帧更新里的那一段，2026-11-24 复核）

`SaveWrite`/`Load` 只是**置请求标志**，真正的动作发生在引擎帧更新的
`0x43F7C2` 一带（`bl` = 0 作比较值）：

```
43f7c2: cmpb %bl,0xfc8(%esi)   ; engine+0xfc8（槽列表/模板是否就绪）
43f7c8: je   0x43f7de
43f7cc: mov  %bl,0xfc8(%esi)   ; 清掉
43f7d2: call 0x43de90          ; 写槽的头部/版本字段
43f7d7: movb $0x1,0xfc9(%esi)  ; engine+0xfc9 = 1（快照就绪）
43f7de: cmpb %bl,0xfca(%esi)   ; engine+0xfca = SaveWrite 请求
43f7e6: cmpb %bl,0xfc9(%esi)   ; 且快照就绪
43f7ee: mov  0xfcc(%esi),%ecx  ; engine+0xfcc = 槽号
43f7f4: mov  %bl,0xfca(%esi)   ; 清请求
...
43f812: call 0x4488b7          ; wsprintfA 拼 "%s/save/s%03d.bin"
43f821: call 0x433fb0          ; 把内存里的槽写进这个路径
43f830: call 0x438300          ; engine+0x14（save.bin 对象）的收尾
43f837: call 0x4396f0          ; save.bin 序列化
```

所以「游戏内保存不生效」在本站的两个真实缺口是：

1. **外壳没有消费请求**：`fvp_vm_take_save_request()` 拿到槽号后要用
   `fvp_save_slot_path()` 拼路径、再用模板槽写文件（模板写入的代码在
   `src/platform/win32/main_win32.c` 的 `write_save_preview()`）；
2. **内存快照未解**：`0x43DE90` + 之后那一大段（约 500–597 KB）才是"读回来能接着玩"
   的关键，`src/save.c` 目前按不透明字节原样透传。

## 2. 存档槽 `sNNN.bin`

### 2.1 头部：7 字节本地时间 **确证**

```c
// 0x43DE90 起
GetLocalTime(&st);          // 0x43DEA5  call *0x45D0C8
cursor = 0;
write_u16(st.wYear);        // SYSTEMTIME +0
write_u8 (st.wMonth);       // +2
write_u8 (st.wDay);         // +6
write_u8 (st.wDayOfWeek);   // +4
write_u8 (st.wHour);        // +8
write_u8 (st.wMinute);      // +10
// 注意：wSecond / wMilliseconds 没有写
```

读取侧（`0x43EFCE`）：

```asm
43efcc: mov    (%esi),%eax
43efce: movl   $0x7,0x8(%esi)      ; ← 游标直接跳到 7，确认头长 7 字节
43efd5: movswl 0x7(%eax),%eax      ; ← 偏移 7 是 str0 的 i16 长度
43efd9: movl   $0x9,0x8(%esi)
```

| 偏移 | 类型 | 字段 | s481 | s485 | 说明 |
|---:|---|---|---|---|---|
| 0x00 | u16 LE | 年 | 0x07E7 = 2023 | 2023 | |
| 0x02 | u8 | 月 | 03 | 03 | |
| 0x03 | u8 | 日 | 0x13 = 19 | 19 | |
| 0x04 | u8 | 星期 | 00 = 日 | 00 | `wDayOfWeek`，0=周日；2023-03-19 确是周日 |
| 0x05 | u8 | 时 | 0x17 = 23 | 23 | |
| 0x06 | u8 | 分 | 0x2B = 43 | 0x2C = 44 | |

6 个样本全部与 mtime 的**日/时/分**一致（mtime 秒数为 26/38/36/27/32/28，格式里没有秒）：

| s800.bin | 2023-03-19 23:44 | 23:44:36 | 0 分 |

### 2.2 三条长度前缀字符串 **确证**

```
u16 len   （不含 NUL）
u8  bytes[len]
```

写侧用 `0x4343C0(len, ptr)`（**不含 NUL**），读侧在 `0x43EFF8` 分配 `len+1`、拷贝 `len` 字节、手工补 `0x00`。

来源就是 `SaveCreate` 的三个分支（`0x43C060`）：

| `SaveCreate(0, s)` | `0x43C0B6` → `0xFB4` | 章节名 / 存档标题 |
| `SaveCreate(1, s)` | `0x43C0E2` → `0xFB8` | 本作**从未用字符串调用**（样本全空） |
| `SaveCreate(2, s)` | `0x43C106` → `0xFBC` | 当前对话行（存档画面预览用） |

证据：

* 脚本里 `pushint8 0; pushglobal 863; syscall 93`（`iroseka.hcb` @0x23AB9）——global 863 是章节名；
* 脚本里 `pushint8 2; pushglobal 227; syscall 93`（@0x23BF8）——global 227 是当前文本；
* 还有一个调试调用 `pushint8 2; pushstring "ＭＡＰ　ＭＯＶＥＭＥＮＴ"; syscall 93`（@0x23AC6）。

样本实测（解码为混合编码，工具内按"更像文本"的一侧选取）：

| 文件 | str0（章节名） | str1 | str2（当前对话行） |
|---|---|---|---|
| s481.bin | `プロローグ`（CP932，10 B） | 空 | `　……。`（GBK，8 B） |
| s485.bin | 空 | 空 | 空 |
| s800.bin | 空 | 空 | 空 |
| s901.bin | 空 | 空 | 空 |
| s905.bin | `プロローグ`（CP932） | 空 | `　谁这样说道。`（GBK，14 B） |

> 编码混用不是笔误：层数据来自日文原版 `iroseka.hcb`（CP932），对话文本来自汉化 `.iroseka.hcb`（GBK）。

### 2.3 缩略图：裸 BGRA，**无文件头** **确证**

紧跟第 3 条字符串之后，是 `w*h*4` 字节的 **BGRA**（B,G,R,A）像素：

```c
// 0x43E0F9
n = engine->thumb_w * engine->thumb_h;
buf = malloc(n*4);
render_thumb(buf);                      // 0x4255C0
write_bytes(buf, n*4);                  // BGR(A)，alpha 恒 0xFF
```

读取侧（`0x43F0C7`）用 `engine+0xFD4 * engine+0xFD0 * 4` 计算长度，再 `memcpy` 回来。

**尺寸不写在槽文件里**：读写两侧都直接用引擎当前的 `engine+0xFD0/+0xFD4`。
这两个值由 `SaveThumbSize(w,h)`（`0x43C180`，w∈20..200、h∈15..150）设置，
并且会被写进 `save.bin` 的 20 字节头（+12/+16）。本作实测 = **200×113**（16:9 ≈ 1.770）。
引擎初值是 `0x60×0x48` = 96×72（`0x440EB1` / `0x440EBB`）。

尺寸的自动化判据（工具里用它兜底）：缩略图 alpha 恒为 0xFF，从图起点数"每第 4 字节 == 0xFF"的连续长度，
等于 `w*h`（图后的引擎数据几乎不可能满足）。6 个样本全部得到 **22600 = 200×113**。

`s481.bin` 头 + 缩略图开头：

```
00000000  e7 07 03 13 00 17 2b 0a 00 83 76 83 8d 83 8d 81  |......+...v.....|
00000010  5b 83 4f 00 00 08 00 a1 a1 a1 ad a1 ad a1 a3 ff  |[.O.............|
00000020  ff ff ff ff ff ff ff ff ff ff ff ff ff ff ff ff  |................|
```

* `e7 07` 年 2023，`03` 月，`13` 日 19，`00` 周日，`17` 时 23，`2b` 分 43；
* `0a 00` str0 长 10 → `83 76 … 83 4f` = `プロローグ`；
* `00 00` str1 空；`08 00` str2 长 8 → `a1 a1 … a1 a3`（GBK `　……。`）；
* **0x1F** 起是缩略图第一个像素 `ff ff ff ff`（白色，该存档是在全白淡出时存的）。

`s485.bin`（三条字符串全空，缩略图从 0x0D 开始）：

```
00000000  e7 07 03 13 00 17 2c 00 00 00 00 00 00 25 2d 2d  |......,......%--|
00000010  ff 25 2e 2c ff 25 2e 2d ff 25 2e 2c ff 24 2e 2d  |.%.,.%.-.%.,.$.-|
```

**关于 `s800.bin` 的 `BM`（0xAF86）**：这是误判。0xAF86 落在缩略图数据内部：

```
0000af7c  ff 9d 7b 84 ff 7a 63 76 ff 96 42 4d ff a4 63 54  |..{..zcv..BM..cT|
```

`42 4d`（`BM`）前后都是像素三元组，前面的 alpha 字节是 `ff`，后面 `ff a4 63 54` 也是像素。
按 BMP 解析会得到 size=1415816447、dataoff=2459400959，明显不成立。

### 2.4 缩略图之后的正文区 **部分确证 / 推定**

#### 2.4.0 先用数据量出来的事实（`tools/tailstat.py`）

在不猜字段语义的前提下，6 个真实槽的尾段能直接量出这些：

| 观察 | 数值 |
|---|---|
| 尾段长度 | 502,020 – 598,984 字节（随内容变化，不是定长） |
| 非零字节占比 | 61,057 – 95,436，约占尾段 **11–16%**（其余是零填充，字段稀疏） |
| 尾段开头 | 6 个槽**完全相同**：前 24 字节全 0，第 25 字节起是 `02 00 00 00` |
| 尾段结尾 | 6 个槽**完全相同**：末 16 字节为 14 个 0 + `01 01`（与旧结论一致） |
| 常量尾长度 | 两两共同后缀 **1,438 – 1,449 字节**（≈1.4 KB 的固定块） |
| 常量头长度 | 两两共同前缀 ≥ **64 字节**（部分槽对到 130 字节） |

结论（可直接写进代码的部分）：

* 尾段 = `≥64B 常量头` + `变长中段` + `≥1438B 常量尾`。解析可以「先跳常量头、再按尾部常量块对齐」，
  不必知道中段每个字段的含义就能保住字节。
* 中段长度随存档内容变化（差 ~97 KB），所以**不能**用固定偏移写死；写回时必须整体保留原中段。

复现：`python fvp/tools/tailstat.py <save 目录>`。

#### 2.4.1 变长中段的密度结构（实测，6 个槽一致的地标）

把中段（`tail[64 : len-1438]`，500,518–597,482 B）按 **4 KiB 块 / 非零密度 5%** 分段，6 个槽
出现完全一致的地标序列：

| 段 | 相对中段起点 | 长度 | 6 槽是否一致 |
|---|---|---:|---|
| 前段 DENSE | +0x00000 | 4,096–16,384 | 槽间有 ≤8 KiB 的整体平移 |
| **零区（固定）** | **+0x04000** | **86,016** | **一致**（s901/s906 因前段偏移变为 90,112 / 86,016） |
| **变长 DENSE 区起点** | **+0x19000** | — | **一致（102,400 这个偏移在 6 个槽里完全相同）** |
| 变长 DENSE 区 | +0x19000 | 229,376–331,776 | 随存档内容变化（差 ~102 KB） |
| **固定稀疏块** | 紧接变长区 | **118,784** | **一致**（s906 在它前面多插了 8,192 B） |
| 固定尾链 | 之后 | 12,288 / 4,096 / 4,096–8,192 / 8,192 / 4,096 / 8,192 / 收尾 1,923–4,947 | 段长一致，收尾块长度随内容变 |

两个可直接用的结论：

* **`+0x19000` 是 6 个槽共同的分界**：之前是「前段 + 86 KB 零区」，之后才是随内容变化的大块。
  写回/解析都可以以此为锚点做自检（`tail[0x19000+64]` 必须落在变长区的第一个字节附近）。
* **118,784 字节的稀疏块**（约 116 KiB）在所有槽里都存在、尺寸与内容无关。
  **§2.4.2 已实测否掉「32 个文本窗口」这个猜想**：5 个槽里它几乎全零（31–112 个非零字节），
  只有演出中途存的 s906 里填了 17 字节周期的记录流 —— 更像动画/事件队列。

复现：`python fvp/tools/tailstat.py <save 目录>` 后再用 4 KiB 密度分段（脚本里已含常量区部分；
密度分段见该工具 README 注释）。

#### 2.4.2 那个 118,784 B 稀疏块里到底是什么（实测）

| 槽 | 块内非零字节 | 占块比例 |
|---|---:|---:|
| s481 / s485 / s800 / s901 / s905 | 103 / 112 / 98 / 31 / 104 | **0.03–0.09%** |
| s906（唯一一个在演出中途存的） | **454** | 0.38% |

5 个槽里这块几乎全零 ⇒ **它不是「32 个文本窗口的内容」**（窗口内容不会全空）。s906 里它有数据，
且是**规则重复的记录流**：

```
+0x51000  16 01 | f4 ff ff ff | 34 03 00 00 | 00 00 | 06 00 00 ff 00
+0x51011  f9 05 | f4 ff ff ff | 34 03 00 00 | 00 00 | 07 00 00 ff 00
+0x51022  f2 05 | f4 ff ff ff | 34 03 00 00 | 00 00 | 08 00 00 ff 00
+0x51033  eb 05 | f4 ff ff ff | 34 03 00 00 | 00 00 | 09 00 00 ff 00
```

* 周期 **17 字节**（非零段起点差恒为 12 / 3 / 2）；
* 每条约含 `int32 = -12`、`u32 = 820`、以及一个**递增 1 的序号**（6,7,8,9）与若干 0 / 0xFF；
* 首字段 `16 01` / `f9 05` 按小端是 278 / 1529 / 1522 / 1515（首个可能被截断，对齐待定）。

**结论（限定表述）**：这是一张「平时为空、演出/动画进行时被填」的表，记录长度 17 字节、
内容像动画/事件队列；**不是** 32 个文本窗口。文本窗口快照因此在别处 —— 早先 §2.4 表 B
的 `32 × 0xB1D` 仍只是推定，未在数据中找到对应块。

复现：`tools/tailstat.py` + 4 KiB 密度分段后取稀疏块，逐字节差分（s906 与其他槽差 485–566 B）。

#### 2.4.3 常量尾的内部结构（实测，6 个槽逐字节相同）

对 1,438 字节的常量尾做「非零字节偏移 / 间距 / 取值」统计，得到：

```
共 1,438 B = 216 × 6B 的定长表 + 140 B 全零 + 末 2B `01 01`
每条 6 字节记录内容完全相同：00 00 64 00 00 00   （即 u16 ×3 = 0, 100, 0）
非零字节：216 个 0x64（=100）全部落在记录内偏移 +2，间距恒为 6
```

| 段 | 偏移（相对常量尾） | 长度 | 内容 | 状态 |
|---|---:|---:|---|---|
| 表 | 0 – 1295 | 1,296 | **216 × `{u16 0, u16 100, u16 0}`** | 结构确证，语义未解（100 很像某个默认值/音量） |
| 零区 | 1296 – 1435 | 140 | 全零 | 未解 |
| 尾标记 | 1436 – 1437 | 2 | `01 01` | 与 §2.4 表 Q 一致 |

216 条这个数量与已知的表（32 文本窗口、10 音频类型、256 SE/音频槽）都对不上，**先按「定长 216×6 表」
对待**：写回存档时整段原样拷贝即可，不必知道每个字段含义。

复现：`python fvp/tools/tailstat.py <save 目录>`（末尾的「常量区」小节）。

`0x43DE90` 的写出顺序（`esi` = 写缓冲结构 `{base, cap, cursor, grow}`，`0x434060` 扩容）：

| 段 | 内容 | 长度 | 状态 |
|---|---|---:|---|
| A | 每槽全局变量 | `8 × countA` | 推定（本作 `countA` 疑似 **0**） |
| B | 32 个文本窗口快照 `engine+0x68DFC0 + i*0xB28` | `32 × 0xB1D` = 91040 | 推定（每窗口长度由 `0x445640` 写死） |
| C | 当前文本窗口号 u32 | 4 | 推定 |
| D | 动态字符串表：u32 计数 + 128 槽 | 4 + Σ(2+len) | 推定 |
| E | 两个 0x100 字节块（`0x6A4BEC` / `0x6A4CEC`） | 0x200 | 推定 |

#### 2.4.4 快照的分段结构：`0x43DE90` 的写入顺序（2026-11-24 结构分析）

`0x43DE90` 不是一个"只写时间戳"的小函数，而是**整个 `sNNN.bin` 的序列化器**：
函数从 `0x43DE90` 到 `0x43E67B` 共 **685 条指令 / 62 次 call**，`this` 就是引擎对象，
缓冲区在 `engine+0x00`（数据）、`+0x04`（容量）、`+0x08`（已写长度）、`+0x0C`（扩容粒度）：

```
43de97: lea 0x14(%esp),%eax     ; SYSTEMTIME*
43de9e: movl $0x0,0x8(%esi)     ; engine->len = 0
43dea5: call *0x45d0c8          ; GetLocalTime(栈上 16B)
43dedb: mov %di,(%edx,%eax,1)   ; 写 u16 年 …
```

按写入顺序把各段列出来（"引擎偏移"是数据来源，"子序列化器"是它调用的函数）：

| # | 段 | 引擎偏移 | 条数 / 字节 | 子序列化器 |
|---:|---|---|---|---|
| 1 | 时间戳 7 B | 栈上 GetLocalTime | 7 | 内联（`0x43DEAB` 起） |
| 2 | 三条长度前缀字符串 | 槽对象内的 str[0..2] | 3 条 | `0x4343C0` ×3 |
| 3 | 缩略图（从窗口对象抓） | `engine+0x8C`（窗口对象） | w*h*4 | `0x4255C0`，像素拷贝 `0x447800` |
| 4 | **32 个协程上下文** | `engine+0x68DFC0` | 0x20 × 0xB28 = **91,648 B** | `0x445640` |
| 5 | **字符串句柄表** | `engine+0x6A49EC` | 0x80 = **128 条** | `0x434410` |
| 6 | 字符串内容块 | `engine+0x6A4BEC` / `+0x6A4CEC` | 0x80 起 | `0x447800` ×2 |
| 7 | 另一组块 + 表 | `engine+0x6A4DF0` / `+0x6A61F0` / `+0x6A63F0` | — | `0x445330`、`0x447800` ×2、`0x4386D0` |
| 8 | **调色板**（ColorSet 写的 256 色） | `engine+0x6A44C0` | **0x400 B**（256×4） | `0x447800` |

| 10 | **外字表** | `engine+0x6A49CC` | — | `0x43DCE0` |
| 11 | 两组小对象 | — | 0x40 项 | `0x4292B0`、`0x429570` |
| 12 | **prim 数组** | `engine+0x61DD64` | **0x34000 B**（4096 × 0x34） | `0x447800` |
| 13 | 位置补间管理器 | `engine+0x651D70` | — | `0x426410` |
| 14 | 透明度补间管理器 | `engine+0x651E04` | — | `0x426830` |
| 15 | 帧动画管理器 | `engine+0x65380C` | — | `0x426CD0` |
| 16 | 移动补间管理器 | `engine+0x65BA54` | — | `0x426F40` |
| 17 | 另两组补间 | `engine+0x679A5C` / `+0x67CE64` | — | `0x427750` ×2 |
| 18 | 三个子对象 | `engine+0x680A6C` / `+0x683E74` / `+0x683F04` | — | `0x4287D0`、`0x428020` |
| 19 | 收尾若干块 | `0x42D880`、`engine+0x8C->0x2D4`、`0x441320`、`0x684378`、`0x6893C0` | — | `0x42D880`、`0x4221E0`、`0x441320`、`0x429EA0` ×2 |

**量级自检**：prim 数组 **0x34000 = 212,992 B** 加 32 个协程上下文 **91,648 B** 就已经
**304,640 B**，再加调色板 1 KB、字符串表与各补间管理器，正好落在实测槽文件
**约 500–597 KB** 的量级上 —— 结构对得上，这是"分段表没读歪"的一个独立证据。

**找锚点的尝试（本轮，失败但有用）**：想用"调色板块"当锚点（`palette[0]=0xFF000000`、
`palette[1]=0xFFFFFFFF`、其余 alpha 全 0xFF，共 1024 B）来在真实 `sNNN.bin` 的尾部
定出绝对偏移 —— 在 6 个真实槽里**一个都没找到**。原因大概率是调色板条目会被脚本的
`ColorSet` 覆盖（本作确实调用 ColorSet），初始黑/白早就不在了。**下一个锚点候选**：
prim 数组（4096×0x34，其中大量 `type==0` 的空记录本身就是特征）或 32 个协程上下文
（0xB28 记录里含 pc/sp 等小整数）。这条已记下来，避免下轮重复踩坑。

**还缺的**：每一段**内部**的字段语义（例如 prim 数组里 0x34 字节各字段、协程上下文
0xB28 字节各字段）。好消息是这两块我们已经**在运行时建模过**（`GfxPrim` 的字段偏移、
`FvpThread` 的上下文字段都从静态分析确认过），所以读档时可以按同一套结构反序列化，
不需要再解一遍 —— 剩下要确认的是各段的**顺序/长度前缀**与"读回来之后哪些字段要重建
（纹理、字符串句柄）"。

### 2.5 与命令的对应

| 命令 | 对存档的影响 |
|---|---|
| `SaveCreate(0, s)` | 写 `engine+0xFB4` → 槽头 **str0** |
| `SaveCreate(1, s)` | 写 `engine+0xFB8` → 槽头 **str1**（本作未用） |
| `SaveCreate(2, s)` | 写 `engine+0xFBC` → 槽头 **str2**（当前对话行） |

| `SaveWrite(slot)` | 置 `engine+0xFCC=slot`、`0xFCA=1`；`0x43F7D2` 处触发 `0x43DE90` 序列化并写到 `%s/save/s%03d.bin` |
| `SaveData(kind, …)` | 写"存档暂存区"（`engine+0x14` 起，1000 条表 + 分类字段），**未完全解读**（kind 0..13，见 §4） |

`SaveWrite` 之后 `0x43F7D7` 还会置 `engine+0xFC9=1`，之后 `0x43F7DE` 的
`engine+0xFCA` 分支才真正落盘；`0x4396F0` 与 `0x43DE90` 是两条独立路径
（前者写 `save.bin`，后者写槽）。

#### `SaveData` 在本作里到底被用了几次（2026-11-24 实测）

用 `fvm --dump-savedata` 统计真实脚本：**90 万步、200 万步都只有 3 次调用**，
而且参数完全固定：

```
savedata 0: kind=2 idx=900 value=1
savedata 1: kind=2 idx=903 value=1
savedata 2: kind=2 idx=904 value=1
```

含义推定：`kind=2` 是"已读文本/进度标记"，`idx` 是编号、`value=1` 是"置真"，
即**只用来打三个已读标记**，不是"把整个游戏状态摊平"的入口。所以
槽尾那 500–597 KB 的引擎状态**不是**由 `SaveData` 拼出来的，而是
`0x43DE90` 直接序列化引擎内部结构 —— 这也解释了为什么解 `SaveData` 的
kind 语义并不能直接换来"能写存档"。

C 侧现状：`src/syscall.c` 的 `case 95` 把这 3 条记录进 `FvpVM.save_data[]`
（上限 256 条 + 溢出计数），`fvm --dump-savedata` 打印；外壳退出总结打印
`savedata N record(s) of M call(s)`。

### 3.3 全局变量数组：1471 × 8 字节 **确证（布局）/ 推定（名称）**

> "全局变量"这个名字是推断：`0x68DFBC` 存放的是与 VM `Value` 同构的 8 字节记录，
> `0x437210` 按下标 `countA + arg` 读取、只接受 `type==2` 的整数，
> 而样本里类型 0（未设）占 480 条、与"脚本全局变量大多未初始化"一致。
> 数组的基址/步长/条数/取值语义是确证的；它不是引擎设置结构体。

```
+0  u8   type        0 = 空/未设，2 = int（已确证），1 = 未定
+1  u8   pad         未初始化堆垃圾（A/B 两版在同一位置不同）
+2  u16  pad
+4  u32  value
```

证据：

* `0x437210` 是取值器：`idx = engine->[0x6A66C8] + arg; e = arr + idx*8;
  return (e->type==2) ? e->value : 0;`（`cmpb $0x2,(%ecx,%eax,8)`）。
* `0x43DE90` 的 `0x43E1C8`：`count = engine->[0x6A66C8]`，`src = arr`，写 `count*8`；
  但**槽文件**这一段在样本里是 0 字节（`countA=0`）。
* `0x4396F0` 的 `0x439743`：`count = engine->[0x6A66CC]`（=1471），
  `src = arr + countA*8`，写 `countB*8` → 就是 save.bin 的 0x0000 段。
* 读侧 `0x43939B` 反向 `memcpy` 回 `arr + countA*8`。

样本统计（A 版）：`type 0` = 480、`type 1` = 846、`type 2` = 145。
`type 2` 的值开头是 `5, 5, 1, 0, 0, 180, 255, 128, 100, 90, 70, 70, 65, 100, …`
——很像一组音量/文字速度/透明度之类的设置，但这些变量由脚本（全局变量）驱动，
**无法只靠引擎代码给每个下标命名**（见 §4）。

### 3.4 已读文本位图：1 MB / 8,388,608 bit **确证**

* 基址就是 `engine+0xFDC`，长度 `0x100000`。
* 位操作出现在：
  * `0x43CB85`（`TextPrint` 路径内）：`idx < 0x800000`，`arr[idx>>5] |= 1<<(idx&31)`，
    置位后把 `ctx+0x814` 写成 1（命令返回 true）→ **"这段文本已读过"**。
  * `0x437A96`：同样的 test-and-set，置位后写 `ctx+0x815`/`CTX` 的返回槽。
* 上限 `cmp $0x800000` 正好对应 1MB × 8 bit。
* 样本已置位 **50,792 bit**。
* 槽文件里**没有**这段——已读标记是全局的，只在 `save.bin`。

> 这就是跳过已读文本（`FC`/`skip`）用到的数据。`save.bin` 因此有 1MB 固定体积。

### 3.5 Flag 位图：256 B / 2048 bit **确证**

* 基址 `engine+0x6A48C0`，长度 `0x100`，与 `FlagGet`/`FlagSet`（id 18/19，
  handler `0x43A270` / `0x43A2E0`）使用的位图**同一地址**（见 `docs/vm-commands.md` §6-6）。
* 样本全部为 0 —— 与本作脚本从不调用 `FlagSet` 吻合（`docs/00-engine.md` §4）。

### 3.6 字体名 `メイリオ` **确证**

* 字符串在文件末尾，由 `0x439B31` 从 `engine+0x6A66C0` 用 `0x434410` 写出；
  该 helper 写 `u16 长度(含 NUL) + 字节`，与读侧 `0x433F60` 对应。
* 值就是 `メイリオ` = **Meiryo**，Windows Vista 之后的日文 UI 常用字体，
  也是本作 `TextFont`/`TextFontName` 的默认字体名。
* 尾部的 u32（A=0，B=9）紧接着字体名，疑为"字体索引/字体数量"，未定。

### 3.7 两份 save.bin 的差异（普通 vs 附带的"全 CG 存档"）

`save/HD版适配全CG存档/iroseka_hd/save.bin` 与本目录的 `save.bin` **同样大小**，
逐字节比较只有 **20 字节**不同：

| 偏移 | 段 | A（普通） | B（全 CG） |
|---:|---|---|---|
| 0x2DF8 | 20B 头 +0（`gfx+0x1FC`） | 0 | **1** |
| 0x88 | 全局变量表第 17 条 +2 | 3 | 1 |
| 0x1A0 | 第 52 条 | … | … |
| 0x310 / 0x314 | 第 98 条 | … | … |
| 0x1692 … | 第 ~723 条 | … | … |
| 0x21AC / 0x2DDC | 表尾若干条 | … | … |
| 0x85445 … 0x8545D | 已读位图 +0x85445 | … | 多 5 字节置位 |
| 0x102F0C | 尾 u32 | 0 | 9 |

全局变量表里变的多是第 2 个填充字节（未初始化垃圾）而 value 相同——真正有意义的
差异集中在 `20B 头 +0` 和已读位图。**结论：`gfx+0x1FC` 那个字节最可能是"全 CG/已通关"标志**，
但它不是 2048 bit 的 Flag 位图（那张表两版都为 0）。

## 4. 已知 / 未知清单

### 已确证

1. 槽头 7 字节时间戳（无秒），字段顺序 = SYSTEMTIME 的 年/月/日/星期/时/分。
2. 三条 `u16 长度 + 字节` 字符串；str0=章节名、str2=当前对话行。
3. 缩略图 = 裸 BGRA、尺寸来自引擎设置（本作 200×113）、不写进槽文件、无 BMP 头。
4. `save.bin` 尾部结构（1MB 已读位图 + 256B Flag 位图 + u32 + 字体名）。
5. 20 字节头里的缩略图宽/高。
6. 全局变量数组基址/步长/条数（1471）与"type==2 即 int"的取值语义。
7. 文件名格式串与读写函数地址。

### 推定

1. 槽内"每槽全局变量"条数 `countA = 0`（全零区无法 100% 排除）。
2. 32 个文本窗口快照的段长 0xB1D、次序。
3. `save.bin` 头 +0 的字节是 CG/通关解锁标志（依据：两版唯一有意义的头差异）。
4. 全局变量表里前几条 `5, 5, 1, 0, 0, 180, 255, 128, 100, 90, …` 像音量/速度设置。

### 未解

- 快照各段**内部**的逐字段语义 —— 分段结构已在 §2.4.4 摸清；其中 prim 数组
  （0x34×4096）与协程上下文（0xB28×32）的字段偏移我们在渲染/VM 侧都已经确认过，
  可以直接复用，剩下要确认的是各段的顺序/长度前缀，以及"读回来之后哪些字段要重建"
  （纹理、字符串句柄）

- 快照各段**内部**的逐字段语义（分段结构已在 §2.4.4 摸清；prim 数组与协程上下文的
  字段偏移我们在渲染/VM 侧已经确认过，可直接复用）

1. **`SaveData` 的 14 种 kind（0..13）**：`0x43D710` 是按 kind 分派，
   已读出：kind 0 = 清空 1000 条表（`0x438300`）；kind 1 = 标记某条（`0x4382A0` / ctx+0x68E7D4）；
   kind 3 = 写 `(id, 字符串)`；kind 4/5/6 = 分配字符串句柄写入 `engine+0x6A49EC` 表；
   kind 7 = 写返回槽类型。其余未读完。
2. 图元（4096 × 0x51C）、动画管理器（64 × 0x34）、primitive 数组（0x34000）的序列化细节。
3. 文本窗口 0x800 字节缓冲的编码（UTF-16？混合？）与 `ctx+0x814/0x818` 的确切含义。
4. `save.bin` 头里 +1/+2/+6/+10/+11 五个字段的语义。
5. `type == 1` 的全局变量到底是什么（值域与 int 重叠；疑似引擎内部的另一种数值表示）。
6. 槽尾 `L`~`P` 各子写器的长度公式（决定能否完整解析/重写）。

## 6. 如果要**写入**存档，还缺什么

### 能安全做的（只改已确证字段）

> 这条路径已有自动化验收：`tests/test_save.c` 拿真实槽当模板，改时间戳 / 章节名 / 缩略图后
> 写盘再读回，断言**引擎状态尾段逐字节不变**（真实样本合计 59 项断言）。

* 改槽头时间戳（7 字节）→ 重算即可，格式固定。
* 改 str0 / str2（长度前缀字符串）→ 只需重排后续偏移，长度任意（`u16`）。
* 换缩略图像素（`w*h*4` BGRA）→ 只要 **不改尺寸**，可以原地替换。
* 改 `save.bin` 的 20 字节头（缩略图尺寸、几个标志位）与尾部字体名。

### 要生成"完整新存档"还缺的信息

1. **引擎状态的序列化规则**：32 个文本窗口、字符串表、图元/动画/primitive 区。
   目前只知道各段长度与部分字段偏移，不知道每个字段的合法取值范围与耦合关系
   （例如 `ctx+0x814/0x818` 是命令返回值槽，乱填会让脚本读到脏值）。
2. **`countA` / `countB` 的权威来源**：它们来自 `iroseka.hcb` 加载时读取的
   两个 i16（`0x438F88`/`0x438FA5`），但 `.hcb` 的实际头部与此读取逻辑的对应关系没验证完；
   样本上表现为 `countA=0, countB=1471`，换脚本/换版本可能变。
3. **`SaveData` 的 kind 语义表**（0..13）：它才是脚本"把游戏状态摊平成可存数据"的入口。
   不读懂它，就无法从运行时状态推导出应该写成什么。
4. **字符串表项格式**（`0x434410`：`u16 长度含 NUL + 字节`）与 `0x6A49EC` 的
   128 槽引用计数表（`0x6A4BEC`/`0x6A4CEC` 两个 0x100 字节块）的维护规则。
5. **已读位图的 bit 索引含义**：`idx` 上限 0x800000，但索引到"哪段文本"的映射
   （脚本偏移？文本行号？）没确认，所以只能复制不能增量生成。

**实践建议**：写存档时以"读现有文件 → 改确证字段 → 原长度写回"为主；
若必须改长度，优先只改字符串段并整体平移后续字节（引擎读取是纯顺序游标，不带偏移表）。

## 7. C 实现（`src/save.c`）

按上面的"实践建议"落地：**只解释已确证字段，其余字节原样透传**。

| API | 作用 |
|---|---|
| `fvp_save_slot_load()` / `fvp_save_slot_store()` | 槽文件解析 / 重写（时间戳 7B、三条长度前缀字符串、`w*h*4` 裸 BGRA 缩略图、尾段不透明字节） |
| `fvp_save_thumb_size_guess()` | 尺寸未知时按 alpha 连续长度推断（`docs/save-format.md` §2.3 的判据） |
| `fvp_save_bin_load()` / `fvp_save_bin_store()` | `save.bin` 解析 / 重写；**从文件尾反推布局**，不依赖任何计数器（§3.1 的判据） |
| `fvp_save_slot_size()` / `fvp_save_bin_size()` | 序列化所需字节数 |

设计取舍：

* **字符串保留原始字节**，不转码 —— 槽里章节名是 CP932、汉化版对话行是 GBK，转码会破坏原字节。
* **尾段不解释**：32 个文本窗口快照 / 图元 / 动画区属于 §4 的"未解"，重排它们等于把没搞懂的
  状态写坏，所以只按长度原样搬。
* `save.bin` 的字体名长度是 `i16`（含 NUL）且紧贴文件尾，因此读取侧从尾部试
  `n = 1..64`，找到"该处 u16 恰为 `n+1`"的候选即认定为字体名 —— 这样换脚本 / 换版本导致
  全局变量条数变化时仍然能解析。

验收（`tests/verify_save.ps1`，已并入 `tests/run_all.py` 的第 6、7 步）：

| 项 | 结果 |
|---|---|
| 合成用例（自检） | **50 项全过**：空槽、超长字符串拒绝、畸形/截断输入拒绝、alpha 尺寸推断、`save.bin` 幂等回环 |
| 6 个真实存档槽 | **逐字节回环一致**，时间戳 / 章节名 / 对话行 / 200×113 缩略图 / 尾段长度全部与本文地面真相吻合 |
| `save.bin` | 1471 条全局变量、缩略图 200×113、字体名 `メイリオ`（8 字节） |
| 检查总数 | 槽回环 **44 项** + 自检 **56 项**，0 失败 |

另有**字节布局回归钉**：一份 52 字节的合成槽（时间戳 + 三条字符串 + 2×2 缩略图 + 5 字节尾段）
序列化后的 FNV-1a 64 固定为 `0x55bc2d006a29f2bf`。以后若有人改动序列化顺序 / 字节序 / 漏写字段，
`make test_save` 会立刻失败。注意这是「布局钉」，不是格式定义 —— 真要改布局必须连这个常数一起改。

> 注意：回环一致只能证明"边界切对了、没有丢字节"，**不能**证明槽内引擎状态被正确解释。
> 真正的存/读档还需要 §4 的 `SaveData` 语义与 `countA/countB` 的权威来源。

### 7.1 全局变量桥（`src/save_vm.c`）

`save.bin` 里唯一能安全还原成运行时状态的就是 §3.3 的全局变量表，而且只有 `type == 2`
（已确证的 int）那 145 条能安全灌进 VM；`type == 1` 的 846 条语义未解（§4 未解 5），
一律跳过并报数，避免把脏值写进脚本变量。

| API / 开关 | 作用 |
|---|---|
| `fvp_save_globals_apply()` | 把 `type==2` 的记录写进 `FvpValue globals[]`；输出 `total/ints/unknown/unset/skipped` 统计。`globals` 传 NULL 时只统计 |
| `fvm --savebin FILE` | 启动 VM 前用 `save.bin` 播种全局变量，打印 `records/ints/unknown/unset` |
| `fvm --dump-globals FILE` | 写 `index value` 行（只写非零 int），用于和独立实现比对 |
| `fvp_save_find_file()` / `fvp_save_bin_load_file()` | 按 `<game>/save/save.bin`、`<game>/save.bin` 顺序找文件并解析；路径按 UTF-8 处理，Windows 上走 `_wfopen`（UTF-8 失败则退回 ANSI，兼容从 argv 拿到的路径） |
| 桌面外壳启动 | `fvp.exe` 在 `fvp_vm_start()` 前调用上面两个函数播种全局变量，日志见 `docs/win32-shell.md` §3 |
| `fvp_save_flags_apply()` | 把 `b->flags`（就是 §3.5 那 256 字节位图）拷进 `vm.flags`；`FlagGet`/`FlagSet`（命令 18/19）直接读写这张图，实现见 `src/flags.c` |

**类型编号陷阱**：存档里的 `2` 表示 int，而 VM 的 `FvpType` 里 int 是 `0`
（`INT=0/FLOAT=1/STR=2`）。两套枚举不能混用，否则会把字符串槽当成整数读。

验收（`tests/verify_save_vm.ps1`）：

| 项 | 结果 |
|---|---|
| 合成记录 | **19 项**：type 映射、`u32 → int32`（`0xFFFFFFF0` → `-16`）、容量不足时只统计不越界、`globals=NULL` 只统计、NULL 文件 |
| 真实 `save.bin` | **13 项**：1471 = **145 int + 846 unknown + 480 unset**（与 §3.3 完全一致），前 14 个 int 值 = `5,5,1,0,0,180,255,128,100,90,70,70,65,100` |
| `fvm --savebin/--dump-globals` | `--steps 0` 时导出 **114** 个非零 int（145 里 31 个为 0），前 12 行与 §3.3 逐个吻合 |
